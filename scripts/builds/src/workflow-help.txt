builds workflow: how work moves through worktrees, builds and landing, and how
a coordinator runs agents. Read it before you make a worktree, build, land or
dispatch an agent. A command refuses a step that lacks what it needs, so this
page states only what no command checks. The project file
(projects/<project>.md in agent-instructions) names the project's lists,
worktrees and standing rules, and `builds help lists` describes the lists: what
waits on the person and what agents can do. `builds brief` prints the coding
rules for the paths you will edit.

`builds ack`, which every agent runs at session start and after compaction,
prints the sections every agent uses, with the lists overview. A coordinator, a
design session and a judge also read the sections of their role, with `builds
ack --role coordinator`, `--role design` or `--role judge`: PLAN, BRIEF,
EXECUTE, DISPATCH and HEALTH CHECK for the coordinator, DESIGN CHANGES and
PUBLISHING DESIGNS for the design session, JUDGING for the judge. An agent that
takes up another role reads that role's sections the same way. `builds help
workflow` prints every section, and `builds help workflow DISPATCH` prints that
section alone, as for any page (`builds help`). When this text changes, the
next builds command an agent runs prints one line that gives `builds ack`, and
the agent runs `builds ack` to read the changed sections: no other command
counts the change as read.


ROLES

A coordinator session plans work and dispatches background agents, each with a
brief. The agents implement, review their own branches and land them.

A judge session settles the findings of those reviews (REVIEW). When it starts,
it runs `builds judge listen --project P` for each project it judges, and while
it listens, only it and the person give a verdict on a finding. When no judge
listens, the coordinator settles the findings, except those of a review the
coordinator ran, which an independent session settles.

A design session draws the boards (pictures of screens, kept in the repo) that
the apps are built to match: new screens, new layouts, and anything that needs
a new component or a change to the design system. It takes its items from
`builds next --for design-session`, from the top, in the order the coordinator
takes its own. When it starts, it runs `builds design listen --project P` for
each project it draws for, so that the dashboard can pass the person's publish
requests to it (PUBLISHING DESIGNS). When the person decides a change to an
existing screen that the design system's existing components can draw, such as
a button added to an alert, the implementing agent edits the board in the same
commit and names the decision. "Design" alone is ambiguous: write "board" or
"product design" for screens and how they look, and "software plan" for the
shape of code and data.

A question for the person goes on the stack first (`builds question ask`),
because the dashboard's Waiting on you tab shows only the stack. Then any
session may ask the person, or ask another session to ask them, naming the
entry's id.

No stack entry, work item or brief says that the person decided something
unless the sentence names where that is written: the decision that records it
(`decision #N`), a rule file such as rules/<group>/<rule>.md,
~/.claude/CLAUDE.md, the CLAUDE.md of repo <repo>, or a section of a builds help
page, such as builds help workflow, DISPATCH. A brief, an agent's earlier
summary or a line copied between briefs records nothing, and builds refuses a
write whose sentence names no source (`builds help lists`, RULINGS). When the
person has not decided, ask them instead of stating what they want.

Work that waits on the person, such as a step only they can take at their Mac,
goes on the stack as a your-step question (`builds question ask --kind
your-step`), and each item or held worktree that waits on it waits on
`question:N`. The dashboard shows such a wait under Waiting on you, and a wait
on a condition under Paused, so a condition names the agent, coordinator or CI
that ends it (`--until`), never the person.


WORKTREES

Each repo keeps a main checkout and side worktrees. The branch, not the
worktree, is the unit of work.

  - The main checkout stays on main, for iterative work and edits made with
    the person. No agent edits, builds, commits or cherry-picks there, the
    coordinator included, and `builds land` fast-forwards it after each
    landing (LANDING).
  - side-1 is the long-lived side worktree for background work: each feature
    or fix is a new branch from origin/main there. It stays built, so never
    delete or recreate it.
  - Extra side worktrees (side-2 and on) are for agents that work at the same
    time. An agent works in the worktree its brief names, or one it gets from
    `builds new --for`, never a side-N it picked by hand.
  - A claimed side worktree takes an agent's commands only on the branch of
    the item running in it.
    - `builds app-build`, `review`, `land`, `cargo`, `checks` and `item`
      refuse when an agent (`--agent` or BUILDS_AGENT) runs them there on
      another branch or a detached HEAD, and name the claim's holder and
      branch. A rebase or cherry-pick in progress passes, and so does a claim
      whose item has not started.
    - An agent that meets this refusal in a worktree it used before has lost
      that worktree to another agent: it works nothing there and gets its own
      from `builds new --for`.
  - App checkouts keep the app builds built. Each lane (mac, android) has its
    own app checkouts and queue, and agents take turns in them through
    `builds app-build`. builds adds and removes app checkouts as the queues
    need, so nobody adds one by hand (`builds help`, APP BUILDS).
  - agent-instructions, which holds builds, works the same way, in side
    worktrees from `builds new ~/dev/agent-instructions --for <who> --project
    builds` (the opening of `builds help`).
  - Work that origin/main lacks (commits, or files not committed) leaves a
    worktree only by landing, or with an item that holds it: one that keeps
    the worktree while it waits in the queue (`builds item stop` records the
    work when a run ends with work left), one running there, or one taken
    there held on the person (`builds item take --held`). `builds release`
    refuses every other worktree with such work, and `builds new` hands none
    out (`builds help`, WORKTREES AND CLAIMS). Only the person throws work
    away, by dropping its item (`builds item drop`, `builds help lists`).

Land the fixes you have ready together, in one batch (decision #1391 in
project bae), since each branch takes its own review, compile check and, for
app changes, app build. An agent with several fixes in hand, such as the items
of its brief, makes them all on one branch, one commit for each fix. A
difference you find in a component or board you are already changing gets its
own commit on the same branch (decision #604 in project builds), and so does
each cleanup of a series you find one after another as you work, with no
review, record or landing between them. The branch gets one review, run with
`--item N` for each item, and one `builds land` that names each item with
`--done N` and each design change with `--design N`. Each commit still holds
one concern. The agent compares the full set of boards, or runs the full test
suite of the code it changed, once after the batch's last commit, and before
then checks only what each change touches. The app build runs last (WHAT AN
IMPLEMENTING AGENT DOES, step 9). A fix waits for the batch only while the
agent still works on its other fixes or the next cleanup of its series, never
for work that nobody has started.


BUILDS

Every build follows these rules (`builds help`, CARGO, BUILD FOLDERS and APP
BUILDS):

  - Run every cargo command through `builds cargo`, which bae's and coven's
    scripts/cargo.sh runs, except the subcommands it refuses, such as fmt.
  - Never set CARGO_TARGET_DIR or another CARGO_* variable, on a command or
    in a script. Each checkout builds into its own folders on /Volumes/Builds,
    and sccache's key holds the path and every CARGO_* variable, so such a
    build gets no cache hits. A setting goes in a --config argument or in
    Cargo.toml.
  - An app build of a branch (`builds app-build <repo> <branch>`) runs only
    the test classes and the shots of the screens the change touches (--test
    <Class>, --shots mac.welcome.), and CI runs the full suites.
  - A full run (`--all-shots mac|android`) runs every shot of one lane with
    the installed shots program. It has two uses:
    - Board matching measures each lane with one, on a commit of origin/main,
      at each step of a round that measures, to list every scene that differs
      from its board. The coordinator runs these, never an implementing agent
      (the board-matching skill, Measurements).
    - An agent that changes the shots program runs one, so that `builds
      shots check-program` can check its change against the cached run.


PLAN, BRIEF, EXECUTE

  - Plan: the coordinator runs the strongest model. For work whose shape is
    still open, it writes a software plan in plans/<name>.md, and the plan's
    open questions go on the decision stack.
  - Brief: each queued item gets a brief that states the goal, the shape, the
    facts gathered so far (measurements, logs, leads), what must hold, and the
    checks.
    - A brief leaves the executor no design decision, and leaves the files and
      lines to the executor, who reads the code.
    - Before writing a brief or settling a choice an agent raises, the
      coordinator reads the spec's text on each behavior the change touches,
      and the brief cites it. `builds item take` checks the brief against
      the spec (DISPATCH).
    - Each sentence of a brief that states a ruling of the person's, or a
      prohibition meant to hold beyond the task, names where it is written
      (ROLES), and so does each hard limit that DISPATCH lists.
    - `builds help briefs` is the instructions for a planner agent that
      writes briefs.
  - Implementation: the brief specifies the behavior and how to test it. Name
    the implementation tier's model on each dispatch: claude-sonnet-5-5 in
    Claude, GPT-6.2 Sol (gpt-6.2-sol) in Codex. `builds health` lists an
    agent that runs another model than its item's tier, or names none.
  - Tier: name an item's tier when taking it. `builds item take --tier
    strongest` is for an item whose agent coordinates, plans or writes a
    spec or another document that takes judgment; `--tier implementation`
    (the default) is for the rest. `builds health` compares each agent's
    model to its item's tier.
  - Use the strongest tier for coordination, planning, review, and document
    edits and surveys that require judgment: claude-opus-5-5 in Claude,
    GPT-6.2 Astra (gpt-6.2-astra) in Codex. When a brief leaves a design
    decision open, the coordinator settles it or assigns a planner, whose
    brief says what the coordinator read and what stays unknown.
  - Review: each agent reviews its branch against the rules, the judge
    settles the findings, and the agent lands the branch once no confirmed
    finding is open (REVIEW, LANDING).
  - At every step, check the shape against the project's standing rules,
    which the project file names and which a plan's author never loads by
    touching files. A plan that proposes a shape they forbid is rewritten
    before dispatch, and a review refuses a commit that brings one in.
  - For work that builds an app screen to match its board, follow the rule
    the project file names for it.


WHAT AN IMPLEMENTING AGENT DOES

  1. Read the code paths its brief names, and the spec's text on each
     behavior it changes. A choice the brief didn't settle, or a brief that
     disagrees with the spec, goes back to the coordinator with both texts,
     never into a guess.
  2. Branch from origin/main in its claimed worktree.
  3. Implement to the brief. A bug fix starts with its failing test. The
     first time you edit a file in Claude Code, builds adds to your context
     each coding rule that covers it, and after each rule the findings that
     recent first reviews confirmed of it most often (`builds help`,
     ACKNOWLEDGING THE RULES). builds counts them in the project's records
     and, for the rules every project shares, in every project's. Write the
     draft so it has none of those findings. In Codex, and for paths you have
     not edited, `builds brief` prints the rules.
  4. Review its own diff once, against the brief and the matching rules.
  5. Check only what the change touches: the hook, the tests of the changed
     code and, for app changes, the app build, which runs last (step 9).
     Nobody runs a full test suite or the full CI script locally: CI runs
     them, and a whole app test suite also opens the app on the person's
     screen. `builds checks run --since origin/main` runs the hook's checks
     over every file the branch changed and leaves HEAD, the index and the
     files as they are. Never move HEAD to check a branch: an app build
     started meanwhile builds the commit HEAD names.
  6. Before every commit, including fix commits, reread every app string,
     error, help text, doc and spec line it adds against
     rules/text-people-read/write-plain-literal-active-sentences.md, and its
     code comments and commit messages for whether they are accurate. No
     review that an agent runs or that a landing waits on checks wording
     (REVIEW).
  7. Commit through the hook. When the commit edits a board for a change the
     person decided (ROLES), record the edit with `builds design record` and
     the decision's id as its `decision` (BOARD EDITS OF A DECIDED CHANGE),
     and amend the
     change with the same `decision` after any later commit that changes the
     board again.
  8. Once the work is committed, review the branch (REVIEW). A change that
     only moves or renames code, regenerates files or applies a codemod takes
     `--kind mechanical --checked-by TEXT` and then lands. Any other change
     takes `builds review <worktree> --kind code --item N` as a background
     task, then, when it reports findings, `builds review wait <landing>` as a
     background task. Fix each confirmed finding in a new commit and review
     again, until no confirmed finding is open. When a confirmed finding looks
     wrong, dispute it once (`builds review dispute`) instead of fixing it.
  9. Run the branch's app build last, so that no later commit makes it run
     again (decision #634 in project builds): after the full comparison of
     boards on a design branch, and after the fixes of the review's confirmed
     findings. The review may run while the agent compares the boards.
     - `builds app-build <repo> <branch>` picks the steps, lane and host
       (BUILDS).
     - A shots check compares against the findings of the commit the branch
       started from: read them with `builds shots findings`, never by building
       that commit, and open the report path it prints, never a checkout's
       shots/ folder.
     - An agent never draws a board or takes a shot itself, and runs no
       `builds shots run`, `capture` or `check`. To see a board or a shot at
       a commit, such as the branch's base, it runs `builds shots picture
       <repo> <ref> <scene> board|shot`, which prints the path of the picture
       from builds' store and makes it through an app build only when the
       store lacks it.
     - To fix a run's shot findings, start from `builds shots findings ...
       --by-cause`, which ranks the design-system components behind the
       findings by the scenes they break: fix the component at the top once,
       not each scene it breaks.
     - A component's shots go in its capture file, one shot for each row of
       its preview (`builds help`, APP BUILDS). Before you add or move them,
       run `builds shots components <Component>`, which lists each row with
       the file that declares its shot.
     - Each fix is a new commit, which the review reads (step 8) before the
       app build runs again.
 10. Land the branch with `builds land` in this worktree, with the brief's
     items (LANDING), once nothing is unreviewed, no confirmed finding is
     open and, for app changes, the app build has passed.
 11. Report the landed commits and the checks, or what stopped the landing.

Agents share their coordinator's scratchpad folder, so each keeps its scratch
files (commit messages, probes) in a folder of its own, named for its branch.


HANDOFF, AUDITS AND FLAKY TESTS

  - When an agent's context reaches about 550k tokens, it writes a handoff
    file at its next clean point (what's committed, what isn't, what's left,
    decisions, traps), and a fresh agent continues from it (`builds item
    handoff`).
  - Read-only agents (planners, audits) read origin/main through `git show`
    and `git grep`, never a checkout.
  - Flaky tests and speed work (profiling, benchmarks, timing a build) never
    go in the work queue, because they need a quiet machine: on a loaded one,
    load hides the cause and skews every number, and repeated runs slow every
    other agent. Open a GitHub issue for each one instead, with what you know
    so far, and take it off the queue. Whoever works the issue does it on a
    quiet machine, and finds a flaky test's cause from its failure output,
    code and logs that record the state at the failure. Run one test alone,
    by name, never the whole suite in a loop.


DISPATCH

  - Give each agent one task, or several to do one after another, one commit
    each.
  - Send the fixes of one area, or of one agent, as one batch (WORKTREES):
    take their items together (`builds item take N M ...`) with one brief.
  - Give work to the agent that already knows the area: a finding goes back
    to the agent that reported it, and an item goes to the agent that last
    finished work there. Send that agent a message to resume it. Start a new
    agent only when no finished agent under the handoff size knows the area,
    or the item needs a different model.
  - Each brief names its worktree, its items, and the project's hard limits
    (the person's checkouts, the keychain, devices, cargo through the
    wrapper, no `git add -A` or stash, no --no-verify), and "review and land
    through builds; don't push main". Send the worker the brief's path.
    - A brief carries no coding rules and no workflow text: builds gives a
      Claude Code agent each rule when it first edits a file the rule covers
      (`builds rules-on-edit`) and every agent the workflow when it runs
      `builds ack`, and `builds item take` refuses a brief that pastes
      either.
    - Each worker credits its own model in the commit trailer.
  - Critical work starts first: what the person sees in the apps (a screen, a
    bug, a feature the person asked for), builds work that blocks or slows
    the agents, and the cleanups the person marks critical.
    - The coordinator places each critical item first (`--priority first`).
    - A cleanup is critical only when the person says so: ask before placing
      one first.
    - The screen-reads cleanup is critical: the iOS, Windows and Linux apps
      wait on it, so that they don't copy the ways of reading data that it
      replaces with plain live queries.
    - Other cleanups (rewording, deleting dead code, merging duplicate types)
      start only when no critical item is ready.
  - Take items from `builds next`, from the top: items placed first, then the
    items that other open items wait on (most first), then the rest by area
    and age. Claim the worktree (`builds claim`), mark the items running
    (`builds item take`), and keep the worktree's note current (`builds
    note`) on every dispatch and handoff. When an agent stops before its work
    lands, stop its item (`builds item stop`), which keeps the worktree and
    branch for the item. Release a worktree by hand only when it holds
    nothing origin/main lacks. `builds item list --running` shows what runs
    after a compaction.
  - When `builds item take` refuses a brief's sentence that states a ruling of
    the person's, or a standing prohibition, and names no source, cite the
    decision, rule file, CLAUDE.md or builds help section, or take the
    sentence out of the brief and ask the person.
  - Before you start an agent, run `builds item check-brief --worktree W
    --brief P`: it runs the checks of `builds item take` (pasted text,
    rulings, spec) on the brief and takes nothing, so you fix a refused
    sentence before an agent starts and reads the brief.
  - `builds item take` checks the brief against the product spec. When it
    refuses for a conflict, put the conflict on the decision stack with which
    text looks wrong and why, or fix the brief when the brief is wrong. Once
    the person decides, take the items again with --spec-decided N, the
    decision or question that records the choice. When take prints a behavior
    the spec doesn't state, tell the agent to add it to the spec in its
    commit.
  - Brief a mechanical change (moved or renamed code, generated files, a
    codemod) as one change, and tell the agent to review it with `--kind
    mechanical --checked-by TEXT` (REVIEW).
  - Dead code, code that nothing outside tests calls, is never a question
    for the person: whoever finds it deletes it, or queues its deletion when
    it is outside their work. The one exception, dead code that is the only
    code doing a behavior the spec states, is in
    rules/necessary-code/write-only-what-is-needed-today.md (Dead code).
  - Disk is a queue limit, never a question for the person: under the floor,
    start nothing new, and start the next work as agents finish and their
    build folders are pruned.
  - Keep the 5-minute load of every build host in its band while ready items
    wait (`builds host band`; a host with none has 0.75 to 1.25 times its
    cores).
    - When `builds health` says a host is under its band, start agents on the
      next ready items.
    - While every host that takes cargo work is over its band, start nothing
      new, except items of project builds, which start whatever the load. A
      host over its band holds nothing back while another host that takes
      cargo work is under its band, since `builds cargo` sends the work there.
    - A host whose kernel reports memory pressure at warning or critical is
      over its band whatever its load. A host whose CPU is under 5% idle has
      no room, so start no agents for it. Health shows each host's memory and
      CPU idle share next to its load.
  - When an agent finishes, start the next work in the same turn, before
    writing up anything else. The agent landed its own commits; land them
    yourself only when the agent ended before it could.


REVIEW

In a repo of a project with lists, each implementing agent reviews its branch
against agent-instructions' rules with `builds review` before it lands the
branch, and the judge settles the findings, never the agent whose branch holds
them. The steps below are the agent's, and `builds help` (LANDING AND REVIEW)
says how builds finds the changes since the last review, what each reviewer
reads, and the review commands.

builds splits the rules into groups and runs one reviewer per group that covers
a changed path. A review reads only the committed changes since the last
review. It checks code and whether text is accurate, never word choice, grammar
or style: the person reviews copy by hand and runs the copy review (`builds
review copy`). It reads design files (the boards, the design system and
canvas.json) only under the rules about how a screen, board or component looks
(decision #364), and screenshot capture files only under the rules about shots
(decision #397).

Spend review usage only where a review can find something (decision #401):
reviews are for code people wrote. `builds review` takes a required `--kind
code|mechanical`. `--kind code` runs the reviewers. `--kind mechanical
--checked-by TEXT` starts no reviewer: the agent calls the change mechanical,
one that only moves or renames code, regenerates files or applies a codemod,
and names the check that covers it (the compiler, the hook, a shots run for
capture files, the states check for boards). `builds land` then records who
made the call and the check, and takes the branch whole with no review while
its net change keeps its patch id. Nobody splits a mechanical change into parts
to get under the review cap, and a branch that mixes a mechanical move with
code someone wrote is two branches. builds needs no --kind for a pure rename, a
design-only change or a change of capture files only.

  1. The agent commits its work and runs `builds review <worktree> --item N`,
     which gives the reviewers the item's brief. builds tells the judge of the
     findings nobody has settled, or, with no judge listening, the agent's
     coordinator.
  2. The agent runs `builds review wait <landing>` as a background task. No
     message reaches an agent that a session dispatched, so the wait's end
     tells it: the wait ends once no finding waits for a settle, and prints
     each settle with its reason.
  3. The judge settles each finding as confirmed or dropped, with why
     (JUDGING).
  4. The agent fixes each confirmed finding in a new commit and runs `builds
     review` again. Each reviewer gives a verdict on every open finding it
     holds: builds closes each finding the branch fixes, and prints why the
     reviewer kept each other one open. The judge settles new findings as
     for the first run.
  5. The agent lands the branch once nothing is unreviewed and no confirmed
     finding is open (LANDING).

An agent that thinks a confirmed finding is wrong disputes it once, with why
(`builds review dispute N --why TEXT`). The judge settles the finding again as
dropped, or keeps it (`builds review keep N --why TEXT`); a judge that gave a
wrong reason for a keep corrects it with `builds review keep N --again --why
TEXT`. builds tells the
coordinator nothing of a second disagreement: the agent reports it, and the
coordinator asks the person whether to allow the finding to land, or tells the
agent to fix it.

A group that raises an open confirmed finding again at the same place (the same
rule, clause and quoted code, at a line that edits above it moved, or under the
old name of a renamed file) keeps it as one open finding. builds tells the
judge nothing, and the run's report says the group still finds it.

In a later run, each group that holds open findings reads every file that
changed since the last review, because the fix of a finding may be in any file.
Each other group reads the changed files its rules cover, except a file where a
group holds an open finding: only the groups that hold findings there read that
file. The run's report names each group that did not read a file, with the
files it did not read.

The changes since the last review are the lines the branch adds or removes that
it did not add or remove at the last review, the lines it no longer changes,
and the commit messages it did not hold then. A reviewer judges only those
lines. Run `builds review` again whenever the branch changed since the last
review: a new commit, a fix, a squash that changed lines, a conflict's
resolution or a reworded message. Main's commits that a rebase brings in are
not part of the changes, so a rebase that keeps every line the branch adds and
removes keeps its review, and a rebase that resolves a conflict differently
leaves only the resolution's lines to read. A reworded message alone leaves
only the changed messages to read, and dropping the commit that held a
confirmed finding's code closes the finding at the next review.

A confirmed finding stays open until a later review closes it, the judge
settles it again as dropped after a dispute, or the person allows its code to
land as it is. Only the person allows a finding, and no agent passes
--by-person on its own judgment (JUDGING).


JUDGING

The judge judges each finding against the code and the rule, and settles it as
confirmed or dropped, with why (`builds review settle`). Each settle and its
--why score the reviews: a confirmed finding counts as a true positive and a
dropped one as a false positive (`builds review scores`). So the judge settles
each finding on what the code does, and its why says what makes the finding
real or wrong. A confirmed finding stays open until one of these happens:

  - A later review closes it.
  - The judge learns that the finding is wrong, from a dispute or otherwise,
    and settles it again as dropped (`builds review settle N --again --why
    TEXT`). The record keeps both settles.
  - The person allows its code to land as it is. Only the person allows a
    finding: the coordinator asks the person first, and once they say so,
    records their words (`builds review settle N allowed --by-person --why
    TEXT`). No agent passes --by-person on its own judgment. An allowed
    finding stays confirmed.

builds refuses to settle a closed or allowed finding again.


LANDING

The branch's agent runs `builds land` for its branch in the claimed side
worktree it worked in, once its work is done there, since land checks out other
commits in that worktree while it checks the result. The coordinator lands a
branch only when its agent ended before it could. Review each branch first
(REVIEW). `builds help` (LANDING AND REVIEW, builds land) says what land checks,
how landings that run at the same time push, and what land leaves in the
worktree.

  - After landing commits whose base is behind main and that touch shared
    code (schema, test stores, bridge types), build main (`check --workspace
    --all-targets --all-features`) before landing more, and send agents whose
    base changed under them back to rebase.
  - Don't run `builds land` in a worktree while its agent or a check still
    runs there.
  - When `builds land` prints `LANDED, NOT RECORDED:`, run the `rerun:`
    command it prints.
  - When a landing fails its checks or its cherry-pick, the branch's agent
    fixes the branch in a new commit, reviews the fix and lands again.
  - When land prints APP BUILDS DO NOT COVER the branch, it fetched and pushed
    nothing. The branch needs a passing app build of its own in each lane it
    changes, which covers every shots prefix that any app build of the branch
    ran since its merge base, including prefixes of runs that failed. Run
    `builds app-build` on the branch, or record why the branch drops a prefix
    with `builds app-build --drop-shots`, and land again. Land never builds
    the result, so a landing that reached main after the branch's build
    changes nothing: CI checks main as a whole.
  - A CI run on main that fails or stalls is the coordinator's to run down.
  - After each landing, `builds land` fast-forwards the repo's main checkout
    to origin/main. In agent-instructions, the checkout's post-merge hook then
    runs install.sh, which installs the landed builds and links the landed
    rules and skills (`builds help`, INSTALLING). When land prints MAIN
    CHECKOUT BEHIND, tell the person and give them the command it prints;
    never stash or reset their edits.


DESIGN TERMS

Agents use one word for each design thing (decision #309), in chat, items,
briefs, review pages and commit messages, and no other word for it:

  - board: a picture of one screen of an app, kept in the repo
    (design/mocks/<name>.dc.html). The app is built to match it.
  - shared board: a board that draws one piece several screens show, such as a
    row or a sheet. The canvas shows it on its Shared page.
  - scratch board: a board file that no commit holds,
    design/mocks/scratch.<name>.dc.html in a worktree, which each design
    repo's .gitignore leaves out. A design session draws versions of a board
    on it side by side to compare them with the person (decision #349).
  - canvas: the published page on claude.ai that shows every board. The
    repo's boards are its source (PUBLISHING DESIGNS).
  - design system: the tokens and the components, in design/system.
  - token: a named color, size or type style in the design system
    (design/system/tokens.json).
  - component: a reusable piece that boards are built from, such as a button.
  - preview: a picture of one component on its own, drawn in each of its
    configurations.
  - design change: one concern that the person reviews and approves, recorded
    with `builds design record` (DESIGN CHANGES).
  - review page: the page where the person reviews a design change. The page
    shows the boards that the recorder picks to show the proposed design, and
    lists the change's other boards by name (decision #369).
  - round: one redraw of the boards on a review page, after the person asks
    for a change.
  - approve: the person's approval of a design change, which lets it land.
  - land: put a design change's commits on main with `builds land`, as for
    any branch.
  - shot: a test's screenshot of the real app view, which a program compares
    with its board.
  - app work: the work that makes the app match a landed design change.

"Part", "mock", "mockup" and "card" never name a component. Say "component"
for a reusable piece and "shared board" for the board that draws one.


BOARD EDITS OF A DECIDED CHANGE

An implementing agent that edits an existing board for a change the person
decided (ROLES) records the edit as a design change with `decision`, the id of
that decision. builds approves the change as it records it, because the
decision is the person's approval, so the change needs no review page. The
agent names each place's app work in the same request (its own item, or how it
checked that the app already matches; `places`, `builds help lists`) and lands
the change with the item that built it (`builds land <worktree> --done N
--design M <sha>...`).

Nothing publishes the designs until the person asks (PUBLISHING DESIGNS).


DESIGN CHANGES

The design session lands its boards through a design change, which the person
reviews and approves first. `builds help lists` (DESIGN CHANGES) gives the
record's fields and commands. In a project that publishes a canvas (`builds
lists design-globs PROJECT --canvas yes|no`), such as bae, builds keeps its
boards in the repo only: recording, reviewing, approving and landing a design
change need no canvas link, artifact or claude.ai account (decision #702).
Landing a design change publishes nothing (PUBLISHING DESIGNS).

The design session records a fix that changes no design with `fix`, and the fix
needs no review page or approval. Such fixes are boards it redrew to follow
the design system's measures, a drawing mistake it corrected, a board it
deleted because the app can no longer reach the state the board draws, and a
board it redrew to draw what the app draws today, where the person decided
nothing about the difference. Each fix is a design change of its own, in a
commit of its own, and the ready fixes land as one batch (WORKTREES): `builds
land <worktree> --design N --design M <sha>...` takes every change with all its
commits and squashes nothing, so each fix keeps its commit.

  1. While drawing, look at a board with `builds design render`, which draws
     it from the worktree as one page of HTML and publishes nothing. To
     compare versions with the person before any commit, draw them side by
     side on a scratch board in your worktree, such as
     design/mocks/scratch.people-rows.dc.html, and give the person its scratch
     view on the dashboard,
     http://127.0.0.1:7787/design/PROJECT/scratch/WORKTREE/BOARD, which draws
     the worktree's files again after each save (`builds help`, STATUS,
     HEALTH AND THE DASHBOARD). Once the person picks a version, draw it on
     the real board, delete the scratch board, then commit, record and amend
     the change (decisions #341 and #349). Never commit a scratch board.
  2. When the boards are drawn, record the change with `builds design
     record`. Run record and amend as background tasks.
     - The title names the part of the app the change draws in a few plain
       words, such as "People rows" (decision #297).
     - The details name what changed in at most 40 words, with no sentence
       over 15 words, and the boards and circles show the rest.
     - The review page has one heading, so record one change per concern. It
       shows the fewest boards that show the proposed design, each in a
       situation that fits it (decision #369). Each board shows its proposal
       alone, and the board as it stands on origin/main beside it only with
       `show_now`, when the before helps the person judge the proposal. An
       entry can name a component in place of a board, to review a change to
       the component through its preview.
     - Circle one area per change (decision #299): one circle around the
       area that holds the change, never one on each element in it. When one
       heading goes and every row below it moves up, circle the area that
       holds the heading and the rows. A board whose proposal shows the
       change without a circle needs none.
     - The record names no app work: no item exists for a change before the
       person approves it (decision #304).
     - The rules review reads the change before the person does (decision
       #362): record and amend run `builds review` on the worktree's branch
       when the review has not read it. Wait with `builds review wait
       <landing>` as a background task, fix each confirmed finding in a new
       commit, and run `builds design amend`. The change reaches the Waiting
       on you tab once the review takes the branch's commits and no finding
       waits, and `builds design show N` says what the review lacks.
     - Record and amend refuse a change whose boards draw a new component
       state that no row of the component's preview shows, until the change
       adds that row to the preview, so that the component's own shot covers
       the state (decision #391).
     - To change the boards again, commit and run `builds design amend`,
       which keeps the approval only when every board and preview of the
       change draws the same as in the commit the person approved. A rebase
       onto a moved main needs no amend.
  3. Everything the person reviews goes on the review page. Never make a page
     of your own or open a browser tab; the person reloads the review page.
     To compare versions during a round, use a scratch board in the change's
     worktree as in step 1: the review page links to its scratch view.
  4. The person approves with the page's Approve button, which sends "Design
     change #N of project P approved: land it." to the session that recorded
     the change. Then name the app work of each place with `builds design
     amend N`, which keeps the approval: an open item, a new item, or how you
     checked that the app already matches. Then run `builds land <worktree>
     --design N <sha>...` in the worktree where the design session drew the
     boards, naming every commit of the change, oldest first. Land squashes
     the commits of a change of design files only into one commit with the
     change's title as its message (decision #292). The button recorded the
     approval, so never run `builds design approve` for it; `builds design
     approve N --by-person` is for an approval the person gives in words.
     When the session that recorded the change has ended, the next design
     session lands it. The rules review read the branch before the person
     reviewed it (step 2), so land needs no new review unless the branch
     changed since.


PUBLISHING DESIGNS

The designs reach claude.ai only when the person triggers a publish: with the
dashboard's Publish to claude.ai... button, or by asking a session to publish.
No landing, approval, item or session starts a publish on its own, and no
session queues or proposes a publish because something landed.

In a project that publishes a canvas, the repo's boards,
design/mocks/canvas.json and design/system are the source of every canvas that
design/mocks/canvases.toml names and of its Design System artifact. An edit
that anyone makes on those pages on claude.ai is an accident: publish the
repo's version over it and merge nothing from it. A session publishes with
the publish-designs skill, which sends every canvas and the design system from
one commit. A publish request
from the dashboard goes to the design session that listens for the project,
which takes it (`builds design publish take N`), publishes, and ends it with
`builds design publish done N` or `builds design publish failed N --why`
(`builds help lists`).


HEALTH CHECK

The coordinator runs `builds health` every 5 minutes while health has work to
watch. Health lists each open item, claimed worktree, agent process, app build,
review, landing and install that has not moved for 30 minutes
(BUILDS_STILL_MINUTES sets the threshold), with the time since it last moved,
and follows each recorded wait to the work at its end. Find out why each has
stopped moving, then start it, unblock it or ask whoever can act on it. When
the last line says "health schedule: can stop", delete the schedule, and create
it again when new work opens or a hold clears. A quiet check needs no message
to the person.

Health puts `new:` before each needs-action line that the same caller's last
`builds health` run did not print. It compares lines with their times, process
ids, loads, CPU shares and sizes removed. A caller with no earlier run gets
every line marked. The record of a caller's last run is a
file in builds' caches folder (`health-seen`), written by text runs only.

Before it lists anything, health makes each fix that needs no judgment call and
prints a line for each (`builds help`, STATUS, HEALTH AND THE DASHBOARD). It
prunes hosts under the free-disk floor, stops idle build daemons and simulators
on hosts under memory pressure, releases claims that nothing holds, releases a
claim whose worktree holds nothing origin/main lacks and has had no change and
no build for 2 hours (BUILDS_IDLE_CLAIM_HOURS) and stops an item marked running
there, ends reviews whose branch has nothing left to land, retires free side
worktrees, sends the judge again each finding that waits for a settle, forgets
a judge whose session ended, and stops each process whose caller is gone and
whose only work is what it prints. It never runs sudo, and stops other
processes only with `--stop-junk`. The lines below are what remains to act on.

  - sccache finished no compiles while clients wait: restart it (`launchctl
    kickstart -k gui/$(id -u)/local.sccache-server`).
  - A host whose sccache server has more than 2 clients waiting for each of
    its cores has more compile work than it can run: start nothing new for
    it. When its cache answers a low share of its Rust compiles, builds
    compile what the cache should hold (BUILDS says what changes sccache's
    key).
  - Junk shells: run `builds health --stop-junk`. When one agent keeps
    leaving polling shells, tell it to wait for notifications instead.
  - Commits that change design files with no design change: whoever made the
    commits records one (`builds design record`), the design session or, for
    a board edit of a change the person decided, the implementing agent.
  - A running item whose worktree is gone or unclaimed: land it, stop it
    (`builds item stop`) or hand it on.
  - A project whose findings wait for a settle while no judge listens, with
    how long the oldest has waited: start a judge session and run `builds
    judge listen --project P --by judge` from it.
  - A branch with commits origin/main lacks that no worktree checks out and
    no item names: check it out in a worktree (`builds new <repo> --resume
    <branch>`) and land it or take an item there, or ask the person whether
    to drop it.
  - An agent that runs another model than its item's tier takes (PLAN,
    BRIEF, EXECUTE), with its worktree, its items and both models: stop the
    agent at its next clean point and continue the item with an agent of
    that tier.
  - Disk under the floor: hold the queue.
  - A host under its band while items are ready: start agents on the next
    ready items (`builds next`).
  - Every host that takes cargo work over its band, under memory pressure, or
    with no room on its CPU: start nothing new until one host is back under
    the high end of its band, with normal memory pressure and its CPU 5% idle
    or more (DISPATCH).
  - A process whose caller is gone that health leaves to run, such as a
    landing whose shell ended, does its work to its end: check what it did
    once it ends. Stop one whose stop failed with the command the line gives.
  - A Mac that shows a system alert in front of every app
    (UserNotificationCenter, SecurityAgent or CoreServicesUIAgent) fails every
    Mac window shot there, because the alert keeps the focus. The line names
    the alert and its pid. Answer or close the alert on that Mac, or end its
    process with the command the line gives.
  - A Mac host whose screen is locked renders no Mac window shot, and the mac
    lane holds each window step for the host until it unlocks: unlock the
    screen on that Mac (`builds help`, APP BUILDS).
  - A host that holds an app build while Chrome cannot start there: a Mac
    whose window server does not answer starts no Chrome, so no shots run
    there can draw its boards. The line names the host, the held build's
    checkout and how long it has built nothing. The held build goes on once
    the window server answers (`builds help`, APP BUILDS).
