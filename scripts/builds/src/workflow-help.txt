builds workflow: how work moves through worktrees, builds and landing, and how
a coordinator runs agents. Read it before you make a worktree, build, land or
dispatch an agent. A command refuses a step that lacks what it needs, so this
page states only what no command checks. The project file
(projects/<project>.md in agent-instructions) names the project's lists,
worktrees and standing rules.


ROLES

A coordinator session plans work, dispatches background agents with a brief
each, reviews their work and lands it. The agents implement. A design session
draws the boards (pictures of screens, kept in the repo) that the apps are
built to match. "Design" alone is ambiguous: write "board" or "product design"
for screens and how they look, and "software plan" for the shape of code and
data.


WORKTREES

Each repo keeps a main checkout and one long-lived side worktree, side-1. The
branch, not the worktree, is the unit of work.

  - The main checkout stays on main, for iterative work and edits made with
    the person. `builds land` fast-forwards it to origin/main after each
    landing, so the person and the agents who read code there see what
    landed, but no agent edits, builds or commits there (LANDING).
  - side-1 is for background work: each feature or fix is a new branch from
    origin/main there. It stays built, so never delete or recreate it.
  - Extra side worktrees (side-2 and on) are for agents that work at the same
    time. `builds new` hands one out and claims it; `builds prune` retires
    idle ones whose work has all landed. An agent works in the worktree its
    brief names, or one it gets from `builds new --for`, never a side-N it
    picked by hand.
  - App checkouts keep the app builds built, and agents take turns in them
    through `builds app-build`; every other side worktree builds host Rust
    output only (`builds help`, APP BUILDS). Each repo's app builds have a
    lane per platform (mac, android), with its own app checkouts and queue.
    The builds tool adds app checkouts on a host while app builds wait in a
    lane's queue and removes them once no build uses them, so nobody adds one
    by hand when many app builds wait.
  - agent-instructions, which holds builds, works the same way: agents
    commit on a branch in a side worktree from `builds new
    ~/dev/agent-instructions --for <who> --project builds` (`--project bae`
    for bae's rules and project file), never in the main checkout. The main
    checkout is the live copy that install.sh links, so a commit on a side
    branch installs nothing (`builds help`).
  - Work that origin/main lacks (commits, or files not committed) leaves a
    worktree only by landing, or with an item that holds it: an item parked
    there (`builds item park`), which keeps the worktree and branch while it
    waits in the queue, or one taken there held on the person (`builds item
    take --held`). `builds release` refuses every other worktree with such
    work, on its HEAD, on a branch it left since its claim began or in its
    files, and names the three ways to keep it: land, park or take --held.
    `builds new` hands out no such worktree, and none where an item runs.
    Only the person throws work away, by dropping its item (`builds item
    drop`), which records the commits and files on the closed item, deletes
    the branch and frees the worktree. Drop refuses an item that shares its
    worktree with other items: stop it first (`builds item stop`), which
    leaves the work to them.
  - `builds health` lists each local branch with commits origin/main lacks
    that no worktree checks out and no open item names. Check it out in a
    worktree with `builds new <repo> --resume <branch>` and land it, or ask
    the person whether to drop it.

Each checkout builds into its own folders on /Volumes/Builds. Never set
CARGO_TARGET_DIR or another CARGO_* variable on a command: the path is part of
sccache's key (`builds help`, BUILD FOLDERS).


LISTS

A project's decision stack, work queue, decision log and design changes are in
the builds store (`builds help lists`). The stack holds what waits on the
person, asked one at a time from the top; a plan's open questions go there. The
queue holds only what agents can do, and `builds next` lists what is ready. The
log holds each answer, and each standing choice about how work runs, with why.
When you make an entry from another record, name that record with `--origin
N`, so the entry's trail shows where the entry came from. Put an audit's tag
only on the first entry of a trail: every later entry's trail has the tag.


PLAN, BRIEF, EXECUTE, REVIEW

  - Plan: the coordinator runs the strongest model. For work whose shape is
    still open, it writes a software plan in plans/<name>.md, and the plan's
    open questions go on the decision stack.
  - Brief: each queued item gets a brief that states the goal, the shape, the
    facts gathered so far (measurements, logs, leads), what must hold, and the
    checks. A brief leaves the executor no design decision, but doesn't name
    each file and line: the executor reads the code. Before writing a brief
    or settling a choice an agent raises, the coordinator reads the spec's
    text on each behavior the change touches, and the brief points at it.
    The spec is a draft that the coding rules outrank, and the person
    decides each change to what it says. `builds item take` checks the brief
    against the spec before the agent starts (DISPATCH). `builds help
    briefs` is the instructions for a planner agent that writes briefs.
  - Execute: an agent that carries out a brief or a plan the strongest model
    settled runs a faster, cheaper model. Name that model on every such
    dispatch: an agent dispatched without a model runs the strongest one.
  - Judgment work (a software plan, an edit of documents, a survey, a review)
    runs the strongest model. A software plan too large for the coordinator
    to hold goes to such an agent; its brief says what the coordinator read
    and what stays unknown, and it writes a plan for the faster model to
    execute.
  - Review: no diff is reviewed more than once. Each change gets one
    review; the coordinator reads the fixes for its confirmed findings.
    Before landing a branch, the coordinator runs the rules review on its
    commits once (`builds review <worktree> --item N`, which gives the
    reviewers the item's brief), judges each finding against the code and
    settles it as confirmed or dropped with why (`builds review settle`), and
    sends each confirmed one back to the agent that made it. The agent fixes
    it in a new commit. The coordinator reads that commit against its
    finding, names it (`builds review fixed`) and runs `builds review`
    again. A review shows the changes since the last review, and nothing
    else, the fixes included. The coordinator settles what
    that run finds, and runs `builds land` with the reviewed commits and
    their fixes in the branch's worktree once the agent is done there
    (LANDING). `builds land` refuses
    commits that lack this step (`builds help`, LANDING AND REVIEW). Each
    settle, with its
    `--why`, is the record that scores the reviews: a confirmed finding counts
    as a true positive and a dropped one as a false positive (`builds review
    scores`), and `builds review replay --landing` scores other models and
    prompts against it. So the coordinator settles each finding on what the
    code does, and its why says what makes the finding real or wrong.
    When it learns later that a confirmed finding with no fix is wrong, it
    settles the finding again as dropped (`builds review settle N --again
    --why TEXT`), and the record keeps both settles. When the agent
    drops the commit that held a confirmed finding's code, nobody fixes the
    finding: `builds review` and `builds land` find the code on no line of the
    branch's change past origin/main, record the finding as needing no fix,
    and stop waiting on a fix for it.
  - At every step, check the shape against the project's standing rules,
    which a plan's author never loads by touching files; the project file
    names them. A plan that proposes a shape they forbid is rewritten before
    dispatch, and a review refuses a commit that brings one in.
  - For work that builds an app screen to match its board, follow the rule
    the project file names for it.


WHAT AN IMPLEMENTING AGENT DOES

  1. Read the code paths its brief names, and the spec's text on each
     behavior it changes. A choice the brief didn't settle, or a brief that
     disagrees with the spec, goes back to the coordinator with both texts,
     never into a guess.
  2. Branch from origin/main in its claimed worktree.
  3. Implement to the brief. A bug fix starts with its failing test.
  4. Review its own diff once, against the brief and the matching rules.
  5. Check only what the change touches: the hook, `builds app-build <repo>
     <branch>` for app changes (builds picks the steps, lane and host), and
     the tests of the changed code. An app build runs only the test classes
     and the shots of the screens the change touches (--test <Class>,
     --shots mac.welcome.); CI runs the full suites, and builds refuses a
     whole lane's shots (mac. or android.) and the steps a `ci-only` line of
     `.app-build` names. Never run a whole app test suite (it opens the app
     on the person's screen) or the full CI script. A shots check compares
     against the findings of the commit the branch started from: read them
     with `builds shots findings`, never by building that commit, and open
     the report path it prints, never a checkout's shots/ folder.
  6. Before every commit, fix commits included, reread every comment, doc,
     spec line and commit message it adds against
     rules/text-people-read/write-plain-literal-active-sentences.md, and
     fix what it finds. The coordinator reads a fix commit for a review
     finding against its finding, and the next run of the review reads it as
     part of the changes since the last review.
  7. Commit, and report the SHA, the base and the checks. Leave nothing
     uncommitted: the coordinator runs `builds land` in this worktree, which
     refuses a worktree with uncommitted changes.

Agents share their coordinator's scratchpad folder, so each keeps its scratch
files (commit messages, probes) in a folder of its own, named for its branch.


DISPATCH

  - Give each agent one task, or several to do one after another, one commit
    each. When its context reaches about 550k tokens, it writes a handoff
    file at its next clean point (what's committed, what isn't, what's left,
    decisions, traps), and a fresh agent continues from it (`builds item
    handoff`).
  - Give work to the agent that already knows the area: a finding goes back
    to the agent that reported it, and an item goes to the agent that last
    finished work there, resumed with SendMessage. Start a new agent only
    when no finished agent under the handoff size knows the area, or the item
    needs the other model.
  - Each brief names its worktree, its items, the rules to read, the
    project's hard limits (the person's checkouts, the keychain, devices,
    cargo through the wrapper, no `git add -A` or stash, no --no-verify), the
    mode, the model's commit trailer, and "report each commit; don't push
    main". A quick-mode brief names the one test that proves the change and
    the clippy command with the hook's feature sets, never "the tests of what
    you touched".
  - Critical work starts first. Critical work is what the person sees in the
    apps (a screen, a bug, a feature the person asked for), builds work that
    blocks or slows the agents, and the cleanups the person marks critical.
    The coordinator places each critical item first (`--priority first`). A
    cleanup is critical only when the person says so: ask before placing one
    first. The screen-reads cleanup is critical, because the iOS, Windows and
    Linux apps wait on it, so that they don't copy the ways of reading data
    that the cleanup replaces with plain live queries.
    Other cleanups (rewording, deleting dead code, merging duplicate types)
    start only when no critical item is ready.
  - Take items from `builds next`. Claim the worktree (`builds claim`), mark
    the items running (`builds item take`), keep the worktree's note current
    (`builds note`) on every dispatch and handoff. A landing that leaves
    nothing to land releases the worktree. When an agent stops before its
    work lands, park its item where the work is (`builds item park`); release
    a worktree by hand only when it holds nothing origin/main lacks (release
    refuses the rest). `builds item list --running` shows what runs after a
    compact.
  - `builds item take` checks the brief against the product spec before it
    marks the items running. When the check finds a conflict, take refuses
    and quotes the brief's sentence and the spec's text: put the conflict on
    the decision stack with which text looks wrong and why, or fix the brief
    when the brief is wrong. Once the person decides, take the items again
    with --spec-decided N, the decision or question that records the choice.
    When take prints a behavior the spec doesn't state, tell the agent to add
    it to the spec in its commit.
  - Read-only agents (planners, audits) read origin/main through `git show`
    and `git grep`, never a checkout.
  - Disk is a queue limit, never a question for the person: under the floor,
    start nothing new, and start the next work as agents finish and their
    build folders are pruned.
  - Flaky tests and speed work (profiling, benchmarks, timing a build) never
    go in the work queue. They need a quiet machine: on a loaded one, load
    hides the cause and skews every number, and repeated runs slow every other
    agent. Open a GitHub issue for each one instead, with what you know so
    far, and take it off the queue. Whoever works the issue does it on a quiet machine,
    and finds a flaky test's cause from its failure output and code. Logs
    that record the state at the failure, such as which process holds a lock,
    show the cause; one test runs alone, filtered by name, never the whole
    suite in a loop.
  - Another worktree may keep an app build while a wave of work needs it;
    clear it once that work moves on (`builds help`, APP BUILDS).
  - When an agent finishes, land its commits and start the next work in the
    same turn, before writing up anything else.


MODES

The person picks the mode and tells the coordinator; each brief names it, and a
switch means telling every running agent. The pre-commit hook is the same in
both.

  - Strict: agents commit through the hook and run the tests of what they
    touched. While `builds health` shows load well over the core count, start
    nothing new.
  - Quick: keep 8 agents running, starting new ones at every health check
    and landing. Before each commit an agent runs clippy with the project's test
    features (and the apps' test-target compiles for Swift or Kotlin), and
    runs only the one test that proves a fix. The landing's compile check
    still checks every landing. At the full-suite run the person sets, a fixer
    agent runs every suite and CI and fixes each failure with the commit that
    caused it. A test that fails meanwhile is checked on origin/main first;
    when it fails there too and isn't the agent's, the agent notes it and
    moves on.


LANDING

Run `builds land` for each branch in its own worktree, the claimed side
worktree its agent worked in, once the agent is done there: land checks out
other commits in that worktree while it builds and checks the result. The land
help says what it checks. Review each branch first (PLAN, BRIEF, EXECUTE,
REVIEW): land refuses the commits unless a finished review read the branch's
net change as it is now.

  - Landings in different worktrees may run at the same time. When origin/main
    moves while a landing runs, origin refuses that landing's push, and the
    landing fetches again and pushes again. Two landings in one worktree run
    one after the other.
  - A landing that leaves nothing to land on the branch leaves the worktree
    detached at the landed commit and releases it. A landing that leaves
    commits on the branch checks the branch out again and keeps the claim, and
    a landing that names a --part keeps the claim too.
  - After landing commits whose base is behind main and that touch shared
    code (schema, test stores, bridge types), build main (`check --workspace
    --all-targets --all-features`) before landing more, and send agents whose
    base changed under them back to rebase.
  - Don't run `builds land` in a worktree while its agent or a check still runs
    there.
  - When `builds land` prints `LANDED, NOT RECORDED:`, run the `rerun:`
    command it prints.
  - No diff is reviewed more than once. Each change gets one review; the
    coordinator reads the fixes for its confirmed findings. Land the branch
    with its named fixes once the review's runs have read its net change as
    it is now. A rebase that keeps every line the branch adds and removes
    keeps its review, even when the lines around them changed. When the
    branch changed since the last review (a commit added after the review, a
    fix, a squash that changed lines, or a conflict's resolution), run
    `builds review` in the branch's worktree again: a review shows the
    changes since the last review, and nothing else, never main's own
    commits that a rebase brings in. Settle the new run's
    findings and name their fixes as for the first run.
  - A CI run on main that fails or stalls is the coordinator's to run down.
  - After each landing, `builds land` fast-forwards the repo's main checkout
    to origin/main, so the person and the agents who read code there see
    what landed. Agents still never edit, build or commit in a main checkout.
    In agent-instructions, the main checkout's post-merge hook then runs
    install.sh, which installs the landed builds and links the landed rules
    and skills. When the landed builds changes a store's schema, install
    waits for every running hook run, review and app build lane, and every
    hook run and review that starts meanwhile waits for install, so commits
    in every project wait until it ends (`builds help`, INSTALLING). An
    install that changes no store's schema waits for none. When land prints MAIN CHECKOUT BEHIND
    (the checkout is not on main, or the person's commits or uncommitted
    edits there stop the fast-forward), tell the person and give them the
    command it prints; never stash or reset their edits.


DESIGN CHANGES

The design session lands its boards through a design change, which the person
reviews and approves first (`builds help lists` has the record and its
commands). Only bae publishes its boards as a claude.ai canvas: its design
changes give each board's canvas link, and landing one ends with publishing
the canvas. builds keeps its boards in the repo and publishes nothing, so its
design changes take no canvas links and landing one has no publish step. A
project's setting says which it does (`builds lists design-globs PROJECT
--canvas yes|no`). A fix that changes no design (boards made to follow the design
system's measures, a drawing mistake corrected) is recorded with `fix` instead:
it needs no review page or approval, and lands with `--design N` like any
other.

  1. While drawing, look at a board with `builds design render`, which draws
     it from the worktree as one page of HTML without publishing the canvas.
  2. When the boards are drawn, record the change (`builds design record`):
     what changed, each board's canvas link (in a project that publishes a
     canvas), and the review page's headings, words and boards. The change
     shows in the dashboard's Waiting on you tab as a card, and its Details
     opens the review page, which shows each board now and proposed side by
     side and draws it again on each load. To change the boards again, commit
     and run `builds design amend`, which clears an approval unless every
     board comes out byte-identical. A rebase onto a moved main needs no
     amend: health and land compare the boards' files, not commit hashes.
  3. Everything the person reviews goes on that page: new boards, proposals,
     before and after examples. Never make a page of your own (a review.html,
     a page in the scratchpad) or open a browser tab; the person reloads the
     review page.
  4. The person approves with the page's Approve button, which sends "Design
     change #N of project P approved: land it." to the session that recorded
     the change. That message is the cue to land: run `builds land <worktree>
     --design N <sha>...` with the worktree where the design session drew the
     boards (the Approve button recorded the approval; never run `builds design
     approve` for it), then, in a project that publishes a canvas, publish
     the canvas, which only a Claude session can do. When that session has
     ended, the next design session runs `builds
     land` for the change. `builds design approve N --by-person` is for an
     approval the person gives in words. When a review fix for one change's
     commit is in another change's commit, builds land cannot land either
     change alone: land them in one call, with `--design N` once for each
     change.
     When a rule group covers a path the commits change, `builds land`
     refuses them until the rules review is finished, as for any branch
     (PLAN, BRIEF, EXECUTE, REVIEW): run `builds review` on them, settle
     each finding, fix each confirmed one in a new commit, read that commit
     against its finding, name it with `builds review fixed`, and run
     `builds review` again, which reads the fixes.

In a project that publishes a canvas, the boards and design/mocks/canvas.json
in the repo are the canvas's source. The published canvas and design system
are copies that let anyone look at the landed boards. An edit made on the canvas page on claude.ai is an accident:
publish the repo's version over it and merge nothing from it.


HEALTH CHECK

While the coordinator's agents run or commits wait to land, a schedule in its
session (CronCreate) runs `builds health` every 5 minutes, and the coordinator
acts on every line of its "needs action" list first. Delete the schedule
(CronDelete) when nothing is left to check. A quiet check needs no message to
the person.

  - sccache finished no compiles while clients wait: restart it (`launchctl
    kickstart -k gui/$(id -u)/local.sccache-server`).
  - Junk shells: run `builds health --stop-junk`. When one agent keeps
    leaving polling shells, tell it to wait for notifications instead.
  - A claimed worktree with no change and no build for an hour: ask its agent
    what it waits on, or land and release it. A claim kept on purpose gets
    `builds note <worktree> --state held "<why, and until when>"`.
  - A held worktree whose wait closed: restart its work and clear the hold.
  - Commits that change design files with no design change: the design
    session records one (`builds design record`).
  - A running item whose worktree is gone or unclaimed: land it, stop it
    (`builds item stop`) or hand it on.
  - A branch with commits origin/main lacks that no worktree checks out and
    no item names: check it out in a worktree (`builds new <repo> --resume
    <branch>`) and land or park it, or ask the person whether to drop it.
  - Disk under the floor: hold the queue.
  - An app lock held long, or with agents waiting: check that the holder is
    building, not stuck. A step past its time limit is killed and passes the
    lock on.
