builds: runs this Mac's build volume (/Volumes/Builds), the repos' side
worktrees and their builds, the app build lanes, the pre-commit hook's checks,
the review of each branch against the rules, and landing. Agents run every
cargo command, app build and landing through it.

A section's heading after the page prints that section alone: `builds help

builds is a Rust program in agent-instructions (scripts/builds).
agent-instructions' install.sh builds it from the main checkout's committed
HEAD, never from the working tree, with the libraries it is built with: the
shots checker, which `builds shots` runs (scripts/shots), and the boards
library (scripts/boards). install.sh then runs `builds install`, which puts
builds on PATH as ~/.local/bin/builds. Agents change
agent-instructions the way they change bae and coven: on a branch in a side
worktree from `builds new ~/dev/agent-instructions --for <who> --project
builds` (or `--project bae` for bae's rules and project file), reviewed and
landed (`builds help workflow`).
The main checkout is the person's, and it is the live copy: install.sh links
its files into ~/.claude and ~/.codex. Its post-commit and post-merge hooks run
install.sh again when a commit or merge on its main branch changes what
install.sh consumes, scripts/builds/ included. A commit on a side worktree's
branch installs nothing; it goes live once it is on main and the main
checkout's main moves to it, which `builds land` does after each landing, as
it does in every repo (LANDING AND REVIEW). To try an edit to builds before
`builds land` puts it on main, run the binary your worktree built
(scripts/builds/target/debug/builds).


OUTPUT

Agents read what builds prints into their context. Everything builds prints is
one of three things:

  - A message about the work: a `builds:` note, a warning, progress, or a
    result for one file or checkout. A kind of message is the messages that
    one place in builds' code prints. A command prints 30 lines of each kind,
    counting each line of a message that has several. As it ends, it prints
    one line for each kind that had more: `builds: left out N more lines of
    one kind, the last of them: <line>`.
  - Output the caller asked for: help, rules, the text of `builds ack`, what
    the show, list and status commands report, the report of `builds health`,
    findings, JSON and paths. builds prints it whole. To see less of a list,
    narrow it with the command's filters. A landing prints whole the refusal
    that ends it.
  - What another program prints, such as cargo, a test, a check or git, and
    the lines a host's builds printed, which that builds capped there. builds
    passes it on as it is.

The dashboard serves until something stops it, so it writes every line of its
log.


ACKNOWLEDGING THE RULES

An agent runs `builds ack` to acknowledge the workflow and lists overview at
session start and after compaction. These sections apply to every project.
When either section changes, each builds command an agent runs prints one
line that says so and gives `builds ack`, and runs as usual; builds counts
the change as read only after `builds ack` shows the changed sections and the
agent acknowledges them, so a command whose output nobody reads leaves the
change unread. The hook that checks `builds ack` refuses a pipe, a redirect
and a script around it. Builds gives the
agent each coding rule that covers a file when the agent first edits it
(`builds rules-on-edit`); `builds brief` prints the rules for paths the agent
has not edited. The reading holds the sections that every agent uses. A
coordinator, a design session and a judge add `--role coordinator`, `--role
design` or `--role judge`, which adds the sections of that role (`builds help
workflow` prints them all); an agent that takes up another role runs `builds
ack` again with that role and reads only its sections. builds takes the roles
an agent holds from the sections it acknowledged, so the gate asks no agent
for a role's sections. After a compaction, the agent names its roles again.

Builds requires acknowledgement for agent commands other than `help`, `ack`,
`agent start`, `brief`, `rules-on-edit`, `install`, `dashboard` and `version`.

Every command takes --project P. The check of an agent's acknowledgement reads
it from the store of the project the agent works in: the one the claim of the
worktree the command runs in names, else --project's. In a repo two projects
hold, an agent's command from a checkout whose claim names neither therefore
needs --project, whatever the command does. A command that makes no other use
of a project, such as `queue`, `takeover`, `build-app` or `retire`, only
checks that the project exists. For `lock`, --project goes before the command
it runs, and for `remote run`, before `--`. Every word after `cargo` and
`lake` belongs to the tool.

  {ack #1}
      Start a reading. Its first line says why builds asks agents to read the
      text: agents that skip it work in the person's checkout, push main and
      poll for builds. For an agent that Claude Code compacted since its last
      acknowledgement, the next line says the text is no longer in its
      context. Then it says the version and how many parts the reading comes
      in, and give the command for part 1, which holds
      a token that only this output shows. The reading holds only the
      sections whose current text the agent has not acknowledged in this
      session, in any project, and names the ones it leaves out. After the
      text changed, the reading holds the changed sections. When the
      agent has acknowledged every section, builds records the
      acknowledgement, names the sections that left the text, and the reading
      holds nothing. builds keeps the
      sections of the version each agent acknowledged, to name the sections
      that changed since that acknowledgement and to tell which roles the
      agent holds.
  {ack #2}
      Print part PART of the reading, with no word added to the text. The
      part's first line says which part it is, and its last line gives the command for the next part, with a token that
      only this part's output shows, and the last part's last line gives the
      acknowledging command with its token. Fetching part N needs the token
      of part N - 1 (part 1 needs the one in the output of `builds ack`), so
      the agent fetches every part in order. Reading a part again shows it
      again with the same token.
  {ack #3}
      Acknowledge version VERSION, giving the token from the last part's last
      line. builds refuses a wrong token and says which part gives it.
  {ack #4}
      Claude Code's SessionStart hook runs this after Claude Code compacts
      an agent (claude/settings.json in agent-instructions). builds deletes
      every acknowledgement and the reading of that agent in every project's
      store, records that Claude Code compacted the agent, and tells the
      agent its id again, so the agent reads the text
      again before its next builds command and every other agent keeps its
      acknowledgements. builds refuses an agent no hook registered, and
      deletes nothing.
  {ack #5}
      The Codex PostCompact hook runs this command and gives it the compacted
      thread. builds clears that thread's acknowledgements. Trust the hook
      definition in Codex so it can run after compaction.
  {agent start}
      Claude Code's SessionStart hook (when a session starts, resumes,
      clears or forks) and its SubagentStart hook run this. builds reads the
      hook's input, registers the agent's id in the session, and adds "Your
      builds agent id is ID. Pass --agent ID to every builds command ..." to
      the agent's context.
  {rules-on-edit}
      Claude Code's PreToolUse hook for Edit, Write, MultiEdit and
      NotebookEdit runs this. builds reads the hook's input and finds the
      file's repo and its project (`builds claim --project`, else the project
      that holds the repo). builds adds to the agent's context each coding
      rule of that project (and the shared rules) that covers the file, with
      the rule's text and, after it, the findings that recent first reviews
      confirmed of that rule most often (two or more, with the paragraphs they
      quote most), unless it gave the agent that rule before. It records
      each rule it gives, under the agent's own id, in the agent's folder
      (`agents/<session>/<agent>.rules`), and forgets them when Claude Code
      compacts the agent. It prints nothing for a file outside every repo.

builds identifies Codex commands by CODEX_SESSION_ID and CODEX_THREAD_ID.
The session id identifies the coordinator. The thread id identifies the agent
running the command. Codex agents run builds without --agent. If an agent
passes that option, its value must match the thread id.

Claude Code supplies CLAUDE_CODE_SESSION_ID. Its hooks register each agent in
<the lists folder's parent>/agents/<session>/<id>. Claude Code agents pass
--agent ID before a `--`, or set BUILDS_AGENT=ID when running a script that
calls builds. The main agent's id is its session id. A dispatched agent uses
the id its hook gives it.

The person's terminal has neither runtime identity, so builds accepts its
commands without acknowledgement. The acknowledgement gate also passes
pre-commit checks in the main checkout and `builds status --json --no-folders`.


AGENTS

`builds agent run` starts an agent on items. builds writes the agent's
opening prompt, starts Claude Code with the flags of the agent's role, records
the session and reads the agent's context. Every `builds agent` command but
`agent start` (ACKNOWLEDGING THE RULES) needs acknowledgement. The coordinator
runs each of them as a background task, and the task ends when the agent's
process ends.

  {agent run}
      Starts a new agent, prints one line (its session id, role, project,
      model, folder and log), and runs until the agent's process ends. Then it
      prints the agent's last result whole and the exit status, and exits
      with the status when it is not 0.
      - implementing: every N is an item that `builds item take` started, all
        in the same worktrees, with the same brief and the same tier. The
        agent runs in the first worktree, with the model of the items' tier.
        builds reads the worktrees, branches and brief from the items' run,
        so the command takes no --brief.
      - planner: every N is an open item that no agent runs, and --brief names
        the brief of the plan. The planner runs the strongest model in the
        worktrees folder of the repo whose main checkout holds the brief.
      builds writes the prompt from these parts, in this order, and no
      template: the project's description (the first paragraph of
      projects/<project>.md in the rules checkout), the role's line, the
      worktree, branch and land command of an implementing agent, each item
      as `builds item show` prints it, the brief whole, the words of
      --message-file, the project's `## Hard limits` section whole, the
      commit trailer of the model, and the agent's scratch folder. builds
      refuses to start an agent when the project file or its Hard limits
      section is missing, and names the file.
      The agent starts with no MCP server, no skill and these tools: Bash,
      Edit, LSP, Monitor, Read, TaskStop, ToolSearch and Write, in an
      environment that holds no caller's identity and no inbox, so the agent
      is a new Claude Code session. The prompt goes to the agent on standard
      input. When the agent's first stream line shows another model, tool, MCP
      server or skill than builds asked for, builds stops the agent and
      fails.
      builds keeps the stream of each agent and Claude Code's standard error
      in <build volume>/agents/<session>/log.jsonl, and gives the agent
      <build volume>/agents/<session>/scratch for its scratch files. It reads
      the context of each turn of the agent (the input, cache-creation and
      cache-read tokens together) from the stream, and records them in the
      store with the agent's session, role, model, items and processes
      (agent, agent_item with the time the agent was given each item, and
      agent_process). builds never stores whether an
      agent runs: it asks Claude Code's record of its running sessions.
  {agent resume}
      Gives the recorded agent SESSION a message: the words of --message-file,
      then, for each --item, the worktree and land command, the item as
      `builds item show` prints it and the commit trailer again. It needs at
      least one of --item and --message-file. Each --item of an implementing
      agent runs, in any worktree and on any branch (the coordinator takes it
      first, in whichever worktree builds hands out). A planner takes an open
      item that no agent runs. builds adds each --item to the agent's record.
      - builds refuses an --item while another agent that runs now has it:
        that agent's record names the item and a worktree the item runs in,
        and Claude Code's record of running sessions names its session.
      - builds refuses to resume an agent whose last turn had 550k tokens of
        context or more, the handoff size, with a message or an item, whether
        or not its session runs: a fresh agent continues its work (`builds
        help workflow`, HANDOFF, AUDITS AND FLAKY TESTS). It takes every
        other recorded agent, whether or not the agent's items are closed.
      - The worktrees and branches that an implementing agent's --item items
        run in replace the recorded ones. Each land command names these items
        and the agent's earlier items that still run there. builds refuses the
        resume unless all those items run in the same worktrees.
      - When Claude Code's record of running sessions names SESSION, builds
        sends the message to the session's inbox and exits at once.
      - Otherwise, or when nothing listens at the inbox, builds runs `claude
        -p --resume SESSION` with the flags of the agent's role and the
        recorded model, appends to the agent's log, records a new process,
        and runs until it ends, as `agent run` does.
        An implementing agent's process starts in the first of the worktrees
        in its record, which builds records as the agent's folder, and a
        planner's starts in the folder of its record. Claude Code finds the
        session by its id from any folder. A message to a running session's
        inbox changes no folder.
  {agent list}
      Prints one line for each agent the project recorded, oldest first: the
      session, role, model, items, folder, whether it runs now or when it
      ended, and the context of its last turn against its model's window,
      such as `292k of 1000k`. An agent at 550k or more is marked past the
      handoff size (`builds help workflow`, HANDOFF, AUDITS AND FLAKY TESTS),
      so the coordinator sees which finished agents can take more work.
      --running lists only the agents that run now.
  {agent show}
      Prints the agent's record: its fields, the log's path, each process of
      the session (pid, start, end and exit status, and the hash of the
      message builds sent it) and the last result text of its log.


BUILD VOLUME

Every build on this Mac writes to the build volume, and builds owns everything
on it:

  <repo>/<checkout>/    one build root per checkout, named for its worktree
                        (main, side-N or an app checkout's name)
  <repo>/app-<app>-checkouts
                        the app's app checkouts, one per line: the name
                        alone for one a person added, and the name, `builds`,
                        the time and why for one builds added. Each app that
                        the repo's .app-build names (an `app` line, or a
                        platform's word) has its own files, so `mac` has
                        app-mac-checkouts
  <repo>/app-<app>-checkouts-removed
                        the checkouts builds removed from the lane in the
                        last 12 hours, one per line: the time, the name and
                        why
  <repo>/app-<app>.locks/
                        one lock per app checkout (app-<app>.locks/<entry>),
                        held by the build that runs there, and beside each
                        lock the record that build keeps (<entry>.run): when
                        it joined the queue, how long it waited, and the step
                        it runs; and when the last build there let the lock
                        go (<entry>.ended)
  <repo>/app-<app>.queue/
                        the builds waiting for the lane's locks: `order` holds
                        one ticket per line, next first, the holders' tickets
                        among them, and each process in line holds a ticket
                        file named <pid>-<n>-here|anywhere, for where
                        its build may run. After a ticket passes the queue,
                        a build that waits for a lock lists the checkouts it
                        tried in .<ticket>.checkouts, one per line. Health
                        reads that file.
  .app-hosts/<host>     a lock builds holds while it counts the host's app
                        checkouts and adds one there, so builds of two lanes
                        never pass the cap of checkouts on a host together
  DerivedData/          Xcode's default DerivedData location
  caches/<name>/        the download caches every checkout shares
  shots/<repo>/runs/    the output of each shots run (APP BUILDS), one folder
                        per run under
                        <commit>/<lane>/<prefix>/<capture>/<comparison>/
  shots/<repo>/pictures/
                        the board pictures shots runs drew, by board hash,
                        and the shots the apps took, by app source tree (APP
                        BUILDS)
  review-texts/<project>/<run>/
                        the texts of each review run (DISK), one file per
                        text, named for the text's hash
  web-pictures/<picture>/
                        one web page's picture, page.png (WEB PICTURES)
  agents/<session>/     what `builds agent run` keeps of each agent it
                        started: log.jsonl, the stream and Claude Code's
                        standard error as JSON lines, and scratch/, the
                        agent's folder for scratch files, a handoff file
                        among them (AGENTS). Setup and prune delete the
                        folder of a recorded agent only when all of these
                        hold:
                        - the agent is past the handoff size, so `agent
                          resume` refuses it
                        - Claude Code does not list its session as running
                        - each item of its record is closed or taken over.
                          An item is taken over once an agent of the same
                          role, given the item after this agent was, has
                          since ended a process with exit status 0
  .chrome-slots/        the slot files that limit the pages Chromes draw at once
                        on the host (APP BUILDS); `builds status` leaves it out
  .detached/            one record for each process builds detached, which
                        runs on after the builds command that started it
                        ends: the dashboard and the builds and prunes it
                        runs, the prune after `builds cargo`, a review's
                        audit, each background removal, the app checkout lock
                        guard and the git that switches an app checkout.
                        builds starts each one in a session of its own and,
                        before the process runs its program, writes its pid,
                        start time, purpose and the builds command that
                        started it to <pid>-<start time>.json. When builds
                        cannot write the record, the program never runs and
                        the step fails.
                        `builds health` and the dashboard remove a record
                        whose process has ended when they read a host's
                        processes. `builds status` leaves the folder out
  .trash/               folders being deleted in the background
  .trash.lock           taken shared by each deletion into .trash, and
                        exclusive only by the floor and prune, to rename
                        .trash to .trash-emptying.<random>/ and empty it

`builds status` lists each of these and flags anything else on the volume as
UNKNOWN (it leaves out macOS's own volume metadata, such as .Spotlight-V100 and
.fseventsd). Something UNKNOWN is either a new kind of build output that builds
should own or a leftover to delete: find out which.


BUILD FOLDERS

Each checkout has one build root, /Volumes/Builds/<repo>/<checkout>/. The repo
lists its build output folders in `.build-dirs` at its root (cargo's target,
Xcode and SwiftPM .build folders, Gradle's build and .gradle, dotnet's obj and
bin, Lean's .lake), and each listed path is a symlink in the checkout to the
same path under the checkout's build root (target ->
/Volumes/Builds/bae/main/target). `.build-dirs` has one line per folder, a
`keep` line for each build that must stay, an `installed` line for each
tool the repo's scripts install into the user's cache home, a `prepare` line
for each program that puts in place what the checkout's builds need, a
`tool` line for each tool the repo builds from its own sources (BUILT TOOLS),
a `linux-package` line for the Debian packages a Linux host needs to build the
repo, and a `macos` line for the repo's packages that only a Mac builds:

  <path> <cap>              the folder and its size cap
  <path> <cap> app <cap>    a second cap, for the folder in the repo's app
                            checkouts
  ... lane <app>      after the caps: only that lane's app checkout
                            builds into the folder, keeps it built and takes
                            its app cap; in the other lane's app checkout it
                            is an ordinary side worktree's folder. A folder
                            with no lane (host target) is every app
                            checkout's
  keep <path>               a build inside a folder that never ages out in
                            main and the app checkouts, where the person runs
                            the app built there (bae:
                            bae-macos/bae/.build/runApp)
  installed <folder> <file> a tool a script installs once per version into
                            <folder> in ${XDG_CACHE_HOME:-~/.cache}, one entry
                            per version, named after it; <file> in the
                            checkout names the version it runs (bae:
                            owner-construction-check
                            scripts/owner-construction-check.sh)
  prepare <program>         a program of the checkout that `builds setup`
                            runs in its top folder, and `builds cargo` before
                            cargo on whichever host runs cargo. The program
                            puts in place what the checkout's builds need
                            beyond their folders, such as a toolchain
                            component or a source that builds compile against
                            (coven: tools/typed-lints/prepare-build.sh). It
                            finishes at once when all of it is in place, runs
                            again each time, so it notices a moved toolchain
                            pin, never runs `builds cargo`, which would run it
                            again, and never asks for a password, since nobody
                            is at a host's screen. When it fails, setup and
                            `builds cargo` fail, naming it. A `builds cargo`
                            that a pre-commit hook check runs (COMMIT CHECKS)
                            runs no prepare program, since a hook installs and
                            fetches nothing: when a piece is missing, the
                            check's build fails and the check names `builds
                            setup` (coven: tools/typed-lints/cargo.sh names
                            the missing path)
  tool <name> <program> <link>
                            a tool the repo builds from its own sources for
                            its toolchain, which builds keeps once per key on
                            each host and links at <link> in the checkout
                            (BUILT TOOLS)
  linux-package <name>...   Debian packages a Linux host needs to build the
                            repo, such as clang for a crate that runs
                            bindgen; `builds host setup` installs them on
                            each Linux host (HOSTS)
  macos <package>...        cargo packages part of whose code compiles only
                            for macOS: on Linux, a cargo job that builds one
                            compiles and checks other code than on a Mac, so
                            `builds cargo` sends it to no Linux host (CARGO)

Tools always write through <checkout>/<path>, so the path a build sees never
changes, however often builds deletes and recreates the folder behind the link.
sccache's keys and cargo's fingerprints stay valid, and two checkouts never
share a folder, so their builds never wait on each other's locks. Every build
follows these rules:

  - Never set CARGO_TARGET_DIR, in the shell profile or on a command: the
    checkout's target link is the target folder. Two checkouts that build
    into one folder wait on cargo's lock and then rebuild what the other
    changed.
  - Never set another CARGO_* variable on a command or in a script (such as
    CARGO_INCREMENTAL or CARGO_PROFILE_*). sccache keys every CARGO_*
    variable, the working directory and the paths cargo passes, so a build
    with another path or another variable gets no cache hits. A setting goes
    in a --config argument or in Cargo.toml.
  - Never set RUSTC_WRAPPER="": it turns sccache off, and nothing on macOS
    needs that.
  - Never point a build at /private/tmp or the user's temporary folder (a
    -derivedDataPath there, a probe crate built where it was made): build in
    a checkout, whose paths lead to the volume.
  - A build script in a linked worktree finds shared refs through `git
    rev-parse --git-common-dir`: the worktree's own git dir has no refs/tags,
    and a build script that watches a missing path reruns on every build.
  - Every file a run writes goes to the build volume, none to the system's
    temporary folder, which fseventsd logs. Each `builds cargo`, `lake`,
    `app-build`, `build-app`, `lock`, `remote` and `shots` run (the shots
    subcommands but `findings` and `check-program`) makes
    <build volume>/.tmp/<pid>-<id>, sets its own TMPDIR to it before it
    starts anything, and deletes it when it ends. Every program it starts
    inherits TMPDIR: cargo and the tests, the Gradle and xcodebuild steps of an
    app build, and the Chrome of a shots run, whose profile folder `tempfile`
    makes there. A run inside another run (a lane of an app build, a `builds
    cargo` of a step) finds TMPDIR naming the outer run's folder and makes none.
    A job on another host makes the folder under that host's build root
    (HOSTS). Each folder's name holds the pid of the `builds` process on this
    Mac that owns the run. `builds health` deletes the folders whose run has
    ended, on every host that answers, and reports entries no run made. A run
    with no build volume mounted fails and writes nothing.
    TMPDIR is no CARGO_* variable, and sccache's key does not hold it (a
    compile with another TMPDIR hits the cache entry the first one wrote), so
    the folder's name never costs a cache hit.
  - The sccache server, which launchd (macOS) or systemd (Linux) starts and no
    run owns, gets a TMPDIR of its own, <build volume>/.sccache-tmp, from the
    job file `builds install` and `builds host setup` write. The job makes the
    folder first, and fails and starts again when the volume is not mounted.

A link whose folder is gone breaks every tool (cargo fails with os error 20,
xcodebuild with code 74, Gradle with "Could not open file hash cache"), so the
repo's scripts/build-layout.sh runs `builds setup`, which recreates the folder,
and the hooks and every build script run that script first. Without builds (in
CI) the script does nothing and the tools write into real folders.

The Claude Code session's rust-analyzer, which agent-instructions'
rust-analyzer plugin (claude/plugins/rust-analyzer) starts, builds into
target-ra, a .build-dirs entry with its own cap in bae and coven, and checks
nothing on save: its `cargo check --workspace` of everything held main's target
over its cap. A Rust repo with no target-ra entry gets a real target-ra folder
in its checkout. The plugin passes these options at initialization, because
rust-analyzer reads a repo's rust-analyzer.toml only after its first build has
started into target.

  {setup}

                              that is missing, delete folders an older layout
                              left behind, apply the disk rules (DISK, below)
                              to the checkout, DerivedData and the shared
                              caches, delete idle build output in the
                              temporary folders, keep the free-space floor,
                              and then run the checkout's `prepare` programs,
                              install elan and the toolchain each of its Lean

LEAN

A Lean package of a checkout is a folder whose .lake build folder the repo's
`.build-dirs` lists and which holds a lean-toolchain file, the toolchain that
lake builds the package with (coven: crates/sqlive/proofs and each package in
spec/proofs). `builds setup` installs elan, Lean's toolchain manager, under
~/.elan on the Mac it runs on when that Mac has none (elan 4.2.4), and then
each toolchain the checkout's packages pin that elan does not list. Setup runs
on a host before each job, so every host that builds a checkout with Lean
packages has their toolchains. elan downloads each toolchain once per Mac,
and every checkout shares it. A Mac that already has another version of elan
keeps it. A `.lake` folder with no lean-toolchain beside it pins nothing.

`builds lake build` runs lake build in the package of the working directory,
on the host with the most room, as `builds cargo` runs a test (CARGO): builds
skips the same hosts, sends the checkout's HEAD plus its working tree, and
runs lake in the matching folder of the host's remote worktree, whose .lake
folder stays between jobs in the host's builds root. The host's setup for the
job installs the toolchains, so a host needs nothing else. One line on stderr
names the host, and the command prints lake's output and exits with lake's
status. These stay on this Mac: every command in a main checkout, a command
run outside a checkout, and a command with an argument that is an absolute
path. On the Mac that runs lake, builds first installs the checkout's
toolchains, unless a pre-commit hook check runs it, and holds the checkout's
guard while lake runs, so no prune deletes the .lake folder under it.
BUILDS_CARGO_HOST picks the host for one command, as for `builds cargo`.

A cargo test that runs a Lean executable, such as coven's narrowing
differentials, which run the runner that SQLIVE_NARROWING_LEAN names, names it
in BUILDS_CARGO_LEAN instead of building it first:

  BUILDS_CARGO_LEAN=SQLIVE_NARROWING_LEAN=crates/sqlive/proofs:narrowingRunner \
    scripts/cargo.sh nextest run -p sqlive --all-features --run-ignored only \
    -E 'test(term_matches_lean)'

The Mac that runs cargo, a host or this Mac, builds the runner from the same
working tree with `lake query`, under the checkout's guard, and gives cargo
the runner's path there, so the tests and the runner they run always come
from one Mac. The host gets BUILDS_CARGO_LEAN as it is, since it names the
package by its folder in the checkout.

  {lake}
                              run lake build with these arguments in the Lean
                              package of the working directory, on this Mac or
                              the host with the most room; builds refuses
                              every other lake command: run those with lake
                              itself (~/.elan/bin/lake)


BUILT TOOLS

A `tool <name> <program> <link>` line names a program the repo builds from its
own sources for its toolchain, such as coven's typed lints' driver, a build of
clippy's driver with coven's lints added. builds keeps one build of the tool
for each key on each host, shared by every checkout of every repo whose key is
the same, and builds it on a host only when no other host of its platform has
it. A platform is an OS and a processor, such as macOS on arm64 or Linux on
x86_64: a build runs only on its own platform.

The repo's <program> answers two requests in the checkout's top folder:

  <program> key             print the checkout's key: two words, the
                            toolchain's id (coven: the commit its rustc was
                            built from) and a hash of the tool's sources
  <program> build <folder>  build the tool into <folder>, an empty folder
                            builds made, and write
                            <folder>/check: a program that makes the build
                            ready to run on the host it is on and fails unless
                            the tool runs there. BUILDS_TOOL_WORK names a
                            folder, one per toolchain on each host, where the
                            program keeps what the next build can reuse, such
                            as a fetched source and a cargo target folder, so
                            a new key compiles only what its sources changed

Each key's build is the folder caches/tools/<name>/<toolchain>/<sources> on
the build volume (a host's builds root on a host), and <link> in the checkout
points at it. To put a key in place, builds copies the folder from another
host of the same platform that has it, else builds it, holding the toolchain folder's lock so one
build at a time uses the work folder. When it builds, it says why no copy
served: each host lacked the key, did not answer, or sent a copy that failed.
Each copy and each build goes into a staging folder of its own, and takes its
place only once its check passes on the host it lands on. builds deletes a
rejected staging folder before it tries the next way, and when it cannot, it
stops with an error that says both why it rejected the folder and why the
deletion failed. `builds setup` copies each key of the checkout that this Mac
has to each host of this Mac's platform that lacks it, and so does a `builds
cargo` job before it runs on such a host, and each copy runs its check on the
host; when that fails, builds says so and the host builds the key in the job's
setup. A host of another platform, such as a Linux host, builds each key in
the job's setup itself. A pre-commit hook
check installs, fetches, copies and builds nothing, so the first `builds
cargo` after a change to a tool's sources puts the new key's build in
place on the Mac that runs cargo, before cargo, and the hook's checks find it
(a run inside a tool's own build, BUILDS_TOOL_WORK set, builds no tool, since
that build holds the key's lock): a `builds cargo` the hook runs
sends no key to the host, the host's setup for its job prepares nothing, and
`builds tool` only points the link at a build the Mac already has. `builds setup` and `builds prune` delete each key's folder,
and each toolchain's folder with its work folder, that no live checkout's key
names. They delete nothing of a tool whose key a checkout fails to print, and
nothing of any tool while a checkout's `.build-dirs` cannot be read.

A repo's script may run a tool as cargo's workspace wrapper through the tool's
link: coven's clippy sets RUSTC_WORKSPACE_WRAPPER to
tools/typed-lints/built/typed-lints-driver. cargo puts the wrapper's path
into the name of each workspace crate's output, and when a crate's sources
have not changed it prints that crate's last warnings again instead of
compiling it. The link's path stays the same when the link moves to a new
key's build, so cargo would print the old build's lints for each crate whose
sources did not change. So `builds cargo`, on the machine that runs cargo and
after the BUILDS_CARGO_BEFORE program, gives cargo the same file in the
key's build folder that the link points at. A new key lints every crate
again, with no source file touched, and a second run with the same key prints
the warnings cargo kept. A wrapper under a link that points at no build fails
the command, naming `builds tool`.

  {tool}
                              put the checkout's key of tool <name> in place
                              on this machine, point the checkout's link at it and
                              print its folder. A repo's script runs it before
                              it runs the tool, wherever cargo runs: coven's
                              clippy names a script that runs it in
                              BUILDS_CARGO_BEFORE. Run by a pre-commit hook
                              check (BUILDS_HOOK_CHECK set), it only points the
                              link at the build this machine has for the key,
                              and when it has none it fails at once, naming
                              `builds setup`


WORKTREES AND CLAIMS

Each repo has a main checkout, the person's, and side worktrees for agents at
<parent>/<repo>-worktrees/side-N. side-1 is long-lived; `builds new` hands out
the others. `builds health` and `builds prune` retire each one that is free:
no claim, a clean tree, every commit on its HEAD on origin/main by patch (a
copy on another branch does not count), no build running there. A retire
removes the worktree whole or fails and leaves it as it was. A new worktree
costs a few seconds, since `builds new` clones a warm checkout's `target` into
it, so a free one waits for nothing. The clone then
deletes cargo's record of each build script run whose `cargo:` lines name a path
of another checkout of the repo (a link search path such as FFMPEG_DIR's), so
cargo runs that script again in the new checkout, and no link names a folder of
a worktree that is later removed.

A claim records who works in a side worktree, so that no other session takes
it: whoever hands out the worktree (a coordinator dispatching an agent, or the
person) claims it. A landing that leaves nothing to land releases it (`builds
land`); whoever handed it out releases it when the work stops, once the
worktree holds nothing origin/main lacks: release refuses a worktree when
releasing it would leave its work with no claim and no item (`builds item stop`
keeps the work with its item instead). A local branch with commits waiting to
land that no worktree checks out and no open item names is work left behind
too: `builds health` lists it, with `builds new <repo> --resume <branch>` to
check it out in a worktree. A claim is a file in the worktree's git dir, so
retiring the worktree deletes its claim; `status` shows it, and `retire`
refuses a claimed worktree. A claim is not a lock: an agent runs a series of
separate commands, so nothing could hold one, and a session that ends without
releasing leaves its claim behind, with its age in `status`. Exclusive use for
one command, such as a build in an app checkout, takes a real lock.

A claim may carry a one-line note that says what its work waits on ("waiting on
Linux CI"), which `status` and the dashboard show, and the note may carry a
state that git can't show:

  waiting-on-you  the work waits on a question or a step only the person can
                  take
  winding-down    the agent is on its last item, then its handoff
  starting        `claim` and `new` set it, with the note "claimed; its item
                  is not yet taken", on a claim for an item that `item take`
                  has not started there; take clears it, `note` never sets
                  it, and `health` never releases a claim that carries it
  held            the worktree is kept on purpose with no work running, such
                  as uncommitted work waiting for another change to land; the
                  note says why and until when. A held worktree needs a
                  running item that waits on an open record, and `health`
                  doesn't call it idle while that record stays open; once the
                  record closes, `health` lists the worktree

A note set without --state has no state, so writing the next note clears the
state. Claiming the worktree again for the same <who> renews the claim's date
and keeps the note.

The dashboard gives each side worktree the first state that matches: Waits met
(no claim, and an open item keeps the worktree with every wait met: land its
commits or resume its agent), Waiting (no claim, and an open item keeps the
worktree while it waits on an open record: the card names each), Ready (no
claim, and an open item with no waits keeps the worktree with its unfinished
work: `builds item stop`, `builds help lists`), Can't read what this worktree
waits on (the daemon could not read an item's waits, the branch's design
coverage or its rules review, and the card says why), Waiting on you
(the claim's note says so, a running item waits on a question or on a design
change the person has not approved, or the worktree's commits are a design
change the person has not approved whose rules review takes them), Paused (the claim's note has --state
held: the card says what its running items wait on), Ready to land (commits
waiting to land, claimed or not: an unclaimed worktree with such commits holds
work an agent left behind; a claimed one waits for its agent to land it),
Winding down, Working (claimed) and Free. While a `builds land`, `builds
app-build`, `builds design record` or `amend`, or `builds shots draws` runs for
a worktree's branch, the card with commits waiting to land stays Working and
names it: Landing, App build, Design record or Board comparison (an app build
that waits in a lane's queue or holds a lane's lock shows the lane instead).
While a landing runs, the card judges no design coverage and no rules review,
since git then shows the commits the landing checked out. Commits
waiting to land show as Ready to land only when `builds land` would take them
as far as the rules review goes; until then the card shows the review's
progress instead: Needs review (no review read these commits, or a group still
has to answer: the branch's agent runs `builds review`), Reviewing (Builds
checks design coverage, reads where the rules review stands or runs a rules
review of the branch's newest commit),
Findings to settle (with the count and who settles them: the judge, the
coordinator or an independent session),
Open findings (confirmed findings that wait for a review that closes them) or
Unreviewed changes (with the count of files that changed since the last
review, which `builds review` reads as a new run of the review). A commit
waits to land while origin/main has no commit with the same change (`git log
--cherry-pick --right-only origin/main...HEAD`), because landing rebases or
cherry-picks it.
The dashboard daemon records each change of a card's state, at most every 5
seconds, in the store of the card's project: the time, the state and the items
the card lists. The daemon judges the state with the same code that draws the
card, and records nothing until it has read the processes once. `builds item
times` reads these records.

  {new}
                              hand out a free side worktree with a fresh
                              branch from origin/main, or add the next side-N
                              when none is free; link it and run its
                              post-checkout, which builds nothing. A free
                              worktree is a side worktree that has no claim,
                              and passes the check `release` makes: no item of
                              any project runs in or keeps it, its tree is
                              clean, no `git commit` runs there, and every
                              commit on its HEAD and on each branch it left
                              since its last claim began is on origin/main by
                              patch. new checks every worktree before it
                              changes one, and it moves and deletes no
                              branch: -b refuses a branch name that exists.
                              new claims the worktree for <who> (default
                              "builds new") under a lock on the repo, so two
                              calls never get the same worktree. When
                              the worktree's host target is empty, new fills
                              it with a copy-on-write clone of another
                              checkout's built target, taken while no build
                              runs there (it waits for one when every source
                              is building), so the first build compiles
                              little. --project P records which project's work
                              it is, and a repo that two projects hold
                              (agent-instructions is in bae and builds)
                              requires it: every lists command run in the
                              worktree, `release`, `health` and the dashboard
                              then use P's lists. --resume checks out an
                              existing branch that no worktree checks out,
                              instead of a fresh one from origin/main: work
                              left on a branch goes back into a worktree this
                              way. An agent that takes an item gets its worktree
                              from `builds item take N --repo R --branch B`
                              instead, which claims the worktree as new does
                              and gives it back when the take is refused
  {claim}
                              record that <who> works in the side worktree
                              (--project as for `new`; a claim renewed without
                              it keeps its project). When builds removes a
                              claim (`release`, a landing, `builds item stop`
                              or `drop`), the worktree keeps it as its last
                              claim, and `new` counts the branches the
                              worktree left from that claim's start
  {note}
                              set the claim's note, or clear note and state
                              with no text; --state needs the text. --state
                              held is refused unless every item running in the
                              worktree waits on an open question, item, design
                              change or condition (`builds item wait N --on
                              REF`, a condition with `--until`); note never refuses it for an app
                              checkout, which runs no item. A note that makes
                              the worktree held, or ends its hold, starts or
                              ends the held time of each item running there
                              (`builds item times`)
  {release}                   remove its claim; refused while an item of any
                              project runs in the worktree, and while it holds
                              work origin/main lacks that no item holds: commits
                              on HEAD, on a branch the worktree left since its
                              claim began (since its last claim began, when it
                              has none; HEAD's reflog says which) that no
                              worktree checks out, files not committed, or a
                              `git commit` that runs there (its hook can run for
                              minutes before git commits the files). A detached
                              HEAD past origin/main counts too. A commit with
                              the same patch as a commit on a branch that
                              another worktree checks out, or that an open
                              item holds, is no such work: release frees a
                              worktree whose commits are all such copies, and
                              names that branch ("builds health" releases it
                              the same way). The refusal
                              names the commits, the files and each `git commit`
                              that runs, and the commands that keep the work:
                              land it, stop its item (`builds item stop`),
                              which keeps the worktree for the item, or take
                              an item there (`builds item take`, with --held
                              when the item waits on something open). An item
                              that keeps the worktree holds all of it. The
                              coordinator may instead throw the work away
                              (`discard`). `new` hands out no worktree that
                              this check would refuse
  {discard}
                              throw away work origin/main lacks that no item
                              holds. The coordinator decides that on its own
                              judgment and never asks the person. For a side
                              worktree W, discard throws away its commits, the
                              commits of the branches it left since its claim
                              began and its files not committed (ignored files
                              stay), deletes those branches, detaches W at
                              origin/main and removes its claim. With --branch
                              B, discard deletes branch B of the repo at REPO,
                              which no worktree checks out and no open item
                              names. discard refuses a worktree an item of any
                              project runs in or keeps (`builds item drop`
                              throws away an item's work), one where a `git
                              commit` runs, and a worktree or branch with no
                              such work. Before it changes git, discard records
                              a decision in the project's decision log: who
                              (--by, else the claim of the worktree the command
                              runs in), why, and each commit and file. git
                              keeps the commits until it removes unreachable
                              objects. When git fails, running the same discard
                              again throws away and records what is left
  {retire}                    remove a clean, unclaimed side worktree and its
                              build root; refuses every other worktree, a
                              worktree an item runs in or keeps, one that
                              `release` would refuse for its work (commits on
                              its HEAD or on a branch it left since its last
                              claim began, or files not committed), one
                              whose HEAD has a commit origin/main lacks even
                              when another branch has a copy of it (`release`
                              accepts that copy), one git has locked and one
                              with submodules. `new` hands out no worktree
                              whose HEAD has such a commit. A retire removes
                              the folder and git's record of the worktree
                              with a rename each, into
                              <main>/.git/builds-retiring, and deletes files
                              only after both: when it fails before then the
                              worktree stays as it was, and the next command
                              that picks or retires a worktree of the repo
                              moves back the folder of a retire that was
                              killed between the two, and deletes files an
                              earlier retire could not


CARGO

Run every cargo command through `builds cargo`; in bae and coven,
scripts/cargo.sh runs it, and the hooks and build scripts use that script.
builds reads cargo's report of each build to record the build copies it used
(DISK, below). cargo typed by hand records nothing, so builds deletes what only
it uses three days after cargo last built it.

`builds cargo` runs every build with --locked, unless the command passes
--locked or --frozen itself. When a commit's Cargo.lock disagrees with its
Cargo.toml files, cargo fails, names the cause and leaves the lock as the
commit has it.

`builds cargo update` rewrites Cargo.lock: run it after you change a
dependency's version, or a git dependency's rev, in a Cargo.toml, and name each
package whose entries change (`builds cargo update -p coven`). builds runs
cargo update as given, on this Mac in the working directory, without --locked,
and refuses an update that names neither a package nor the workspace (-w), since
cargo would then move every dependency in the lock to its newest compatible
version. An update builds nothing, so builds records no run and no build
copies for it.

`builds cargo mutants` runs cargo-mutants (scripts/cargo.sh mutants in bae and
coven) on the host with the most free cores, placed as the runs below are
(HOSTS says which hosts take a run), except that no host counts as warm for it:
cargo-mutants copies the workspace and builds the copy afresh. builds caps the run's `--jobs` by the
room under the chosen host's load band: the band's high end less the host's
5-minute load average, rounded down, and at least one (this Mac's band when the
run stays here or the host refuses it). A run that asks for more
jobs gets the cap, and one line on stderr says so; a run that names no jobs
keeps cargo-mutants' one. Each job builds and tests a whole copy, so a run
over the whole workspace takes hours: scope it to the code that changed with
`--file`, once for each file (`scripts/cargo.sh mutants --file
src/queue.rs --file src/queue_tests.rs -p bae-queue`), or with `--in-diff
FILE` for a diff, and look at what a run would test first with `--list`.
cargo-mutants has no cargo message format for builds to read, so builds
records no build copies for it. builds skips a host without cargo-mutants at
the one version builds installs (27.1.0, installed by `builds install` on this
Mac and by `builds host setup` on each host, compiled there with `cargo install
--locked`), as it does for nextest below.

`builds cargo` also runs the subcommands that only read the workspace: tree,
metadata, locate-project, pkgid and verify-project. builds runs each on this
Mac in the working directory with --locked, as it runs a build: without
--locked, cargo rewrites a Cargo.lock that disagrees with the manifests.
builds adds nothing else to a read, and records no run and no build copies for
it. builds refuses every other subcommand that builds nothing, such as fmt and
clean: run those with cargo itself.

Every checkout but main builds without incremental compilation (`builds cargo`
passes --config build.incremental=false), the app checkouts included. sccache
refuses every incremental compile, so with incremental off sccache keeps each
workspace crate a checkout built, and the checkout gets it from the cache when
it builds the same sources again, as an app checkout does when agents move it
back to a branch it built before. sccache's key holds the folder cargo compiles
a crate in and every CARGO_* variable, CARGO_MANIFEST_DIR among them, and cargo
compiles each workspace crate in the checkout's top folder, so a workspace
crate one checkout built never serves another checkout. A crate from a
registry or a git source compiles in cargo's shared source folders, so its
cached build serves every checkout. The only incremental folders are those a
repo's lint wrapper keeps for the crates it lints (DISK). A full build without
incremental output is smaller, so the app checkouts' folders take lower caps.
Main, the person's checkout, stays on one branch and keeps incremental. To turn
incremental on in a profile, set profile.dev.incremental in Cargo.toml, never
CARGO_INCREMENTAL=1, with which sccache refuses every compile.

In a side worktree, `builds cargo` runs test, clippy, check, doc and nextest
run|list on the host that ran the checkout's last run of the same subcommand,
which `builds cargo` reads from the runs it records, while that host can take
the run. Each host keeps its own build folder for the checkout, and only the
host of the last run has that run's build. Another host's folder for the
checkout may be cold, and there cargo compiles again everything that changed
since that host's last build for the checkout. When no host ran the
subcommand for the checkout, or that host cannot take the run now, builds
runs it on the host with the most free cores, each counted at the host's core
speed. builds skips a host that does not answer, is under the free-disk
floor, refuses jobs (HOSTS), has no measured core speed (`builds host setup`)
or has no clone of the repo. A job that builds a package that a `macos` line of
the checkout's `.build-dirs` names (BUILD FOLDERS) skips every Linux host: the
job builds the packages its -p arguments name, with none every package with
--workspace, else the package of the folder it runs in, or every package in
the workspace's own folder. One line on stderr names each host the job skips
for that reason. For a nextest run, builds also skips a host
without cargo-nextest at the version builds installs (0.9.143, installed by
`builds install` on this Mac and by `builds host setup` on each host), and
names the host and the version it has (a mutants run skips a host the same way
for cargo-mutants). A run of tests (test, nextest run, mutants) also skips a
host without node at the version builds installs (22.17.0, installed the
same way, from nodejs.org into ~/.cargo/bin, which starts every host job's
PATH), because builds' own tests run the dashboard's and the design
renderer's page scripts in node. `BUILDS_CARGO_HOST` naming such a host
fails. A host's free cores are its cores minus its
one-minute load, less the host's cores again for each `builds cargo` or
`builds lake` run that started there in the last minute and still runs: cargo
and lake run a compile job per core, and the load average shows a run only
after a while. A host's core
speed is this Mac's time divided by the host's time for one fixed compile on
one core, which `builds host setup` times on both, so a job goes where it
finishes first.
This Mac wins a tie. When several runs start at
the same time, builds picks a host for one run at a time, so the runs go to
different hosts. The load average never shows the compiles that wait in
sccache's queue on a host whose cores are all busy, so builds also counts the
`builds cargo` runs it placed on each host that still run. Each host's share
of those runs and the new one is their number split by the hosts' cores,
rounded up, and a host that would pass its share takes no new run, not even a
run whose last run went there, while another host stays within its share. builds sends the checkout's HEAD plus its working tree (staged and unstaged edits, deletions,
and files git neither tracks nor ignores) as a commit to the host's clone only,
runs cargo in a remote worktree there that keeps its build between runs, in the
folder that matches the one the command ran in (cargo picks the package of the
folder it runs in), prints the same output and exits with the same status. The host's cargo gets
BUILDS_CARGO_LEAN, CLIPPY_ARGS, RUSTDOCFLAGS, RUSTFLAGS, RUST_BACKTRACE,
RUST_LOG and RUST_TEST_THREADS from the caller's environment; one line on stderr names the
host. When the host refuses the job before cargo starts there (sending the
commit or claiming a worktree fails there), builds records the host as
refusing jobs, says so on stderr with what the host said, and runs the command
on this Mac. A stop signal stops cargo on the host, and so does the end of
`builds cargo` by any other signal, SIGKILL included, or a connection to the
host that closes: no job on a host outlives the command that started it. A
connection that fails mid-run fails the command, naming the host and each
sleep either Mac recorded meanwhile (HOSTS); builds never runs the command
again here, since cargo may have run part of it there. A landing's
compile check runs `builds cargo`, so it follows the same rules. These stay on
this Mac:

  - every other subcommand (build, rustc, run, bench, install, update, and the
    reads, such as tree and metadata)
  - a command with --message-format, --target, --release or a path argument
    (--manifest-path, --target-dir, an absolute path)
  - a command run with CARGO_TARGET_DIR or FFMPEG_DIR set, or with
    RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER or BUILDS_CARGO_BEFORE set to a
    path outside the checkout (a wrapper given as a bare name, such as
    sccache, is the host's own)
  - every command in a main checkout

To test builds itself, run `builds cargo nextest run --bin builds -E
'test(/^trees::/)'` with a filter for the modules you changed. nextest runs
each test in a process of its own. `cargo test` runs the tests of a binary as
threads of one process, which share one descriptor table: a child that one
test starts holds a copy of every file another test has open, locks included,
until the child execs, so a test that takes a lock without waiting can find it
held and fail only in a run with other tests.

One sccache server serves every checkout. launchd runs it
(local.sccache-server) on sccache's default port, 4226, with
TMPDIR=<build volume>/.sccache-tmp and no idle timeout; its cache is caches/sccache, capped in
~/Library/Application Support/Mozilla.sccache/config. `builds install` writes
both here and on every host, `builds host setup` writes them on a host (whose
cache is sccache's default folder, ~/Library/Caches/Mozilla.sccache on a Mac
and ~/.cache/sccache on Linux). On a Linux host the user's systemd runs the
server from the unit ~/.config/systemd/user/local.sccache-server.service, with
TMPDIR=<builds root>/.sccache-tmp, and its config is ~/.config/sccache/config. `builds status`
flags a config that no longer holds builds' cap, and `builds health` names each
host whose server launchd or systemd does not run, whose config does not hold
builds' cap, or
whose server runs with another cap than its config's: a server reads its
config when it starts, so one that started before builds wrote a new cap keeps
the old one until it starts again.
Builds commands that set TMPDIR for a run allow sccache clients to use the
shared server. They give clients an error log path that prevents them from
starting a server. If no server answers, sccache fails and names
local.sccache-server in the error log path. Run that job under launchd on
macOS or systemd on Linux. A server that uses a run's TMPDIR fails to compile
after builds deletes the folder. sccache never caches build scripts, an incremental
compile or a crate clippy lints, and a crate that reads OUT_DIR misses in each
new checkout. sccache also hashes the bytes of each library a crate names,
and a crate that includes a file its build script wrote, as serde does,
records the OUT_DIR path in its library. So `builds cargo` gives cargo
~/.local/bin/builds-rustc as RUSTC_WRAPPER (a symlink to builds that `builds
install` and `builds host setup` make), unless the caller names a wrapper
other than sccache. builds-rustc runs sccache, and for a crate whose build
script wrote files into its OUT_DIR it adds
`--remap-path-prefix=<OUT_DIR>=/OUT_DIR`, so that crate's library is the same
bytes in every checkout and the crates above it come from the cache. A
repo's own wrapper, such as bae's clippy wrapper, runs builds-rustc where it
would run sccache. sccache hashes each proc-macro a crate names, and ld names a
dylib by its path, so `builds cargo` links this Mac's own target with
~/.local/bin/builds-linker (a symlink to builds that `builds install` and
`builds host setup` make): it runs cc and names each proc-macro dylib
@rpath/<its file name>, so one proc-macro built in any checkout is the same
bytes and the crates above it come from the cache. A cdylib, such as
bae-bridge's, keeps the name ld gives it. `builds help workflow` says when to
restart the server.

APP BUILDS

An app build runs only the test classes and the shots of the screens a change
touches: name each class with --test, and each screen's shots with --shots and
a prefix (mac.welcome. for the Mac welcome screens). CI runs the full suites.
An app build waits in its lane's queue and then runs for minutes, so run
`builds app-build` as a background task.
`builds app-build` refuses a --shots prefix that selects every shot of a lane
(mac. or android.) and a step that a `ci-only` line names, and says why. It
also refuses, before the build joins a lane's queue, a --shots prefix that
starts no shot the harnesses declare at the branch's commit, and names the
nearest declared prefixes.

A design branch passes `--design-shots` in place of listing prefixes: builds
picks the shots of each board the branch changes (named for the board) and the
rows of each component it changes (`mac.component.row.` for MacRow), keeps
those that the harnesses declare, and says which change picked no shot and
why. A changed README picks nothing, and a changed shared design-system source
picks no component: name those shots with --shots. The picks join any --shots
and --test picks, and leave out the scenes that wait on app work.

To run every shot of one lane, pass `--all-shots mac` or `--all-shots android`.
A full run has two uses: board matching's measurement of a lane on a commit of
origin/main, which the coordinator runs (`builds help workflow`, BUILDS), and
the run that a change to the shots program is checked against.
An app build runs the installed shots program, so --all-shots never checks a
change to the shots program on a branch. To check that change, run `builds
shots check-program` (below) over a lane's cached --all-shots run. For a
change to screens, name their prefixes with --shots instead. builds runs the
lane's `shots` line once, with the prefix that every shot of the lane starts
with (mac.), so the run goes where any --shots run of the lane goes: it waits in
the lane's queue, holds a lock of the lane, and takes a free app checkout (for
a `shots` line that passes --windows, only one on a host, as below). builds caches its findings and report
under that prefix like any other shots run's (below), and `builds shots
findings <repo> <ref> mac mac.` prints them again. The shots program takes a
window's shot on the display of the host it runs on, whose size may differ
from another host's, so a window that fits one display and not the other can
pass on one and fail on the other.

App builds (an Xcode app, a Gradle app, a bridge cross-compiled for a platform)
take 10-20 GB per platform per checkout, so a repo keeps them built only in
main, for the person's installs and releases, and in its app checkouts, one or
more per lane: the long-lived ones a person records with `builds app-checkout`
(worktrees here or on a host), and the ones the builds tool adds on a host
while other builds wait for the lane and removes once no build uses them.
Every side worktree builds host output only (for Rust, target, which tests,
clippy and the hook use).

A worktree is a side worktree or an app checkout, never both, and its name
says which. A side worktree is named side-N, and `builds new` and `builds item
take` hand only side worktrees to agents. An app checkout takes any other name
of letters, digits, dashes and underscores that does not start with remote-,
which job worktrees take. `builds app-checkout` refuses a side worktree, and
builds fails on a lane's set that names one.

The builds tool adds checkouts to a lane while other builds wait in its queue,
and removes the ones it added that no build uses. A build that joins a lane's
queue and has to wait adds a checkout `builds-<lane>-<n>` on a host.
builds picks the host with the most free cores (its cores less its one-minute
load) among those with at least one core free, free disk above the floor
(BUILDS_FREE_FLOOR_GIB) by one checkout of the lane (about 22 GB for mac and 10
GB for android, as measured on the M1; a host that has a checkout of the lane
to clone from, below, needs only what the clone does not share: about 12.3 GB
for mac and 1.3 GB for android), and fewer than 6 app checkouts in all;
a lane has at most 4. The new checkout's first build makes it on the host, as for one `builds
app-checkout --host` records. A build that waits adds a checkout only on a
host. A build that may run only on this Mac (the android build-app, a mac
build-app or app-build that runs a `here` step) and finds the lane with no
checkout on this Mac adds a new worktree of ~/dev/<repo> named
`builds-<lane>-<n>`, set up as `builds new` sets one up and recorded in the
lane as the person's, so builds never removes it. A new app checkout of a lane
starts from copy-on-write clones of the cargo
build folders of the lane's warmest checkout on the same host (the one whose
lock a build let go of last), so the new checkout takes almost no new disk
and its first build compiles little: for the mac lane the host target and
target-macos, for the android lane the host target and target-android. builds
holds the source's lock while it clones, so no build runs there, and waits
for it when every source is building. A takeover ends the wait, and the new
checkout then starts empty. This holds for a checkout builds adds on a host, for a
checkout `builds app-checkout --host` records (its first build makes it there),
and for a worktree here that `builds app-checkout` adds to a lane that already
has a checkout on this Mac; it fills only folders that are empty. builds clones
no Xcode tree, SwiftPM package folder or Gradle folder, because each holds the
checkout's own path and a copy would rebuild or break: Xcode's build
description and compile commands name the tree and the sources by path,
SwiftPM's workspace state and git alternates point into the folder, and
Gradle records each task's outputs by absolute path. When the clone fails on a
host, builds removes the new checkout, so the next build makes it again.

A build that joins a lane's queue, and `builds prune`, remove each
checkout builds added that no build has used for 60 minutes, with its worktree
and build folders on the host. A checkout a person added stays until a person
removes it. builds reads and changes a lane's set of checkouts, and a build
takes a checkout's lock, only under the lane's queue lock, so two builds never
add the same checkout and no build takes one that builds is removing. `builds
queue` and the dashboard show when and why builds added or removed each one.

A lane is the part of a repo's app builds that shares no build output with the
other: in bae the mac lane is Xcode and target-macos, and the android lane is
Gradle and target-android. Each lane has its own app checkouts, locks and
queue, so a Mac build and an Android build never wait on each other, and each
app checkout keeps only its own lane's folders built. A checkout is one lane's,
never both. A lane with several app checkouts builds in as many at once, and
its queue gives each free checkout to the first build in line that may use it:
waiters go in the order they came, a waiter takes a free checkout it may use
even when a waiter ahead of it may not (a build that may run anywhere passes
one that waits for a checkout on this Mac), and one that dies in line never
lets anyone past the holders. A ticket's name ends in the words here or anywhere,
which say where its build may run.

An app build holds its checkout until the build finishes. If its lane process
exits during a foreground step, Builds holds the checkout until that command
exits. A daemon that the step starts can keep running after the checkout
becomes free.

An app checkout's working tree belongs to whoever holds its lock, and only for
the command they run holding it: nobody edits there or leaves changes behind.
Commit on your branch in your own worktree, then run `builds app-build`, which
takes the lock, checks out your commit (detached, because your branch stays
checked out in your worktree) and builds. Put everything that needs the build
(its tests, launching the app) in that one command; the next holder moves the
checkout. To change something, commit or amend in your worktree and run the
command again. A dirty app checkout fails the command rather than carry
someone's changes into your build: find out whose they are before deleting
them. After its steps, `builds app-build` checks the checkout again. When a
step changed a file your commit holds, or added a file that no ignore rule
covers, the build did not build your commit as it is: builds puts the checkout
back on your commit and fails the build, naming the files.

Another checkout may keep an app build while a wave of work needs it (the
person asks for an app build in a worktree, or parallel agents each need one).
Clear it once that work has moved on: retire the worktree, or delete the
folders behind its app links while nothing builds there.

Xcode's compilation cache. Every step of an app build, here and on a host, runs
with XCODE_XCCONFIG_FILE naming the checkout's settings file,
<root>/.xcode-settings/<repo>/<checkout>.xcconfig, which turns on
COMPILATION_CACHE_ENABLE_CACHING and sets COMPILATION_CACHE_CAS_PATH to
<root>/caches/xcode-cas, one store for the host. Xcode keys each Swift and Clang
compile by its content and its command line, which holds the checkout's and the
build tree's absolute paths, so without more a compile is a hit only in the
checkout that made it (a second checkout hit 23 of 279 compiles). On a machine
whose Xcode is 27.2 or newer, the settings file also turns on path mapping
(SWIFT_ENABLE_PREFIX_MAPPING and CLANG_ENABLE_PREFIX_MAPPING) and maps the
checkout's working tree to /^checkout and its folder on the build volume
(<root>/<repo>/<checkout>) to /^build, in SWIFT_OTHER_PREFIX_MAPPINGS and
CLANG_OTHER_PREFIX_MAPPINGS, so every checkout of a repo on the host compiles
with the same command lines. On 2026-11-21 on the M1 (Xcode 27.2), bae's `bae`
scheme built cold in one checkout with 0 of 274 hits (185 s) and then in a
second checkout of the same commit with 272 of 272 hits (138 s), while the host
was busy with other builds. Xcode 26.3 crashes in that scheme with any mapping
(swift-frontend, bad_optional_access in CachingDiagnosticsProcessor, exit 65),
so a machine with an older Xcode gets caching without mapping, which only
speeds up a rebuild in the same checkout. A path with a space cannot be
mapped, so the step fails naming it. `builds prune` deletes the store whole when
it is over its 10 GiB cap, as for the other shared caches.

A repo's `.app-build` at its root says what its app builds run, one line each:

  step <lane> <name> <program> [<args>...]
                    a step of the lane. A step is a program, not a shell
                    string: a step that needs a shell is a script in the repo
  on <pattern> <step>...
                    the steps a changed path matching the pattern builds (a
                    pattern ending in / or naming a path matches the paths
                    under or at it; one starting with * matches the paths
                    ending in the rest)
  needs <lane> <step>...

                    changed path picked one of the lane's steps
  sources <lane>[:<name>] <folder>...
                    the folders that declare the lane's test classes; with
                    :<name>, the `test <lane>:<name>` line runs the classes
                    declared there
  test <lane>[:<name>] <program> [<args>...]
                    how the lane runs test classes: builds runs the line
                    once for all of a build's classes that the line runs,
                    and copies the word that holds {class} once for each
                    class; a lane may have a named test line per kind of
                    test (bae: mac:shots for the shot test bundle)
  shots <lane> <program> [<args>...]
                    how the lane runs the shots (pictures of app views, each
                    checked against its board) whose names start with the
                    prefix in its {select}: `builds shots run`, to which
                    builds adds --before <findings.json> when the run
                    compares with another (below)
  shared-shot-display mac
                    The Mac harness leases a shared display for window shots.
                    Bitmap shots from that harness need no display.
  shots-<setting> ...
                    a setting of the shots checker (`builds shots`), which
                    reads these lines itself: the parser of the other lines
                    skips them
  results <lane> <path>...
                    the folders a --test or --shots run on another host
                    copies back to this Mac
  here <step>...    steps that never run on another host (bae's signed macos
                    step)
  opens-windows <lane>[:<name>]...
                    the test lines whose runs open windows (bae's mac:ui line,
                    for its UI tests); a --test run of such a line runs on this
                    Mac or on a host, and one such run at a time on each
                    host, this Mac included (APP BUILDS)
  ci-only <step>...
                    steps that only CI runs, such as a whole test suite
                    (bae's macos-tests-all); app-build refuses such a step
                    when a caller names it,
                    leaves it out when it runs every step of a lane, and
                    refuses an `on` or `needs` line that names it
  limit <step> <time>
                    the step's time limit (90s, 30m, 2h), in place of 45
                    minutes

A step that runs past its limit gets SIGTERM to its whole process group, and
what of the group still runs ten seconds later gets SIGKILL. The step fails the
build, which gives up the lock.
builds limits each run of a test line, with all of its classes, to 10 minutes.
A --shots or --all-shots run of the shots checker (a `shots` line that runs
`builds shots run`) has 20 minutes and 6 seconds for each scene it takes: before
the run, builds counts the scenes with `builds shots scenes`, the same command
with the same arguments, in the checkout where the run happens (on a host, under
the build's programs there), prints the count and the limit it gives, and kills
the run past that limit. A whole lane's run (467 Android scenes, 702 Mac scenes
in bae) so finishes on the hosts builds has, and a run that hangs is still
killed, since its limit is fixed before it starts. A `shots` line that runs
another program has 20 minutes. `builds build-app` and `builds lock` set no
limit.

SIGTERM, SIGINT or SIGHUP stops an app build. `builds app-build` passes the
signal to each lane, and each lane passes it to the process group of the step
that runs; a step on a host stops there. A lane that waits for its turn in the
queue or for a host's display stops waiting, and a lane between two steps
starts no other. The lane puts the checkout back on its commit when the steps
changed it and gives up its lock and the host's window lock. When the lane had
taken a checkout, builds records its run as stopped, with the step that the
signal ended as stopped. Once every lane has ended, app-build exits and says
which signal stopped it.

The same signals stop `builds build-app` and `builds lock`. Each passes the
signal to the process group of the command that runs, and a build on a host
stops there. Each stops waiting for its turn in the queue, starts nothing
after the signal (build-app copies, installs and quits no app), gives up its
lock and exits saying which signal stopped it, with the exit status 128 plus
the signal, as a shell gives a program that a signal ended. The dashboard shows
a build-app run that exits so as Stopped, and one that exits with any other
nonzero status as Failed.

An app checkout may be on another host (`builds host`). Its lock, queue and
record of its last build stay on this Mac, under the entry <host>:<name>. A
build there sends the commit to the host's clone as a job ref (never to
GitHub), switches the checkout to it (the checkout must have no changes), and
runs each step through `builds remote step`, with the same time limits and
takeover; its output comes back behind [<lane> <host>:<name>]. After each
--test or --shots run there, passed or failed, the folders of the lane's
`results` lines are copied to /Volumes/Builds/<repo>/<host>:<name>/<path> here,
where agents read them. A step on a host ends with its exit status as soon as
its command exits: builds stops the processes the command left in its process
group, and a process it left elsewhere (a build daemon) cannot keep the step
running, since the command's output reaches ssh through relays that builds
ends. A connection to a host that stops answering ends within a minute and
fails the step, and builds keeps this Mac awake while a build holds a
checkout on a host, since a sleep here ends the connection (HOSTS). A mac
lane checkout on a host needs Xcode there. The lane's list of checkouts stays
on this Mac, so builds writes the lane's name to the file builds-app-lane in
the checkout's git dir on the host: when a person adds
a checkout the host already has, and when a build makes a new one there. The
host's own `builds setup` and `builds prune` read the file and keep the
checkout's builds warm, as this Mac does for its own app checkouts.
The android build-app, a mac build-app whose build is a `here` step, `builds lock` and a build that runs a `here` step never
take a checkout on a host. A build that runs a test class through a line an
`opens-windows` line names, or a --shots or --all-shots run of a `shots` line
that passes --windows (bae's mac line), takes a checkout on this Mac or on a
host, as any other build does, and its windows may show on the person's screen
and take their keyboard focus when it runs on this Mac (decision #485 of
project builds). A build may run a `here` step and such a test class together:
it runs them in an app checkout on this Mac. A host runs UI tests only
with the settings HOSTS names, since nobody is at its screen to type a
password.

Each Mac has one keyboard focus. A test that opens windows or a shot that
takes the keyboard focus holds that Mac's window lock exclusively. A Mac
harness that declares `shared-shot-display mac` leases the same shot display
across builds on that Mac. Its window shots take the lock in shared mode, so
they can draw together. Builds reads window scenes from `frame: .window(`
and reads scenes that take the focus from `takesFocus: true`. Bitmap-only runs
of a sharing harness take no lock. A Mac harness that passes `--windows`
and adds its own display takes the lock exclusively for every capture.

The lock covers every repo, lane and checkout on one host. A step that finds
the lock held waits and names the run it waits for when builds knows its name.
The build keeps its app checkout and its place in the lane while it waits.
A takeover ends the wait. Builds cannot tell whether a `builds remote run`
command opens windows, so each remote job on a Mac holds the lock exclusively
until it ends. Linux remote jobs and cargo jobs take no window lock.

Before each mac lane step that opens windows, after it takes the host's
window lock, the lane reads the host's display once, this Mac included:
`ioreg` for the lid and the screen lock (IOConsoleLocked and
CGSSessionScreenIsLocked), `system_profiler` for the displays, and
`lsappinfo` for the app in front. While the reading gives a reason the host
cannot show the step's windows, the lane holds the step, prints "waiting for
host <name> to show windows, since <reason>" ("this Mac" on this Mac) once for
each new reason, and reads the display again each time it changes, checking
every 15 seconds; it starts the step once the reading gives none and prints
"host <name> shows windows again". A takeover ends the wait. The reasons are:

  - its screen is locked, which keeps every window from rendering;
  - a system alert (UserNotificationCenter, SecurityAgent or
    CoreServicesUIAgent) is in front of every app, which keeps the focus from
    every window the step brings forward;
  - for a --shots or --all-shots run whose prefix starts a scene shown in its
    window, its lid is closed and it lists no other display: the run draws
    the scene on a shot display, which macOS makes only when the Mac has a
    display to add it to. Before such a run takes a checkout on a host, it
    reads each host's display and takes a host that can draw, the one with
    the least load. When none can, it takes one that cannot, and its window
    steps wait until the lid opens or a display is attached. A host that does
    not answer is skipped and named. This Mac is never asked about its lid,
    and runs of UI tests and every other step ignore the lid.

builds holds a step in the same way while Chrome cannot start on the host
(below): the person fixes each of these at the Mac. When the host's Xcode
cannot start, or its UI tests time out turning on automation mode (below),
builds instead records the host and runs the lane on another host.

While the step runs on the host, it runs under `caffeinate -d -u`, which
holds a display assertion there, so the display neither sleeps nor locks
during the step.

While a host holds a step for one of these reasons, the lane records beside
its lock the step, the reasons and when the hold began. `builds health`
reads that record and lists each held step with its host, its reasons, its
build and how long it has waited. `builds health` also lists each Mac whose
screen is locked or that shows a system alert while no step waits there
(HEALTH CHECK in `builds help workflow`).

A shots run draws the boards it compares with Chrome, and on a Mac Chrome's
main thread waits for the window server to answer before it prints the address
of its debugging socket, so a host whose window server does not answer never
starts Chrome. A build with --shots or --all-shots starts Chrome on its
checkout's host (`builds shots chrome`) after it takes the checkout and before
it builds anything. While Chrome prints no address within its 120 seconds, the
lane prints "waiting for Chrome to start on host <name>" with why, once for
each new why, keeps its checkout, records the step "start Chrome" beside its
lock with why, and starts Chrome there again every minute, then goes on when
Chrome starts and prints "Chrome starts on host <name> again". A takeover ends
the wait. A Chrome that fails to start for another reason fails the build at
once. `builds health` lists each host that holds a build this way, as it lists
the steps a display holds (HEALTH CHECK in `builds help workflow`).

Each host draws no more pages at once than half its cores (at least one),
however many Chromes run there, so drawing boards leaves room for the host's
other work. Every program that starts the pinned Chrome (a shots run, `builds
shots draws`, `builds web picture`, the shots crate's tests) takes a slot before it opens a page and
gives it back when the page closes. A slot is an exclusive flock on one of the
files in <build volume>/.chrome-slots, the volume that BUILDS_ROOT names, so a
test and a builds run on one host share the slots, and the kernel frees the
slots of a process that dies. With no build volume mounted, a program that
starts Chrome fails and writes nothing. A page that finds every slot held
prints "waiting for one of the host's N Chrome slots" once on stderr and waits.
The 120 seconds a page has to draw start once it holds a slot.

When a host's Xcode cannot start, every xcodebuild run there fails, whatever
code it builds: xcodebuild prints "A required plugin failed to load" and names
the fix (as after someone updates Xcode and nobody runs its first launch, which
installs its system content). When a mac lane step fails after printing that
line, builds records the host (this Mac included) in the folder
host-xcode-failures beside the file `hosts`, and the lane runs again from its
place in the queue in a checkout on another host. The mac lane skips a recorded
host's checkouts, and `builds health` lists the host under "needs action" with
xcodebuild's fix, until `builds host clear-xcode <name>` removes the record. A
step that fails without that line failed because of its code, and fails the
build. A mac lane step that fails after XCTest printed "Timed out while
enabling automation mode" failed because the host lacks the settings that UI
tests need (HOSTS): builds records the host in the folder host-ui-automation-failures
beside the file `hosts` and runs the lane again on another host in the same
way, until `builds host setup <name>` finds the settings on and removes the
record.

last step, here and on each host. Its merge base's shots runs and its own
use the same version of the shots checker. If `builds install` starts
moving the stores after the app build picks its program and before a lane
starts, the lane stops and asks you to run `builds app-build` again
(INSTALLING). Each version keeps its builds in ~/.local/lib/builds/<version>/,
named by `builds version`'s hash.
The first app build of a version copies the builds it started from into
that folder, once the copy says that version (when an install replaced the

installed builds in its place). The build holds the folder while it runs,
starts its lanes from the folder's builds and puts the folder first on PATH,
so `builds shots run` in a `shots` line runs the folder's builds. Before each step on a host, the lane copies the folder
to the same place on the host when the host lacks it, and runs the step
under `<folder>/builds programs hold`, which holds the host's folder and
puts it first on PATH there. `builds install` removes each other version's

builds caches each --shots and --all-shots run on the build volume, in
/Volumes/Builds/shots/<repo>/runs/<commit>/<lane>/<environment>/<prefix>/<capture>/<comparison>/,
so the next run in the checkout cannot overwrite it. The run-v2.json file
holds the end time, exit status and kind of run. For a recheck, it also holds
the source run's verdict. Builds treats records from before it kept the run
kind as cache misses. The output.txt file holds the shots program's output.
The report folder holds the pictures, findings.json and the index.html
page when the run writes one. The folder's path is the run's
key: the repo, the full commit, the lane, the environment, the prefix, the
capture version and the comparison version. A later run of the same key
replaces the folder whole.

The environment is the host software that draws the shots, which the lane
reads from the host of the checkout it builds in, each time it takes the
checkout, and never from a constant. For the mac lane it is the macOS build
and the Xcode build, such as 26B131-17C529, from `sw_vers -buildVersion` and
the `Build version` line of `xcodebuild -version`. For the android lane it is
the host's OS name and machine, such as Darwin-arm64, from `uname -sm`, since
Robolectric loads native graphics per OS and architecture. A command that
fails fails the build with what it printed. Another macOS or Xcode draws the
same app's shots with other element labels and other pixels, so a shots run
compares only with a run made in its own environment, and builds reuses a
cached shot only in the environment that took it. The lane prints the
environment it draws in. A read of a commit's own run (`builds app-build
--shots` printing a cached run, `builds shots findings`, `builds shots
check-program`) takes the newest run of the commit and prefix made in any
environment and says which environment made it. No code reads the runs that
builds cached before the key held an environment, which sit one folder level
higher: the cap neither reads nor deletes them, so deleting the folder runs in
the repo's folder in shots once removes them. The cap does delete the old
pictures, which no build asks for again.

The shots checker that builds is built with has a boards version, a capture
version for each platform and a comparison version, which `builds shots
version` prints. The boards version is a hash of the files that draw a board,
the boards library's files among them, and the versions of the packages the
checker uses. A platform's capture version is a hash of those and of the files
that take only that platform's shots: the harness sources the checker holds
for mac or for android and the file that lists them, and for web the file that
takes a page's shots in Chrome. The comparison version is a hash of the files
that compare a shot with its board and write the findings and the report, with
the boards library's files and the same package versions
(scripts/builds/build_source.rs lists the files each version reads). A change
to builds alone keeps every version, and so does a change to a test file or
test module, to the comments or layout of a Rust file, to a line of a Kotlin or
Swift harness that holds only a `//` comment (in a file that opens no block
comment or multi-line string), to what builds asks the checker outside a run
(library.rs) or to the shots checker's command line (the subcommands and their
arguments): every stored shot, board picture and run stays valid. builds keys the board pictures
by the boards version, the shots and their element lists by their platform's
capture version, and the findings by that capture version and the comparison
version.

A board whose mono stack names "SF Mono" (bae's does) draws that family. The
Mac installs its mono system font only as the hidden family ".SF NS Mono",
which Chrome cannot name, so without help Chrome draws the stack in Menlo,
7.225 pt a character against the app's 7.43. The Mac ships the SF Mono family
inside Terminal.app
(/System/Applications/Utilities/Terminal.app/Contents/Resources/Fonts). The
shots renderer and the dashboard's board and preview pages add `@font-face`
rules for each SF Mono file there to the design system's tokens.css, and serve
the files under /fonts/sf-mono/ (the dashboard with
Access-Control-Allow-Origin, since its frames have no origin), reading them
from the Mac when a page asks. The repo keeps no copy of the SF Mono files
(it keeps the Roboto, Inter and JetBrains Mono files that the shots checker
serves in place of Google Fonts), and the
tokens.css that builds writes and publishes has no such rule. A host that is
not a Mac has no such folder, adds no rule and draws the next family of the
stack; on a Mac, a folder that is gone, or lacks or cannot read one of the
files, fails the drawing and names it. The page that `builds
design render` prints is a file, which cannot load the SF Mono files (their
URLs are server paths), so it draws the next family of the stack.

The checker compares the colours of an element only where the element's own
pixels show. When a later element of the same list, such as a sheet, popover
or scrim, is not part of an element and overlaps its box by more than the
box-edge tolerance in each direction, some pixels in that box are the covering
view's and a glyph there may be cut. On Android the shots read each window (a
menu or a dialog, a tree of its own) before the page it opens over, the outer
window before the windows inside it: a window covers the page's texts wherever
the list holds it, a later window covers an earlier one, and the page, lying
under every window, covers none of theirs. In each case the checker reports
no colour finding for the element: no background, glyph colour or foreground
colour difference, and no finding that it found no measurable glyph colour.
It checks the element's presence, words, box and font as for any other
element. The Android harness writes no window role into a shot's list, so on
Android only the board's list says what covers a text. A Mac board's modal has
no element of its own, so the board reader records what the page draws over
each element (`cover` in the element list, absent when nothing): after it
measures the element's box it asks the page which element is on top at five
points of the visible part, and the element is covered when one of them is an
element inside neither the element nor around it. It marks an element a sheet
clips partly the same way. The page answers only for points inside its
viewport, so the reader scrolls a point beyond it to the middle of the
viewport, asks, and scrolls back; an element with a point the page still does
not answer for (a page that cannot scroll), and no point covered, is recorded
untested. An element
whose own style turns pointer events off is asked with them on for the moment.
The checker reports no colour finding for a board element recorded covered or
untested, on any platform, and writes a note naming the element and which of
the two it was.

Android's native text rounds each glyph advance to a whole pixel, so a line the
app draws is up to half a pixel off for each glyph against the board's
fractional advances (167.66 px against 169.0 for "Your music, everywhere" at 16
px), and the error adds up along a line and across the chips of a row. On the
android lane the checker lets each glyph set a width and a place off by half a
pixel: the width of an element with a label (a text, or a chip a label sizes)
may differ by that for the glyphs of its label, and its left edge may sit off by that for the
glyphs of the labels before it on its line and its own, besides the box-edge
tolerance. A text whose width differs by that much compares its left edge as a
text of the same width does. The mac lane keeps the box-edge tolerance alone.

The checker measures a text's glyph colour from the brightest pixels it
draws, and thin glyphs (the Mac's 11.5 pt years) have strokes under a pixel
wide, so no pixel shows the colour in full: three years drawn in #6A6A7A
measured #61616F, #575765 and #5B5B69. When one side's glyph colour is not the
colour of at least a quarter of that side's foreground pixels (within one step
a channel), and it lies on the line from the side's background to the other
side's colour, 0.7 of the way or more and within the colour tolerance, the
checker takes it as the other side's colour with partial coverage and reports
no difference. A colour that fills its strokes, or lies off that line or below
0.7, still differs.

The checker reads a text's place from its box, and a platform's text box can
span its container: the Mac's window title is the whole title bar. A shot text
box that is wider than the board's text box and holds it on every side (each
edge within the box-edge tolerance), with the same middle height within that
tolerance, puts the text where the board does, so the checker reports no move
or height difference for it. A box that is not wider, or that does not hold
the board's box or has another middle, still reports them.

The checker estimates the offset of the shot's frame from the board's as the
median offset of the matched pairs' top-left corners. A text box that is not
as wide as its pair, within the box-edge tolerance, adds its vertical offset
and its horizontal one only when no other pair gives a horizontal offset,
because a wrapped line and a line that spans its container sit in their boxes
by alignment, and the boxes' left edges differ while the text does not move.

A change to the comparison alone (a tolerance, the sentence of a finding, the
report page) changes only the comparison version, so the next shots check
takes no shot and builds no app for it. When builds has the run of a commit
under the current capture version and no run under the current comparison
version, the lookup of that run (`builds app-build --shots`, `builds shots
findings`, and the lookup of a merge base's run below) runs the installed
builds' `builds shots recheck` over the cached report, caches the findings as
the run of the current comparison version, and prints one line that says so.
The recheck links to the source run's pictures and writes every finding to
the cached text and findings.json. Rechecks publish their findings only in
those files. Builds uses the source run's verdict when app-build reuses the
comparison. When a cached recheck exits with a different status from its
failed source comparison, app-build reports the source failure.
A change to a file that takes only one platform's
shots changes that platform's capture version alone, so the other platforms'
shots and runs and every board picture stay valid. A change to another file of
the capture, to a file the capture and the comparison both read, or to a
package the checker builds from changes the boards version and every capture
version, and then a run takes its shots, draws its boards and builds the app
again. Each run's findings.json names both versions, and
builds caches no run whose findings.json names other versions. A run that died
before it made findings caches nothing. A failed run also caches nothing when
its output says the host kept it from taking a shot: the harness got no shot
display, another app kept the focus, or Xcode or UI automation did not start.
The lane stops at that run's step.
The cache is build output on the build volume: builds holds each repo's folder
in shots under its cap, deletes the runs and pictures that agents used least
recently first (DISK), and makes a deleted run again when an agent asks for it.

Beside the runs, builds caches each repo's board pictures in
/Volumes/Builds/shots/<repo>/pictures/boards/, as <board hash>.png with its
element list <board hash>.json. A board hash is the hash of everything the
board's picture depends on: the board's file and the parts it mounts (for a
component shot, the preview page and the shot's name), its frame on the
canvas, the design system's built files, the canvas runtime copy, the copies
of React, the pinned Chrome, the boards version of the shots checker, and the
shots-unshot, shots-preview, shots-slot, shots-glyph, shots-window and
shots-body-class lines. app-build passes the folder to each shots run
on this Mac (`run --pictures`), and the run draws only the boards whose hash
the folder lacks and adds each new drawing to it, so builds draws a board
once for its inputs. Beside each board's picture in a run's boards folder,
the shots program writes the board hash as `<scene>.hash`, and the run's
findings.json records it by scene (`boards`), so that builds can tell whether
two runs of a scene drew the same board (`builds shots findings`).
`builds shots draws` and `states` keep a shared board and a component's
preview page in the same folder by the same kind of hash, each with a file
`<hash>.instances.json` that holds the components the page draws (alone, for
a page `states` read and drew no picture of); the cap deletes it with its
picture.

The same folder caches the app's shots by the lane's app source tree, in
pictures/<platform>/<app tree>/, where <app tree> is a hash of the lane's
environment, of its platform's capture version and of the lane's app source
tree: a hash of the git objects, at the commit,
of each path the `on` lines name for a step of the lane, of .app-build, and
of the Rust the app builds from: every file of each crate whose folder an
`on` line of the lane matches or that a matched script builds with `-p
<crate>`, of every workspace crate those depend on (from the manifests at
the commit), and of Cargo.toml, Cargo.lock, rust-toolchain(.toml) and .cargo/.
app-build passes that id to each shots run on this Mac (`run
--app-tree`), so the one id means everything that draws the shots. When the folder caches every shot the run selects for that
tree, the run takes the shots from it and runs no capture command;
otherwise it captures them and caches them there. A commit that changes no
path of the lane's app takes no shot again. Once a run has cached every shot
a prefix selects, the shots checker marks the prefix taken for the tree (and
whether the run took the shots shown in a window). When an app-build asks a
lane only for shots, no changed path needs a step of the lane, and the
folder holds a mark for each prefix (a mark of mac. covers mac.welcome.),
the lane runs no step: it checks out the commit and runs the shots line with
--no-capture, which takes every shot from the folder and fails rather than
capture from an app nobody built. The output says which lanes build nothing
and why.

A lane with two or more --shots prefixes takes the shots of all of them once:
before the runs of the prefixes it runs a "capture shots <prefixes>" step, the
lane's `shots` line with one `--select <prefix>` for each prefix (a line whose
{select} stands after a flag, or beside other text, as `--select={select}`) and
--capture-only, which takes every selected shot into the picture folder, marks
each prefix taken and ends without drawing boards or comparing. Each prefix then
runs with --no-capture and takes its shots from the folder, so the app's capture
(Gradle, xcodebuild) starts once for the lane, not once for each prefix. The
capture step uses the strongest window access any of its prefixes needs,
and its time limit counts the scenes of every prefix; the prefix runs
open no window. A capture step that fails fails the build with its output, and
a prefix run that finds a shot missing in the folder fails as --no-capture does.
A lane with one prefix runs that prefix alone, as before. The merge base's runs
(below) are made the same way, and its capture step passes no --base. The steps
are recorded as "capture shots ..." and "shots <prefix>". For a shots run on a host,
app-build copies the board pictures and the shots cached for the lane's app
tree to a temporary folder on the host, passes that folder to the run, and
afterwards moves the pictures the run added into the folder here.

The key is the lane's whole app tree, not one key for each shot, on Mac and
Android alike: a commit that changes any file of the lane's app retakes
every shot the lane selects. builds does not narrow it to the files a shot is
drawn from, because the compilers' dependency output cannot say so. Swift's
`-emit-dependencies` .d file of each source lists every source of the module
and the SDK interfaces, so it holds no per-shot set. The .swiftdeps files
are the incremental build's binary record of declaration names each file
provides and uses: they name types of another module (BaeKit) only by
mangled name, and they cannot see what a shot reads when it runs
(resources, strings, assets). A key built on them could reuse a shot that
should be taken again, which is worse than taking it again. builds reads no
such record from Kotlin, so Android keeps the lane key too.

A shots run of a commit that origin/main lacks compares with the run of its
merge base with origin/main: builds passes the findings.json of that run to
the `shots` line as --before, and the run fails only on the pairs it makes
worse, a pair with a finding that run lacks for it, and lists the pairs whose
findings the merge base's run has too. A pair the merge base's run did not
check, because the branch adds its scene, has no run to compare with: the run
lists its findings as first observations and does not fail on them. A scene
that has no board, or whose capture wrote no picture, still fails. A pair the merge base's run tried and captured no usable
shot of, because the capture crashed or failed first, has no picture to
compare with: the run reports it as a pair the base never rendered, with its
findings, and does not fail on it. `builds land` prints those pairs and
their counts. A pair the merge base's run rendered still fails when the
branch adds findings to it, except a finding about the state, reading
order or role of an element that run reported as missing from the shot or
extra in it: that run could not compare the element, so the branch shows
the finding for the first time. The same holds for a finding on an element
that neither the base run's board nor its shot held at all, such as a row its
shot ended above, which the branch brings into view (findings.json lists the
elements each pair compared, under `seen`). The run it compares with is the newest cached run of the
merge base in the same lane and environment, by the same shots versions, whose prefix starts
the run's own (a run of mac. stands in for a run of mac.welcome.), and whose
report holds findings.json. When no one run covers the prefix, and the runs
of narrower prefixes (made in that environment by those versions) together
tried every shot that the merge base declares under it, builds saves them as
the run of the prefix, with each scene from the newest run that tried it and
with no report page. When builds has none cached, the lane's process
that builds the branch builds the merge base first, in the same app checkout
and the same turn of the lane's queue: it takes a lock on the lane's runs of
that merge base (the file base-run-<lane>-<commit>.lock in the repo's folder
on the build volume), checks out the merge base, runs the lane's `needs`
steps there (none when the picture folder caches every shot the runs take for
the merge base's app tree), runs the prefixes it lacks with `--base`, caches
their findings, and then checks out the branch and builds it as usual. A build
that finds the run being made waits for the lock, then finds the run cached
and builds none. A prefix that starts no shot declared at the merge base needs
no run there: the branch's run compares it with an empty run
(`--empty-before`), so every scene it selects is new and lists its findings
without failing on them. The merge base's run compares with nothing and fails no pair
with findings, since those findings are what the branch's run compares with,
and it lists them as such. Its findings are cached before the branch builds;
only a step or a shots run that fails without failing pairs, as when it cannot
render, fails the build, with that run's output. builds never asks a branch to
rebase for a comparison: a branch that starts behind origin/main's tip
compares with the run of its own merge base. A run of a commit on origin/main
compares with nothing, so its pairs' findings fail it. A lane's process
(`--lane`) that names no step runs its picks against the checkout as it is, so
it builds no merge base: it fails, naming the command that makes the run it
lacks. A shots check's "before" side is read from the cached runs, never
built again.

WEB PICTURES

An agent sees a web page it changes, such as a site on its dev server, in a
picture that builds takes.

  {web picture}
                              picture the page at <url> on this Mac and print
                              the path of the PNG

The URL is an http or https URL, and builds refuses any other. The window is
--width CSS pixels wide (1440 without it) and 900 high, at two pixels per CSS
pixel, so the PNG is 2880 by 1800 without either flag. With --full-page the
PNG shows the page's whole height, and the window the page loads in stays 900
high. A page that no server answers, or that Chrome does not finish in 120
seconds, fails the command, which names the URL. A server's error page, such
as a 404, is a page like any other.

builds pictures the page as a person sees it once the page has settled, so a
page that fades its content in shows the content. Once the page's load event
has fired and its fonts have loaded, builds waits until no CSS animation or
transition of the page is running, one that waits out its delay included, and
the picture has stayed the same for 500 milliseconds. When a page has not
settled after 10 seconds, such as a page that animates forever, builds
pictures the page as it is then. The command prints that the page had not
settled, then the PNG's path, and succeeds.

builds draws the page with the Chrome a shots run pins, which it keeps in the
build volume's caches, with a new profile folder in the run's temporary folder.
The page takes one of the host's Chrome slots (APP BUILDS). The command takes
no app checkout, no place in a lane's queue and no window lock: of what an app
build waits for, the command takes only that Chrome slot.

The command waits as a shots step on this Mac waits (APP BUILDS). While this
Mac's screen is locked or a system alert is in front of every app, it prints
"waiting for this Mac to show windows, since <reason>" and takes the picture
once the reason ends. A closed lid on this Mac holds no shots step and no
picture. While Chrome prints no address within its 120 seconds, it prints
"waiting for Chrome to start on this Mac" with why, starts Chrome again every
minute and takes the picture once Chrome starts. `builds health` lists no
waiting picture.

The pictures are in the folder web-pictures on the build volume (DISK).


HOSTS

builds can run jobs on other machines, its hosts: other Macs, and Linux
machines that run Debian or Ubuntu, such as a rented server or a cloud
instance. This Mac is always one, named local. A host keeps its clone of each
repo at ~/dev/<repo>, its worktrees at ~/dev/<repo>-worktrees/, and its build
roots in /Volumes/Builds when it is a Mac with that volume, else in
~/builds-root.noindex on a Mac and ~/builds-root on Linux. A Linux host takes
`builds cargo` jobs, except a job that builds a package only a Mac builds
(CARGO). App builds run only on Macs, and `builds remote run` picks only Macs.

To add a Linux host, give it a user that this Mac reaches over ssh by key and
that may run sudo, then run `builds host add <name> <user>@<address>` and,
with a person at this terminal to type the sudo password, `builds host setup
<name>`. Setup installs everything else the host needs (below).

A host refuses jobs when it answers but cannot start one. builds finds this
two ways: a probe, which asks the host for its load and disk, also runs git
there, in the shell a job's push reaches, and git fails (as it does on a Mac
whose Xcode license is not accepted); or sending a job's commit or claiming a
worktree for it fails there. builds records each host that refuses jobs in
the folder host-refusals beside the file `hosts`, with when it first refused
and what it said, and every pick passes over it. `builds health` lists each
recorded host under "needs action", and the dashboard's load card for the host
says "refuses jobs" in place of its core count when git fails there. Fix the cause on the host; the next probe
that finds the host answering with git running removes the record, and builds
uses the host again. builds probes this Mac with the script it runs on every
other host, so this Mac also refuses jobs when git fails here. `builds host
list` probes every host, and so does every
`builds cargo` and `builds remote run` that picks one. A host whose Xcode
cannot start, or whose UI tests timed out turning on automation mode, refuses
mac app builds only (APP BUILDS).

No Mac that builds uses goes to idle sleep while builds works on it or for
it. Each builds process that runs work holds macOS's power assertion
PreventUserIdleSystemSleep from its start to its end, which keeps the Mac
from sleeping when nobody uses it, on battery or on power, and `pmset -g
assertions` lists it under builds' name with the command. Those processes are
`builds agent run` and `resume`, which keep running while their agent does,
`cargo`, `lake`, `lock`, `app-build`, `build-app`, `remote run` and `remote
step`, a `shots` command that runs the checker, `review` in each form that
runs reviewers, `land`, `health`, `checks run`, `item take`, `new`, `setup`,
`app-checkout`, `app-clone`, `prune`, `install`, `host` and `tool`. A command
that only reads or waits, such as `review wait` or `judge listen`, holds
none, and neither does the dashboard, whose own runs are builds processes
that do. When builds runs a command on a host that is a Mac, a builds there
holds the assertion until the command ends, and the command does not run when
it cannot.

builds lists in one table each program it runs that reads or changes more
of the machine than the files builds names: ssh, claude, codex, launchctl,
systemctl, ioreg, system_profiler, lsappinfo, pmset, caffeinate, defaults,
osascript, xcodebuild, xcrun, lsof, pgrep and sudo. builds finds each by name on PATH.
When BUILDS_SYSTEM names a folder, as builds' own tests set it, builds runs
each program from that folder instead, refuses to run one the folder lacks
and names it, and writes each power assertion it would take and release to
the file `power` in the folder. A script that builds runs on a host runs the
same programs.

While builds works on a host over ssh, in a lane's app checkout there or in
a job of `builds remote run` or `builds cargo`, it also keeps this Mac awake
with NetworkClientActive, which keeps it awake through a maintenance wake
while it runs on power. A Mac that sleeps answers nothing on its
connections, and the host ends a connection that gets no answer for about
twenty seconds, which stops the command there. Neither assertion keeps a Mac
on battery awake once its lid closes or through a maintenance wake. When ssh to a host exits 255, the status it gives
when its connection fails, builds reads the power log (`pmset -g log`) of
this Mac and of the host, and says on stderr each sleep either one recorded
while the command ran: when it began, how long it lasted, the reason macOS
gave, such as Clamshell Sleep or Idle Sleep, and whether the Mac ran on
battery.

A Mac runs UI tests with nobody at its screen only with three settings on.
Without them, XCTest asks for a password on its screen, or says "Timed out
while enabling automation mode" (and `automationmodetool` says the device
requires user authentication), and the test class runs no tests. Each
setting has a check that only reads and a command that turns it on:

  - Automation Mode without a password: `automationmodetool` says the device
    does not require authentication;
    `sudo automationmodetool enable-automationmode-without-authentication`
  - developer mode: `DevToolsSecurity -status` says enabled;
    `sudo DevToolsSecurity -enable`
  - the user in the _developer group:
    `dseditgroup -o checkmember -m <user> _developer` says yes;
    `sudo dseditgroup -o edit -a <user> -t user _developer`

`builds host setup` checks the three on the host and runs the commands for
the ones that are off through sudo there when a person is at this terminal to
type the password (over `ssh -t`); with nobody at the terminal it fails and
names the commands to run on the host. `builds health` checks them on every
host, this Mac included, and lists each host that lacks one under "needs
action" with the commands.

Spotlight's indexer reads every file a build writes where it indexes, so
builds keeps Spotlight off each Mac's build root. Spotlight skips a folder
whose name ends in .noindex, so a host's build root in its home folder,
~/builds-root.noindex, needs nothing more. A .metadata_never_index file in a
folder does not keep Spotlight out. A build volume's indexing is a setting of
the whole volume: `mdutil -s /Volumes/Builds` reads it, and
`sudo mdutil -i off /Volumes/Builds` turns it off. `builds host setup` checks
it on the host and runs that command through sudo there when a person is at
this terminal; with nobody at the terminal it fails and names the command.
builds never runs mdutil on a build root that is a folder, because the
folder's volume holds other files. `builds status` says whether Spotlight
indexes the build root.

fseventsd keeps a history of each volume's file changes, and works for each
program that follows a folder there, which kept it at a core while agents
built. builds keeps the build volume out of both. Nothing in builds follows
the build volume. Instead, each builds command that changes a build root
measures the folders of each root it changed when it ends, whether it passed
or failed, writes their sizes to
/Volumes/Builds/.builds-daemon/sizes/<repo>/<checkout>.json and tells the
daemon of them all at once. A command changes a root when it makes the root,
builds or clones into it, checks out another commit in its checkout, adds
its checkout to a lane or takes it out, deletes a folder in it, or removes
it. The dashboard and `builds status` read those records, and measure a
folder that has none once. A write that no builds command made, such as a
cargo run by hand, shows in a size only after the next builds command that
changed the root. The volume's own setting stops the history: a
file named no_log in /Volumes/Builds/.fseventsd, which macOS reads when it
mounts the volume. The file does not stop live events to a program that
follows a folder there. Only root reads that folder, so builds asks FSEvents
for the UUID of the volume's history, which a volume with a history has and
one with no_log has not. `builds host setup local` creates the file through
sudo when a person is at the terminal, and `builds health` lists the volume
under "needs action" while it keeps a history, with the commands: `sudo touch
/Volumes/Builds/.fseventsd/no_log`, then, with the dashboard and every build
stopped, `diskutil unmount /Volumes/Builds` and `diskutil mount <the
volume's device>` (`df /Volumes/Builds` names it).

DISK

builds keeps disk use bounded: it deletes the build copies and builds that no
build uses, deletes a folder that is still over its cap, and keeps a free-space
floor on the volume. `setup`, which runs before every hook and build, and
`prune` do all of this, and `builds cargo` deletes the copies a build replaced
as it exits. The dashboard runs `builds prune` every 6 hours, and `builds
health` says when a prune last finished. Builds keeps folders its open-file
scan finds in use and folders whose checkout guard a build holds. A process
outside builds can open a file after that scan. Builds warns during a build
if cleanup cannot move a folder to the trash. An explicit prune reports a
failed move and exits with an error. If removal fails after a move to the
build volume's trash, the next prune can remove that folder from the trash.

Unused build copies. Cargo names each unit it builds (one crate target, for one
profile, target and feature set) by a hash of everything that build depends on,
so every dependency bump builds a new copy of each unit above it, and the old
copy stays. In each cargo folder (target, target-macos, ...) builds deletes
every file of a unit that no build used for BUILDS_UNUSED_DAYS days (default
3), and of a unit a newer copy replaced: a copy of the same package and target,
mode, features and profile, built from other sources, that a build used after
the unit's last use. Two copies come from other sources when another compiler
built them, or when each was built against a source folder or version of a
package that the other was not built against (another version or git revision
of a dependency, or a workspace crate's new version). A copy that was built
against a further version of a package beside all the other's, as a feature
that pulls one in does, comes from the same sources. builds reads each unit's
package version from cargo's report of a `builds cargo` build and keeps it in
the unit's fingerprint folder. For a unit that no such build used, builds
compares only the compiler and the source folders. Two different units can come
from the same sources: cargo builds some, such as a build script's runs that
differ only in debug info, whose records it writes alike. A unit is also
replaced when a newer build of its package (such as the library beside a test
binary) was built against another copy, from other sources, of something the
unit was built against. Copies built from the same sources for another package
selection or feature set (`-p x` against the workspace, or one package with and
without its test features) stay side by side, and so does whatever a unit that
stays was built against. A unit's last use is the last build that reported it,
rebuilt or up to date; a unit that no recorded build used counts as used when
cargo last built it.

Incremental folders. builds deletes the incremental folders that only deleted
units used, and every incremental folder that nothing wrote anywhere inside
for BUILDS_INCREMENTAL_HOURS hours (default 6), in every checkout: main's
builds compile incrementally, and in the others a repo's lint wrapper may keep
an incremental folder for the crates it lints (bae's
scripts/clippy-rustc-wrapper.sh). The build folder's cap bounds the rest.

Object files. In every checkout, builds deletes the object files that no build
or debugger reads: an rlib's loose objects, and the objects a binary's debug
map doesn't name, which each incremental rebuild leaves behind under new names.
This needs split-debuginfo "unpacked", macOS's default; keep it, since packed
builds slower and larger, and off drops file and line from the top crate's
frames.

Separate builds inside one folder. A folder is aged by its newest write, so a
stale build beside a live one (last week's Xcode tree beside today's) would
never age out. builds finds the builds inside each folder and deletes each one
no build used for BUILDS_UNUSED_DAYS days, in main and the app checkouts too,
but keeps a build a process holds a file in and, in main and the app checkouts,
one a `keep` line names. It recognizes an Xcode tree (info.plist beside Logs,
and Build or ModuleCache.noindex, up to two levels below the folder) and a
SwiftPM <triple>/debug or <triple>/release folder in a .build that holds
workspace-state.json. A build's last use is the newest write inside it, since
xcodebuild and `swift build` write even when everything is up to date. dotnet's
and Gradle's folders are not split: an up-to-date `dotnet build` writes
nothing, and Gradle keeps no build per variant. `status` lists each build under
its folder with its last use (`status --json`: the folder's `trees`).

Builds and deletions never overlap. builds deletes a unit's files only while it
holds the checkout's guard (<build root>/.builds-cargo.lock) and cargo's lock
on that profile folder, both taken without waiting, and keeps any unit a
process holds a file of. `builds cargo` holds the guard, shared, from before
cargo starts until cargo has exited and its report is read, because cargo
decides which units are up to date before it runs anything and lets go of its
own lock before `cargo test` runs the tests. A build waits on the guard only
while a deletion holds it, a few seconds, and a build that starts after a
deletion rebuilds the unit, mostly from sccache.

Caps. A folder still over its cap is deleted whole (renamed into .trash,
removed in the background) and recreated empty, and the next build refills it,
mostly from sccache. A cap is about twice a fresh build of its folder. A
claimed worktree's folder is never deleted whole, since its agent is at work in
it: status shows it over its cap as "claimed, kept". Sizes, against caps and in
status, count each block once (`builds du`): cargo copies each library and
binary it builds for you out of its build copy's files as an APFS clone, which
du counts once per file, and rustc hard-links a build copy's files into
incremental/.

Free-space floor. Caps bound each folder, not the volume: a checkout with every
platform built takes 45-52 GB, and the build volume shares its APFS pool with
the main disk. So builds keeps a free-space floor of 30 GiB
(BUILDS_FREE_FLOOR_GIB), and frees space up to a target of the floor plus a
margin of 20 GiB (BUILDS_FLOOR_MARGIN_GIB), so that the next build's writes
don't take the volume under the floor again at once. `setup` starts deleting
when the volume has less free than the floor, and `prune` starts as soon as
the volume has less free than the target. Each finishes emptying the trash,
then deletes the build roots of checkouts that are gone, DerivedData's idle
entries, then the incremental folders nothing wrote inside for 60 minutes in
every checkout (claimed ones, main and the app checkouts included), and then
the whole folders that nothing wrote to for 30 minutes in the side worktrees no
agent claims, in a host's job worktrees no job claims and, but for the
folders its own lane builds into, in every app checkout, never in main. Each
kind goes least recently written first, until the volume has the target free. builds says what it deletes and why, and
a last line gives the space it freed and the free space after. If builds can't
reach the floor, it warns, naming the free space and the biggest folders, and
the build goes on: whoever runs the agents stops starting more. Only under the
hard floor of 10 GiB (BUILDS_HARD_FLOOR_GIB) does setup fail, before the build
starts, rather than let the build run out of space halfway. These deletions
never touch a shared cache.

DerivedData. bae passes -derivedDataPath into a .build folder in the checkout
(scripts/xcode-trees.sh is its one definition, and a pre-commit check refuses
the flag anywhere else), so DerivedData holds only what one-off xcodebuild runs
(-showBuildSettings, package resolves) and the Xcode app write: one
<project>-<hash> entry per project path, mostly SwiftPM checkouts of about 3
GB. It is one disposable cache with a 15 GiB cap. `setup` and `prune` delete its
entries, least recently written first, while it is over the cap; `prune` also
deletes entries nothing wrote to for a day, and the floor deletes its idle
entries first. Every deletion skips an entry written in the last 30 minutes or
one a process holds a file in.

Shared caches. Each tool keeps its downloads (sccache, its compiler outputs) in
caches/<name>, linked from where the tool looks, with a cap each:

  gradle   8 GiB  ~/.gradle
  npm      1 GiB  ~/.npm
  nuget    6 GiB  ~/.nuget
  swiftpm  3 GiB  ~/Library/Caches/org.swift.swiftpm
  sccache 50 GiB  ~/Library/Caches/Mozilla.sccache
  xcode-cas 10 GiB  no link: builds names the folder to Xcode (APP BUILDS)

`setup` and `prune` replace a cache over its cap once nothing has written to
it for 30 minutes and no process holds a file in it. Builds prepares a
replacement with the cache's settings files (gradle.properties, Gradle's init
scripts, NuGet.Config), then exchanges it with the live folder in one step.
If preparation or exchange fails, the live folder and its settings stay in
place. Nothing else deletes a cache: every checkout would download it all
again, and a SwiftPM fetch cut off halfway corrupts its cache. sccache keeps
its own cache under its cap; builds only shows it.

Shots runs. The folder shots caches each repo's shots runs, board pictures
and app shots (APP BUILDS), with a cap of 2 GiB for each repo's folder.
`setup` and `prune` delete a repo's whole runs, board pictures and app
source trees' shots while its folder is over the cap, least recently used
first. A run's last use is when it ended or when builds last read it (to
print its findings or to compare a branch's run with it). A board picture's
is when a run last drew or took it. An app source tree's shots of one
platform go together, and their last use is when a run last captured or took
one of them. Whatever a run used in the last 30 minutes stays. A run that a
branch with commits origin/main lacks still needs stays however long ago it
was used: the run of the commit of any of the branch's app builds that ran
the prefix, and the run of that commit's merge base with origin/main, which
the build compared with. Only runs that no such branch names are deleted.
When the runs that branches need take more than the cap, `prune` keeps them
all, and `health` says so and names the branches. `setup` and
`prune` also delete each staging folder and half-written picture file that a
run which died left behind, and each folder the deleted runs left empty. A
run fills its staging folder at the top of the folder shots and makes the
folders of its key only when it puts the run in place, so a run that stops,
or that builds does not keep, leaves no folder under runs. For each folder
they clean in shots, a repo's or shots itself, they print one line, however
many files they delete there: the number of folders and files they deleted, or
on a dry run would delete, the space that freed and, when the cap made them
delete, what the folder held and its cap.
They delete nothing in the folder while a shots step reads or writes it,
which a step on this Mac does while it runs and a step on a host does while
builds copies a before run and pictures to the host and the new pictures
back. A lane also keeps the pictures of its app tree from before it checks
which pictures the folder has until its last comparison of that tree. When
a reader or writer accesses the cache during a prune pass, builds skips the
remaining deletions. A later prune measures the cache again.
Before deleting folders, builds checks which files other processes hold open.
Builds reports an error if it cannot read a shots run's last-use time.
Each host keeps the board pictures it was sent in
~/.cache/builds-pictures/<repo>/boards and builds sends it only the ones it
lacks, deleting the ones this Mac no longer holds only when no other step has
a picture folder there that changed within a day; a step brings back only the
board pictures it made. `status` shows each repo's folder's
size against the cap.

Review texts. The folder review-texts holds what each review run sent its
reviewers and what they answered, one folder per run, with a cap of 2 GiB; the
project's store holds only the findings, verdicts and settles, and the hash of
each text. `setup` and `prune` delete whole runs' texts while the folder is
over its cap, least recently used first, as they do shots runs: a run's last
use is when it was recorded or when builds last read a text of it, and a run
used in the last 30 minutes stays. Builds reports an error if a published run
has no file recording its last use. Once a run's texts are gone, a command
that needs one (`builds review audit`, `propose`) says so and goes on to the next.
`status` shows the folder's size against its cap. What `setup` and `prune`
delete there they print in one line, as for a folder in shots.

Web pictures. The folder web-pictures holds the pictures of `builds web
picture`, one folder per picture, with a cap of 1 GiB. `setup` and `prune`
delete whole pictures while the folder is over its cap, the oldest first, and
keep a picture taken in the last 30 minutes. Builds reports an error if a
picture's folder has no page.png. `status` shows the folder's size against its
cap.

When xcodebuild fails with "Couldn't check out revision" or "file not found" on
a SwiftPM dependency (often Sparkle), its cache is corrupt: disconnect any VPN
(a VPN can cut fetches short), delete the app's Xcode build trees and its
SourcePackages folder and ~/Library/Caches/org.swift.swiftpm/repositories/
<dependency>*, and run the repo's build script again. Every script that
resolves packages and every script that builds after it must pass the same
xcodebuild flags, -derivedDataPath above all, or the packages land where the
later build can't find them.

iOS simulators. Keep at most one iOS simulator runtime and one simulator device
installed, since each runtime takes 8 to 20 GB of the disk the builds share.
When you install a new runtime, delete the old runtime and its devices (`xcrun
simctl runtime list`, `xcrun simctl runtime delete`, `xcrun simctl delete`).

Cargo's git checkouts. `setup` and `prune` delete each checkout in
~/.cargo/git/checkouts that no live checkout's Cargo.lock pins, holding cargo's
package cache locks. The git databases in ~/.cargo/git/db stay.

Installed tools. A repo's script may install a tool once per version into a
folder in the user's cache home, for every checkout on the Mac to share (bae's
ownership checker, about 10 MB per coven revision), and a `.build-dirs`
`installed` line names the folder and the file that names the version a
checkout runs. `setup` and `prune` delete each version in the folder whose name
no live checkout's file contains, reading the file in every live checkout,
whether or not its own `.build-dirs` has the line. An entry whose name starts
with a dot is one a script is still installing, and `setup` and `prune` leave
it. When builds cannot read a checkout's `.build-dirs`, the folder or one of
the files, it deletes nothing there and says why. When no live checkout has
the file a line names, builds deletes nothing in that folder and says so.

Build output in the temporary folders. A build pointed at /private/tmp or the
user's temporary folder writes 5-14 GB there that nothing else deletes. `setup`
and `prune` delete each cargo target, DerivedData or SwiftPM folder there, up
to four levels deep, that nothing wrote to for 30 minutes and no process holds
a file in; `status` lists them. They skip /private/tmp's claude-* (Claude Code
sessions' scratch, whose entries go three days after the session's last
change), com.apple.* and tmux-* (live sockets), and anything the user doesn't
own. A program may delete a folder there while `setup` or `prune` works: they
say nothing of a folder that is gone when they come to delete it, and go on.
builds' tests set BUILDS_TEMP to a folder of their own, which takes the
place of /private/tmp and the user's temporary folder, and builds then deletes
nothing in a TMPDIR outside it and the build volume.

Agent registrations. `builds agent start` registers each agent in
<the lists folder's parent>/agents/<session>/, and only a command that an
agent of that session runs reads it. `builds rules-on-edit` keeps the rules it
gave each agent there too. `prune` (not `setup`) deletes each
session's folder once Claude Code's record of running sessions (~/.claude/
sessions) no longer names the session. When builds cannot read that record, it
deletes none and says so.

Never run `cargo sweep --time` or `--maxsize`: APFS doesn't refresh access
times, so sweep deletes the builds needed next. `cargo sweep --installed` after
a toolchain upgrade is fine.

COMMIT CHECKS

A repo's `.checks` at its root declares the checks its pre-commit hook runs,
one per line: `<kind> <name> <paths> <program> [<args>...]`. The kinds:

  check   a static check
  fix     a formatter; the files it changed are staged again
  whole   a check that reads the whole tree: the hook runs it when a path
          matches, and `builds land` runs it on every landing, since two
          commits that each pass the hook can break it together. It names
          neither {files} nor {crates}
  test    a checker's own test; CI runs it, never the hook

paths is a comma-separated list of globs over repo-relative paths: `*` stays
inside one path segment, `**` is any number of segments, and a glob with no `/`
matches the file name anywhere. The program is not run by a shell. As a whole
argument, {files} is the matching staged files that still exist, and {crates}
is `-p <crate>` for each workspace crate holding one (a root Cargo.toml,
clippy.toml or .clippy.toml counts as every crate, since each configures the
workspace's lints, and so do a root rust-toolchain.toml or rust-toolchain,
which picks the compiler and the clippy of every crate, and .cargo/config.toml
or .cargo/config, cargo's settings for every crate; a root
Cargo.lock counts as each crate whose resolved dependencies changed against
HEAD, or against the commit `builds checks tests --since` names: its own lock
entry or one it depends on at any depth); a check with neither runs whole
whenever a matching file is staged. A glob written `every:<glob>` marks files
that configure the check of every crate, such as the sources of a lint driver
the line runs: a staged file it matches hands {crates} every crate, for that
line alone, and builds refuses the mark on a line that names no {crates}.

  {checks run #1}
                              what the pre-commit hook runs: the check and fix
                              lines the staged files match, from the repo root:
                              the fix lines first, one at a time in file order,
                              then every check line at the same time, since
                              the checks only read the tree the fixes left.
                              `builds checks run` prints each line's name, time
                              and result (with a failing line's output) in
                              that order, and the total time. Every line runs
                              even after one fails, and the exit status is
                              non-zero if any did. It
                              refuses before any line runs, naming each file,
                              when a staged file also has unstaged changes,
                              since the checks read the working tree;
                              unstaged changes to unstaged files are fine. It
                              records each run, a refused one as a failed run
                              with no checks, in the project's store: when,
                              repo, worktree, branch, the commit HEAD pointed
                              at when it started (its base), each staged file
                              (its change and lines added and removed), each
                              line (run with its time, its result and this
                              Mac's cores and one-minute load when it started,
                              or skipped), for a line that failed an excerpt
                              of its output (the lines from the first test
                              panic or compiler error, else the last lines)
                              and the staged files it was handed that its
                              output names, the planning time and the total. For
                              each check it sets BUILDS_HOOK_CHECK to the run's
                              start and the check's position, so a `builds
                              cargo` the check runs records which check started
                              it (CARGO), and the figures show where the check
                              ran: on the host of that cargo run with that
                              host's load, else on this Mac. `122.8s on local,
                              load 21/14` means the check took 122.8 seconds on
                              this Mac, whose one-minute load average was 21
                              on 14 cores. A run it can't
                              record says so on stderr and ends as the checks
                              decided; a repo in no project records nothing
  {checks run #2}
                              run the check and fix lines that the files the
                              branch changed since it left <rev> (git
                              merge-base <rev> HEAD) match, over those files
                              as HEAD has them, and leave HEAD, the index and
                              the files as they were, so an agent checks a
                              whole branch without moving HEAD. It refuses
                              before any line runs, naming each file, when the
                              working tree differs from HEAD in a file the
                              branch changed. A fix line that would change a
                              file fails, naming the file, and builds puts the
                              file's bytes back. Each line prints as for
                              `run`. builds records no range run, since the
                              record is of commits
  {checks whole}
                              run every `whole` line on the tree as it is (the
                              checks `builds land` runs on a landing), printing
                              each one's time and result, with a failing one's
                              output; the exit status is non-zero if any failed
  {checks stats}
                              read the recorded runs back, for the project of
                              the current repo unless --project names one,
                              each repo apart (or only --repo's): the passing
                              runs (every check passed) with their median and
                              slowest total; per check how often it passed and
                              was skipped, its median and slowest time over its
                              passes, and the median of its latest 10 passes
                              against the 10 before; the slowest passing runs
                              with their diffs; and each set of checks whose
                              newest passing run took over 45 seconds, the
                              hook's limit (until a newer run of that set
                              takes less), with where its slowest checks ran
                              and how loaded that host was, as the dashboard
                              shows beside each check's time in the runs over
                              the limit. Nothing counts failures. --since
                              counts runs from that local day on. --change
                              <rev> instead splits the runs of the repo that
                              has <rev> (refused when no repo has it or more
                              than one does, which --repo settles) by whether
                              their base contains <rev> (git merge-base
                              --is-ancestor, so a worktree on an old base after
                              the change landed counts as without), and prints
                              per check, on each side, the runs that ran it,
                              the median count of crates it was handed and its
                              median and slowest time. The dashboard shows the
                              same per repo and lists a set of checks over the
                              limit among the findings
  {checks list}
                              print what `run` would run, without running it
  {checks tests}
                              the test lines whose paths match the files
                              changed in <rev>..HEAD; --run runs them and fails
                              if any fails. A <rev> not in the history selects
                              every test, and says so
  {install-hook}              write the repo's pre-commit hook, a script that
                              runs `builds checks run`, in core.hooksPath when
                              it is set, else in the git common dir's hooks,
                              which worktrees share; it overwrites the file


WAITS

builds records how long agents wait on four kinds of work. `builds waits`
prints, and the dashboard's "waited today" figure opens, the time of each kind
per local day and per band of load per core, with each row's count, median and
total, so a person can see which kind of work agents wait on longest and how
load changes the wait for each kind. Every wait counts, whatever its result.
The kinds:

  commit hook      each `builds checks run`, passed or failed, from its start
                   to its last check's end, with this Mac's load when its
                   first check started (COMMIT CHECKS)
  test run         each `builds cargo test` and `builds cargo nextest` run
                   that no hook check started, from the start of `builds
                   cargo` to cargo's exit, with the load of the host that ran
                   cargo when builds picked it (CARGO). Days before builds
                   recorded every `builds cargo` run have no test runs
  app build queue  each lane run's wait in its lane's queue, a wait after a
                   takeover included, with the load of the checkout's host
                   when the run took the checkout (APP BUILDS)
  app build step   each step of a lane run, its test lines and shots runs
                   included, with the load its run recorded

Load per core is the one-minute load average over the host's cores, in four
bands: under 1, 1 to 2, 2 to 4, and 4 and over. A wait whose record holds no
load counts under "not recorded": a hook run from before builds kept each
check's starting load, an app build run from before builds kept its host's
load, or one whose host did not answer.

  {waits}
                              print the time of each kind of wait per local
                              day and per band of load per core, for the
                              project of the current checkout unless
                              --project names one: for each kind and day, a
                              row for all loads, then a row for each band;
                              --since counts waits from that local day on.
                              The dashboard shows the same for today and
                              yesterday


LANDING AND REVIEW

A branch's agent puts its commits on origin/main by running `builds land` in
the worktree whose branch holds them, once its work is done there. In a repo of
a project with lists, the agent first reviews the branch against
agent-instructions' rules with `builds review`, and the judge settles each
finding (`builds judge listen`). `builds help workflow` (REVIEW) says how an
agent reviews its branch and how the judge settles each finding, which files
each group reads in a later run, and how long a confirmed finding stays open.

Each branch's change has one review, which builds finds by its repo and its
key (by default the branch, such as `branch:work`) and which stays open until
the change lands. Branches of the same name in two repos are two changes, each
with its own review.
The review is a series of runs. builds records which run is the last review:
the run whose net change (`git diff` from the branch's common ancestor with
main to its head) the review has read. A later run asks only what the review
lacks: the groups that gave no answer (their reviewer failed), over the diff
they did not answer, and, in a new run that becomes the last review, the
changes since the last review (`builds help workflow`, REVIEW). The run asks
the groups that cover a changed path, the groups that hold an open confirmed
finding, over every changed file, whether or not their rules cover it, and,
when a commit message changed, each group that reads commit messages
(commit_text) and whose rules cover a path the branch changes. A group that
holds an open confirmed finding reads every change since the run that raised
it, with the finding: when a run read some of those changes without the
finding (the judge confirmed it later, for example), a run of that group alone
reads the changes since the last net change the group read with the finding,
even when nothing changed since the last review. A reviewer that holds an open
finding also reads the branch's commits, oldest first, each with its message
and the files it changes, so that a finding that asks for a change to go in a
commit of its own closes once a commit holds that change alone. A reviewer reads the commit
messages as one more file, named COMMIT_MESSAGE. Only groups whose rules judge
what a message says read the messages (in agent-instructions, the group
Commits and repo contents, whose rules ask whether the text is accurate).
When nothing is unread and a confirmed finding stays open, `builds review`
asks each group that holds one again, over the whole net change at the
branch's head, so that the group can close a finding that a commit fixed.
A finding that a review closes still counts as a true positive.
`builds review` refuses the run, naming the last review, when the review
lacks nothing, no confirmed finding is open and no closed finding goes back to
its group.

`builds review` checks code and whether text is accurate, never word choice,
grammar or style: it never asks a copy group (copy, below), whose rules judge
wording. In agent-instructions the copy group is Text people read. The person
reviews copy by hand, and may run the copy review (`builds review copy`),
which asks only the copy groups. No landing waits on the copy review.

builds finds the changes since the last review by replaying the net change
the last review read onto the branch's current common ancestor with main, in
a tree of git's own (`git merge-tree`, which checks nothing out), taking the
lines of that net change where main changed the same lines, and diffing that
tree against the branch's head. A file the replay cannot write (one side
deleted it, for example) shows its whole net change, and so does every file
when the repo no longer has the commits the last review read. The commit
messages the run reads are those the last review's net change did not hold.

The changes since the last review are the lines the branch adds or removes that
it did not add or remove at the last review, the lines it no longer changes,
and the commit messages it did not hold then. Main's commits that a
rebase brings in are not part of the changes, so a rebase that keeps every line
the branch adds and removes keeps its review, and a rebase that resolves a
conflict differently leaves only the resolution's lines to read. A reworded
message alone leaves only the changed messages to read, and dropping the commit
that held a confirmed finding's code closes the finding at the next review.
Dropping the commit that fixed a closed finding gives the finding back to its
group (below).

In a later run, each group that holds open findings reads every file that
changed since the last review, because the fix of a finding may be in any file.
Each other group reads the changed files its rules cover, except a file where a
group holds an open finding: only the groups that hold findings there read that
file. The run's report names each group that did not read a file, with the
files it did not read.

Each reviewer reads the changes since the last review, and raises findings
only on lines those changes add or remove. builds drops a finding whose code
sits only on the lines around them, which the diff shows for context: a later
run never flags a line that the fix did not change. The reviewer may read the
whole branch as it is now, for context. The reviewer also gets each open
confirmed finding of its group's rules, with its file, line, quoted code
and problem. The reviewer checks whether the branch still has each problem,
including fixes in other files, and gives each finding a verdict. Builds
records which run closed each fixed finding and prints the reviewer's reason
for keeping each other finding open. A closed finding goes back to its group
when the changes since the run its group last judged it change a path that the
diff of the closing run changed. For a finding on the commit messages, the
commit messages count as a path, and a diff changes them when it holds a commit
message that the earlier change did not hold. The group's reviewer gives the finding the
same verdict as an open one: `fixed` keeps it closed, and the run records that
it closed the finding again; still open opens the finding again, and the report
names the run that closed it and the reviewer's reason. A call that fails
writes nothing about the finding, and the next review gives it back again. A
closed finding under check keeps no other group from its file. `builds review
show` lists each close and each reopen. Builds checks open findings against the
branch head under review. A retry over an older commit reads only that diff.
Builds fails the group if an exchange omits a verdict or if its reviewers
disagree on whether a finding is fixed. A failed group leaves its findings open.
Builds records which calls kept each finding open so that a later review starts
from the last changes the group read with that finding.

`builds land` refuses a branch until its review takes it: nothing on a path
a group's rules cover changed since the last review (the net change of the
worktree's HEAD past origin/main against the net change the last review
read), and no commit message that a group reads changed since then; every
group asked over a diff a run read answered over it; every
finding is settled; no confirmed finding is open; and no closed finding is
waiting to go back to its group. Land finds the review
by the change's repo, the repo of the worktree it lands from, and its key: the
branch land started on, which land reads before it starts and passes to
`review check-landing` and `review landed` as `--landing`. When land refuses, it names what is unreviewed (the paths that
changed since the last review, and COMMIT_MESSAGE when a message changed),
the groups that gave no answer, the
unsettled findings, the open ones, and each closed finding that goes back to
its group with its closing run and the paths of its fix that changed. A
landing may hold some of the
branch's commits and leave the rest for later, once the review takes the
whole branch: while commits of the branch wait to land, the change stays
under review. A landing whose changed paths no group covers needs no review,
and neither does a landing in a repo of no project with lists: there is
nothing to record. A design-only landing (`--design N` alone) follows the
same rule. `builds review` and land find the changes since the last review
with one function, so they never disagree. Once a change has landed, `builds
review` on the branch opens a new change under the same key, and reads the
branch's net change past origin/main.

The rules are grouped in folders, and each group that covers a changed path
gets one reviewer in a read-only checkout of the reviewed commit. Claude has
Read, Grep and Glob. Codex runs in its read-only sandbox. Builds chooses Codex
in a Codex session and Claude in a Claude Code session or from a terminal.
A command that accepts --reviewer overrides that choice. Builds fails
the check if the chosen reviewer cannot answer.
The reviewer's instructions include the group's rules, the project's
projects/<project>.md and the brief of the first --item that has one. Builds
sends the diff as the message. The reviewer answers with a verdict for every
rule and, for each finding, the rule's clause, the
code with its file and line, and what goes wrong. builds drops a finding whose
clause is not in the rule, that is on COMMIT_MESSAGE when its group reads no
commit message, that is on a design file when its rule judges no design file
(below), whose whole quote appears on neither side of the diff with a line
that the diff adds or removes, or whose
code sits only on comment lines when the group of its rule judges no code
comment (skips_comments), and records it as dropped with that reason.
When several changed lines hold the same quote, the line number must
identify one occurrence. Builds drops the finding if both versions hold
the quote at that number or if the number identifies neither occurrence.
Builds drops a finding when the reported line identifies an unchanged
occurrence in either file version and no changed occurrence at that line.
A comment line
is a line whose first characters past its indent are a comment's mark in the
file's language: `//`, `/*` or `*/` in Rust, Swift, Kotlin and C# (and `*` in
a block comment of all but Rust), `#` in Python, shell and TOML, and `--` in
SQL. Every review goes in the project's store: the change's landing under
review (found by its key until the change lands) with its last review, the
net change each run read, the group, rules, model, prompt, token counts, cost,
verdicts, findings, how each was settled (both settles of a finding settled
again), and the run that closed each closed one. A call's prompt is its
system prompt without the project's instructions and the brief (the opening,
the group's question, how to answer and its rules' text), with its passes,
whether it reads the commit messages, and the answer schema; builds keeps the
text and names it by its hash. A group's model and prompt are its setup: two
calls with the same setup were asked the same way. Every audit and replay
records the same, with the commit of the rules checkout it read. A rule's `blocking` marks its
findings blocking in the reviewer's prompt and the report; every finding,
blocking or not, must be settled before the commits land. A rule marked
`review: false` in its front matter is one a reviewer cannot check, such as
one that needs the network: no review asks it, and builds still gives it to
the agent that edits a file it covers.

Builds keeps the input and output totals, the uncached input count, cache
read and write counts, and the reasoning output count. A count stays unknown
if Builds cannot read or derive it. An exchange keeps each count the reviewer
reported even when the group has no complete total for that count.
Builds names the review group when the reviewer omits its usage report or any
of the input, output or cache counts. Builds also reports an invalid reasoning
count. A valid answer still goes through the review checks.

The review checks design files only against the rules about how a screen,
board or component looks, never against the rules about code (decision
#364). The design files of a repo are the boards, the design system and
canvas.json: the paths its design globs give (`builds lists design-globs`),
the same files `builds design only` accepts. A rule that judges how things
look says so in its front matter with `design: true`. Every other rule covers
no design file, whatever its paths match. So a group runs for a design file
only when one of its rules judges design files and covers the file, and a
group reads a design file only then, even when it holds an open finding.
builds drops a finding of a rule without `design: true` on a design file, and
records it as dropped with that reason. The copy review, audits and replays
follow the same rule, with the design files of the change's repo.

The review searches screenshot capture files for new findings under the
rules about shots (decision #397). The
capture files of a repo are the files below each folder that a `shots-declared`
line of its .app-build names, which the checkout holds. A rule that judges
capture files says so in its front matter with `capture: true`. Every other
rule covers no capture file, whatever its paths match, and builds drops a
finding of such a rule on a capture file and records it as dropped with that
reason. A group that holds an open confirmed finding also reads capture file
changes to decide whether the branch fixes the finding. The shots
run checks that a moved shot gives the findings it gave before. `builds review
groups --changed` and `builds review replay` know no checkout of the repo, so
they treat no file as a capture file.

Before an agent starts on a brief, `builds item take` checks the brief against
the product spec with the same reviewer runner, in each worktree the take names
whose repo has spec files (`builds lists design-globs --spec-files`). The
reviewer reads the rule every-change-agrees-with-its-product-spec. Codex uses
GPT-6.2 Sol for this check. Claude uses the tier of the rule's group. The
reviewer quotes each sentence of the brief that states a behavior the spec states otherwise (a conflict), with the spec file and the
spec's text, and each sentence that states a behavior the spec doesn't state
(unstated). Storage the brief adds that the spec's schema text does not list,
such as a new column, is unstated, since the commit adds it to the spec. builds
looks for each quote in the brief and in the spec file, finds the line the
spec's text starts on, and sets aside a finding whose quote it does not find.
take prints each conflict and each unstated behavior as a spec edit for the
agent's commit, and takes the items. take records every check in the project's
store: the brief's text, the spec files and the commit the reviewer read them
at, the model, prompt, answer and each finding. Builds keeps the same token
counts as a branch review and records the price when the reviewer reports one
(`builds help lists`, item take).

Every review command but `review groups` without --changed reads or writes a
project's store:
the one --project names, else the project of the worktree or current
directory; `review replay` of cases writes each case's project's store. When
that project has no store, the command fails with "there is no store for
project P" and asks no reviewer.

After the push, land records the commits it pushed, and, once the branch has
nothing left to land, the change's landing as landed, with its review run.

REVIEW RECORDS' ENDS: a landing stays open until its change ends, and an open
landing is one that health and the dashboard list. A landing ends in one of two
ways, and the record says which. It ends as landed with the run that covered the
commits: `builds land` records that after the push, and `builds health` records
it when every commit of the branch is on origin/main by patch (or the branch is
gone and the commit its last review read is on origin/main), as when someone
landed the branch another way. `builds health` also records a review as landed
when its key names no branch and no audit (such as `detached:<sha>`) and the
commit its last review read is on origin/main by patch. A landing ends as abandoned, with what builds
found, when the branch is gone from the repo, no other branch, remote branch or
detached worktree holds the commit its last review read, origin/main lacks that
commit, and no open item names the branch. Each `builds health` run reads each
open landing against the repo's clone on this Mac and ends the ones that have
nothing left, and says each in one line. A landing whose branch still holds
commits to land, or that an item keeps, stays open. An abandoned landing keeps
its runs, findings and settles, which the review scores count as before, and
counts nowhere as landed: it has no landed run, so no audit and no case
reads it. A branch of the same name can be reviewed again at once, as after a landing.
A review under a key `audit:<name>` or `audit:<name>-<number>` is a review of
an audit of main: its findings are in code that is on main, so no branch or
agent waits on them. An audit may run as several reviews, `audit:<name>-1`,
`audit:<name>-2` and so on. When the last finding of one of them is settled,
builds makes one item for the audit, "Fix the confirmed findings of audit
<name>", in the area `audits`, straight in the backlog (decision #743), so
the item waits until the person starts it.
The audit's other reviews add their findings to that item, not a second item.
Each review ends as abandoned with the item's number, so no health line or
dashboard row lists it. A review with no confirmed finding ends with no item.
`review landed` then starts an audit of a sample of the landed reviews, never
of a landing of design files only, which looks for findings they missed. A separate finding check reads each candidate
miss the audit raises against the text of its rule, and the audit settles the
miss with the model's answer: confirmed, or dropped with the model's reason.
Nobody settles a candidate miss by hand. `review case propose` turns each
confirmed miss into a case: a recorded change in the review/cases folder of an
agent-instructions worktree, with the findings it must produce, which `review
replay` runs a grouping over. The same command builds the rest of that test
set from landed reviews.

The settled findings score the reviews. A confirmed finding is a true positive
(TP), a dropped finding a false positive (FP), a candidate miss an audit raised
and the coordinator confirmed a false negative (FN), and a rule a reviewer
answered "none" for, over a diff with no confirmed miss in it, a true negative
(TN). Precision is TP / (TP + FP) and recall TP / (TP + FN). A finding counts
as its last settle, so one settled again as dropped is an FP, and a confirmed
finding that a later review closed stays a TP.
`review scores` prints them per group and rule for each setup. `review replay --landing` asks
again over the diffs a landing's reviews read, under another model, rules
checkout or set of groups, and scores the replay against the same settled
findings: a confirmed finding it raises again is a TP and one it misses an FN,
and a dropped finding it raises again is an FP. A replay finding names the same
site as a settled one when both name the same rule and file (one path may be
shortened from the left) and one quote of code holds the other, once whitespace
and markdown marks are gone; failing that, when their lines are at most three
apart. Each settled finding pairs with one replay finding at most. A replay
finding that pairs with none is new, and nobody has judged it.

Every rule is in exactly one group. A group is a folder rules/<group-dir>/ of
agent-instructions that holds its group.toml; its rules are the .md files in
that folder and in projects/<project>-rules/<group-dir>/ (a project-rules
folder must name a group folder of rules/, and a group whose rules are all
project rules still has its group.toml under rules/). A rule's slug is its
file name without .md and is unique across all folders. `builds review groups`
checks this, and so does builds' test. The group.toml fields are top-level keys:

  name          the group's name, as `builds review` prints it
  question      the one design question the group's rules answer
  tier          optional. Choose high, medium or fast. The default is high.
                Claude uses Opus, Sonnet and Haiku respectively.
                Codex uses GPT-6.2 Sol for reviews and checks. A command
                with --model accepts gpt-6.2-sol when it runs Codex. Codex
                uses high reasoning effort for code reviews. Builds records
                the effort with the prompt.
  instructions  optional; extra words for the reviewer
  enumerate     true when the reviewer lists every site of the diff that
                `sites` describes, one changed file per call, and judges each
                site against every rule of the group (the file's new text
                around each hunk is in the message)
  sites         what a site is, for an enumerate group: the end of "every site
                in the diff that ..."
  commit_text   true when the commit messages of the change are read as one
                more file named COMMIT_MESSAGE: one more call for an enumerate
                group, and the end of the diff for any other
  skips_comments
                true when the group's rules judge no code comment: builds
                drops a finding of such a rule whose code sits only on
                comment lines
  copy          true when the group's rules judge word choice, grammar and
                style: only the copy review (`builds review copy`) asks the
                group, and `builds review`, its audits and its replays never
                do
  passes        how many times each call is made, default 1; the findings of
                all are kept, and the later calls read the first one's prompt
                from the cache
  project_facts true when the group also answers for the project facts that
                every commit keeps (the spec moves with the commit, bae writes
                as local), as one more verdict named project-facts

A group runs when at least one of its rules covers a path that a commit of
the change adds, changes or deletes: a path the rule's paths match that is no
design or capture file, or such a file when the rule judges files of its
kind (`design: true`, `capture: true`). Its reviewer
reads the full body of every rule in the group, the project's always-loaded
instructions (projects/<project>.md), the diff and the landing's brief, and
answers for every rule. No group reviews the test cases in the review/cases folder: a
case holds old code on purpose, so builds leaves that folder out of every diff
and list of changed paths that a review or `builds land` reads. To test
another grouping, change the folders in a worktree of agent-instructions and
run `review replay --rules-root` on it.

                              whose commits it lacks is not replayed; a run
                              that read the changes since the last review
                              replays those changes.
                              Prints each diff's new findings, then per group
                              and rule the counts of the recorded reviews
                              ("in use") beside the replay's, over the rules
                              the replay asked, with each side's setups,
                              calls, tokens and cost. Each replay goes in the
                              store. Exits 1 when a diff could not be read or
                              a call gave no answer
  {review audit}
                              audit a landing whose change landed, over the
                              commits of the run it landed with, read in DIR's
                              repo. The audit asks only the groups that the
                              landing's reviews ran, and of each group the
                              rules that cover a changed path, each on its
                              own group's model: one reviewer per rule, and
                              one review with those rules shuffled into other
                              groups. A finding in a rule and file
                              that the landing's reviews did not raise is a
                              candidate miss. The finding check reads
                              each candidate miss with its rule's text and
                              the diff of its file, and the audit settles
                              the miss confirmed, or dropped with the model's
                              reason; a miss whose check gave no answer stays
                              unsettled, printed with the command that
                              settles it. A confirmed miss becomes a case
                              (`review case propose`) and a fix item.
                              The audit starts at most 3 reviewers at once
  {review misses #1}          the candidate misses nobody has settled
  {review misses #2}
                              settle each of them as an audit settles the
                              misses it raises, over the diff the audit
                              reviewer that raised it read (the store keeps
                              each reviewer's message), with --model
                              as the check's model when given. Exits 1
                              when the store keeps no such diff or a check
                              gave no answer
  {review rates}
                              each group's audited miss rate: audits, confirmed
                              misses, and the latest 10 audits
  {review scores}             the reviews' scores from every settled finding
                              and confirmed miss in the store: per group, each
                              setup (model and the first 8 digits of its
                              prompt's hash) with the rules commits it read,
                              its calls, tokens and cost, its TP, FP, FN, TN,
                              unsettled findings, precision and recall, then
                              the same per rule; then what audits and
                              replays cost. A call made before builds
                              recorded cost counts as "cost not recorded".
                              Last, the command prints, per day and per group,
                              the confirmed findings per 100 changed lines on
                              each branch's first review, which shows whether
                              agents' first drafts improve. A group's rate counts only the
                              branches whose first review asked it, and the
                              rates leave out a first review from before
                              builds counted its changed lines
  {review case propose}
                              build the test set from the store's landed
                              changes of DIR's repo, written in the
                              review/cases folder of the agent-instructions
                              worktree --rules-root names. For each group, in
                              name order, the command takes the newest N
                              (default 2) landings whose first review raised
                              a finding of that group that the coordinator
                              confirmed with a reason of its own, not with
                              one of the generic reasons it confirmed
                              findings with in bulk, such as "real as the
                              finding says". The model check (--model,
                              default finding-check model) reads each such finding against
                              its rule's text. The case is the net change
                              that review read, with only the files of the
                              findings the check confirms and every commit
                              message. The case expects each confirmed
                              finding by rule and file, and as a `finding`
                              site of its code, and labels as `none`
                              each added line that no finding of the landing
                              names, that has 24 characters or more, and
                              whose text appears only once in its file. The
                              command writes no case for a landing whose
                              findings the check all rejects, and keeps the
                              case of a landing that has one already without
                              asking a model. The command also writes a case
                              for each confirmed candidate miss, over the
                              diff the audit reviewer that raised it read,
                              which the store keeps, with only the files of
                              the misses.
                              Exits 1 when a check gave no answer, and writes
                              no case for that landing
  {review case add #1}
                              add the change of a confirmed finding as a case
                              expecting it, written in the review/cases folder
                              of the agent-instructions worktree --rules-root
                              names (never a default: the main checkout is the
                              person's)
  {review case add #2}
                              add a confirmed miss the same way; --clean-for
                              SLUG in place of --rule and --file adds a change
                              that rule must stay quiet on

  {install}                   wait for another install to put its builds on
                              PATH, then read each store's schema. When every
                              store already has this builds' schema, move no
                              store, wait for no command, and copy builds onto
                              PATH as below. Otherwise (a store has another
                              schema, or no store has one yet), wait until no
                              builds command will write a store with the
                              schema it started with, naming each and when it
                              started. Wait for every hook run (`checks
                              run`), review that asks reviewers, and landing
                              (`land`) until it records its run, each of which
                              records after long work. Then wait for other
                              commands to finish using the stores. Each app
                              build lane finishes its steps on the programs
                              it started with. Install waits for any lane
                              that is recording its run. When install moves
                              the stores first, a lane that already started
                              waits for the move and gives its run to the
                              installed builds, which finds the repo's
                              project and records the run in its store.
                              If install moves the stores before a lane starts
                              and the app build picked the earlier program,
                              the lane asks you to run app-build again. While
                              install waits, hook runs, reviews and landings
                              that start wait for it and then run the
                              installed builds; other commands keep working. A
                              builds command started by a hook run, review or
                              landing runs under it, and an install that would
                              wait refuses to run under one. Then
                              move the stores to this builds' schema (builds
                              refuses to compile when its schema's stamp
                              differs from the one migrate.rs records, so each
                              schema change records the new stamp beside its
                              move from the schema before), copy builds onto
                              PATH in one rename (a failed build leaves the
                              installed one), restart each running dashboard
                              with the new builds, link
                              ~/.local/bin/builds-linker and

                              waiting commands start. If a dashboard fails to
                              restart, install reports the failure and keeps
                              its options for that build root so you can retry.
                              If you start a dashboard on that root, install
                              uses the running dashboard's options. Then create
                              the shared caches and their links (moving a real

                              and only once the compiles of the server it

                              what launchd and the server's log say, unless
                              launchd's server then listens on the port),
                              remove each other version's folder that no app
                              build holds (APP BUILDS), point
                              Xcode's default DerivedData at the

  {version}                   print `builds` and a hash of the sources this
