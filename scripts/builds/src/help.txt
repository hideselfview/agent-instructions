builds: runs this Mac's build volume (/Volumes/Builds), the repos' side
worktrees and their builds, the app build lanes, the pre-commit hook's checks,
the review of each branch against the rules, and landing. Agents run every
cargo command, app build and landing through it.

More help:

  builds help workflow  how work moves through worktrees, builds and landing,
                        and how a coordinator runs agents
  builds help lists     a project's decision stack, work queue, decision log
                        and design changes, and their commands (builds
                        lists, question, item, next, area, decision, design)
  builds help briefs    the instructions a coordinator gives an agent that
                        writes implementation briefs

builds is a Rust program in agent-instructions (scripts/builds).
agent-instructions' install.sh builds it from the main checkout's committed
HEAD, never from the working tree, and runs `builds install`, which puts it on
PATH as ~/.local/bin/builds. Agents change agent-instructions the way they
change bae and coven: on a branch in a side worktree from `builds new
~/dev/agent-instructions --for <who> --project builds` (or `--project bae` for
bae's rules and project file), reviewed and landed (`builds help workflow`).
The main checkout is the person's, and it is the live copy: install.sh links
its files into ~/.claude and ~/.codex. Its post-commit and post-merge hooks run
install.sh again when a commit or merge on its main branch changes what
install.sh consumes, scripts/builds/ included. A commit on a side worktree's
branch installs nothing; it goes live once it is on main and the main
checkout's main moves to it. To try an edit to builds before it lands, run the
binary your worktree built (scripts/builds/target/debug/builds).


BUILD VOLUME

Every build on this Mac writes to the build volume, and builds owns everything
on it:

  <repo>/<checkout>/    one build root per checkout (main or side-N)
  <repo>/app-checkouts  the mac lane's app checkouts, one name per line
  <repo>/app.locks/     one lock per app checkout (app.locks/side-N), held by
                        the build that runs there
  <repo>/app.queue/     the builds waiting for the lane's locks: `order` holds
                        one ticket per line, next first, with the holders'
                        tickets at the head (one per app checkout), and each
                        waiting process holds a ticket file
  <repo>/app-android-checkouts, app-android.locks/, app-android.queue/
                        the same for the android lane
  DerivedData/          Xcode's default DerivedData location
  caches/<name>/        the download caches every checkout shares
  .trash/               folders being deleted in the background
  .trash.lock           taken shared by each deletion into .trash, and
                        exclusive only by the floor and prune, to rename
                        .trash to .trash-emptying.<random>/ and empty it

`builds status` lists each of these and flags anything else on the volume as
UNKNOWN (it leaves out macOS's own volume metadata, such as .Spotlight-V100 and
.fseventsd). Something UNKNOWN is either a new kind of build output that builds
should own or a leftover to delete: find out which.


BUILD FOLDERS

Each checkout has one build root, /Volumes/Builds/<repo>/<checkout>/. The repo
lists its build output folders in `.build-dirs` at its root (cargo's target,
Xcode and SwiftPM .build folders, Gradle's build and .gradle, dotnet's obj and
bin, Lean's .lake), and each listed path is a symlink in the checkout to the
same path under the checkout's build root (target ->
/Volumes/Builds/bae/main/target). `.build-dirs` has one line per folder, and a
`keep` line for each build that must stay:

  <path> <cap>              the folder and its size cap
  <path> <cap> app <cap>    a second cap, for the folder in the repo's app
                            checkouts
  ... lane mac|android      after the caps: only that lane's app checkout
                            builds into the folder, keeps it built and takes
                            its app cap; in the other lane's app checkout it
                            is an ordinary side worktree's folder. A folder
                            with no lane (host target) is every app
                            checkout's
  keep <path>               a build inside a folder that never ages out in
                            main and the app checkouts, where the person runs
                            the app built there (bae:
                            bae-macos/bae/.build/runApp)

Tools always write through <checkout>/<path>, so the path a build sees never
changes, however often builds deletes and recreates the folder behind the link.
sccache's keys and cargo's fingerprints stay valid, and two checkouts never
share a folder, so their builds never wait on each other's locks. Every build
follows these rules:

  - Never set CARGO_TARGET_DIR, in the shell profile or on a command: the
    checkout's target link is the target folder. Two checkouts that build
    into one folder wait on cargo's lock and then rebuild what the other
    changed.
  - Never set another CARGO_* variable on a command or in a script (such as
    CARGO_INCREMENTAL or CARGO_PROFILE_*). sccache keys every CARGO_*
    variable, the working directory and the paths cargo passes, so a build
    with another path or another variable gets no cache hits. A setting goes
    in a --config argument or in Cargo.toml.
  - Never set RUSTC_WRAPPER="": it turns sccache off, and nothing on macOS
    needs that.
  - Never point a build at /private/tmp or the user's temporary folder (a
    -derivedDataPath there, a probe crate built where it was made): build in
    a checkout, whose paths lead to the volume.
  - A build script in a linked worktree finds shared refs through `git
    rev-parse --git-common-dir`: the worktree's own git dir has no refs/tags,
    and a build script that watches a missing path reruns on every build.

A link whose folder is gone breaks every tool (cargo fails with os error 20,
xcodebuild with code 74, Gradle with "Could not open file hash cache"), so the
repo's scripts/build-layout.sh runs `builds setup`, which recreates the folder,
and the hooks and every build script run that script first. Without builds (in
CI) the script does nothing and the tools write into real folders.

The Claude Code session's rust-analyzer, which agent-instructions'
rust-analyzer plugin (claude/plugins/rust-analyzer) starts, builds into
target-ra, a .build-dirs entry with its own cap in bae and coven, and checks
nothing on save: its `cargo check --workspace` of everything held main's target
over its cap. A Rust repo with no target-ra entry gets a real target-ra folder
in its checkout. The plugin passes these options at initialization, because
rust-analyzer reads a repo's rust-analyzer.toml only after its first build has
started into target.

  builds setup [<checkout>]   link the checkout's build folders, recreate any
                              that is missing, delete folders an older layout
                              left behind, apply the disk rules (DISK, below)
                              to the checkout, DerivedData and the shared
                              caches, delete idle build output in the
                              temporary folders, and keep the free-space
                              floor


WORKTREES AND CLAIMS

Each repo has a main checkout, the person's, and side worktrees for agents at
<parent>/<repo>-worktrees/side-N. side-1 is long-lived; `builds new` hands out
the others and `builds prune` retires them once they are idle.

A claim records who works in a side worktree, so that no other session takes
it: whoever hands out the worktree (a coordinator dispatching an agent, or the
person) claims it, and releases it when the work lands or moves on. A claim is
a file in the worktree's git dir, so it goes when the worktree does; `status`
shows it, and `retire` refuses a claimed worktree. A claim is not a lock: an
agent runs a series of separate commands, so nothing could hold one, and a
session that ends without releasing leaves its claim behind, with its age in
`status`. Exclusive use for one command, such as a build in an app checkout,
takes a real lock. A claim whose <who> ends in "(landing)" marks the worktree
its coordinator lands commits from.

A claim may carry a one-line note that says what its work waits on ("waiting on
Linux CI"), which `status` and the dashboard show, and the note may carry a
state that git can't show:

  waiting-on-you  the work waits on a question or a step only the person can
                  take
  winding-down    the agent is on its last item, then its handoff
  held            the worktree is kept on purpose with no work running, such
                  as uncommitted work waiting for another change to land; the
                  note says why and until when. A held worktree needs a
                  running item that waits on an open record, and `health`
                  doesn't call it idle while that record stays open; once the
                  record closes, `health` lists the worktree

A note set without --state has no state, so writing the next note clears the
state. Claiming the worktree again for the same <who> renews the claim's date
and keeps the note.

The dashboard gives each side worktree the first state that matches: Waiting on
you, Landing (a landing claim), Held, Ready to land (commits waiting to land,
claimed or not: an unclaimed worktree with such commits holds work an agent
left behind), Winding down, Working (claimed) and Free. Commits waiting to land
show as Ready to land only when `builds land` would take them as far as the
rules review goes; until then the card is in review and says where the review
stands: Needs review (no review read these commits, or a group still has to
answer: the coordinator runs `builds review`), Reviewing (a review of the
branch's newest commit runs), Findings to settle (with the count), Waiting on
fixes (confirmed findings with no fixing commit among them) or Unreviewed
commits (commits the review did not read that no finding names as its fix,
which land as a change of their own). A commit waits to land
while origin/main has no commit with the same change (`git log --cherry-pick
--right-only origin/main...HEAD`), because landing rebases or cherry-picks it.

  builds new [<repo>] [-b <branch>] [--for <who>] [--project P]
                              hand out a free side worktree (no claim, a clean
                              tree, every commit on origin/main by patch, not
                              an app checkout) with a fresh branch from
                              origin/main, or add the next side-N when none is
                              free; link it and run its post-checkout, which
                              builds nothing. It claims the worktree for <who>
                              (default "builds new") under a lock on the repo,
                              so two calls never get the same worktree. When
                              the worktree's host target is empty, new fills
                              it with a copy-on-write clone of another
                              checkout's built target, taken while no build
                              runs there (it waits for one when every source
                              is building), so the first build compiles
                              little. --project P records which project's work
                              it is, and a repo that two projects hold
                              (agent-instructions is in bae and builds)
                              requires it: every lists command run in the
                              worktree, `release` and the dashboard then use
                              P's lists
  builds claim <checkout> <who> [--project P]
                              record that <who> works in the side worktree
                              (--project as for `new`; a claim renewed without
                              it keeps its project)
  builds note <checkout> [--state waiting-on-you|winding-down|held] [<text>]
                              set the claim's note, or clear note and state
                              with no text; --state needs the text. --state
                              held is refused unless every item running in the
                              worktree waits on an open question, item, design
                              change or condition (`builds item wait N --on
                              REF`); a landing claim or an app checkout, which
                              runs no item, is never refused
  builds release <checkout>   remove its claim; refused while an item runs in
                              the worktree
  builds retire <checkout>    remove a clean, unclaimed side worktree and its
                              build root; refuses an app checkout


CARGO

Run every cargo command through `builds cargo`; in bae and coven,
scripts/cargo.sh runs it, and the hooks and build scripts use that script.
builds reads cargo's report of each build to record the build copies it used
(DISK, below). cargo typed by hand records nothing, so builds deletes what only
it uses three days after cargo last built it.

Every checkout but main builds without incremental compilation (`builds cargo`
passes --config build.incremental=false), the app checkouts included. sccache
refuses every incremental compile, so with incremental off sccache keeps each
workspace crate any worktree built: a build of the same sources in another
worktree, or in an app checkout that agents move between branches, comes from
the cache, and no incremental folders pile up. A full build without incremental
output is smaller, so the app checkouts' folders take lower caps. Main, the
person's checkout, stays on one branch and keeps incremental. To turn
incremental on in a profile, set profile.dev.incremental in Cargo.toml, never
CARGO_INCREMENTAL=1, with which sccache refuses every compile.

In a side worktree, `builds cargo` runs test, clippy, check, doc and nextest
run|list on the host with the most free cores (cores minus the one-minute load;
this Mac wins a tie), passing over a host that does not answer, is under the
free-disk floor, refuses jobs (HOSTS) or has no clone of the repo. It sends the
checkout's HEAD plus its working tree (staged and unstaged edits, deletions,
and files git neither tracks nor ignores) as a commit to the host's clone only,
runs cargo in a remote worktree there that keeps its build between runs, prints
the same output and exits with the same status; one line on stderr names the
host. When the host refuses the job before cargo starts there (sending the
commit or claiming a worktree fails there), builds records the host as
refusing jobs, says so on stderr with what the host said, and runs the command
on this Mac. A stop signal stops cargo on the host, and a host that drops
mid-run fails the command, naming the host; builds never runs the command
again here, since cargo may have run part of it there. A landing's compile
check runs `builds cargo`, so it follows the same rules. These stay on this
Mac:

  - every other subcommand (build, rustc, run, bench, install)
  - a command with --message-format, --target, --release or a path argument
    (--manifest-path, --target-dir, an absolute path)
  - a command run with CARGO_TARGET_DIR or FFMPEG_DIR set, or with
    RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER or BUILDS_CARGO_BEFORE set to a
    path outside the checkout (a wrapper given as a bare name, such as
    sccache, is the host's own)
  - every command in a main checkout

One sccache server serves every checkout. launchd runs it
(local.sccache-server) on sccache's default port, 4226, with the system's
TMPDIR and no idle timeout; its cache is caches/sccache, capped in
~/Library/Application Support/Mozilla.sccache/config. `builds install` writes
both, and `builds status` flags a config that no longer holds builds' cap.
Never start a server any other way: a server inherits the TMPDIR of the client
that starts it and fails every compile once that folder is deleted, and the
Unix-socket mode (SCCACHE_SERVER_UDS) races when clients start at once and
leaves orphaned servers. sccache never caches build scripts, proc-macros, an
incremental compile or a crate clippy lints, and a crate that reads OUT_DIR or
depends on a proc-macro crate misses in each new checkout. `builds help
workflow` says when to restart the server.

  builds cargo <subcommand> [<args>...]
                              run cargo (build, check, clippy, doc, rustc,
                              rustdoc, test, bench, run, install, nextest
                              run|list|archive), record the build copies it
                              used, and pass the rest of its output, a
                              program's or the tests', through. It holds the
                              checkout's guard while cargo runs, and as it
                              exits starts `builds units after-build`, which
                              deletes the copies the build replaced.
                              BUILDS_CARGO_BEFORE=<path> [<args>] runs a
                              program of the checkout in its top folder before
                              cargo, on whichever host runs cargo, and a
                              failure stops the command with its status.
                              BUILDS_CARGO_HOST=<name> picks the host for one
                              command (local is this Mac); a command that must
                              stay here runs here, with a note on stderr. Each
                              run's host and time go to the project's store.


APP BUILDS

App builds (an Xcode app, a Gradle app, a bridge cross-compiled for a platform)
take 10-20 GB per platform per checkout, so a repo keeps them built only in
main, for the person's installs and releases, and in its app checkouts:
long-lived side worktrees, one or more per lane, that the project file names
and `builds app-checkout` records. Every other side worktree builds host output
only (for Rust, target, which tests, clippy and the hook use).

A lane is the part of a repo's app builds that shares no build output with the
other: in bae the mac lane is Xcode and target-macos, and the android lane is
Gradle and target-android. Each lane has its own app checkouts, locks and
queue, so a Mac build and an Android build never wait on each other, and each
app checkout keeps only its own lane's folders built. A checkout is one lane's,
never both. A lane with several app checkouts builds in as many at once, and
its queue gives a free lock to the next build in line: waiters go in the order
they came, and one that dies in line never lets anyone past the holders.

An app checkout's working tree belongs to whoever holds its lock, and only for
the command they run holding it: nobody edits there or leaves changes behind.
Commit on your branch in your own worktree, then run `builds app-build`, which
takes the lock, checks out your commit (detached, because your branch stays
checked out in your worktree) and builds. Put everything that needs the build
(its tests, launching the app) in that one command; the next holder moves the
checkout. To change something, commit or amend in your worktree and run the
command again. A dirty app checkout fails the command rather than carry
someone's changes into your build: find out whose they are before deleting
them.

Another checkout may keep an app build while a wave of work needs it (the
person asks for an app build in a worktree, or parallel agents each need one).
Clear it once that work has moved on: retire the worktree, or delete the
folders behind its app links while nothing builds there.

A repo's `.app-build` at its root says what its app builds run, one line each:

  step <lane> <name> <program> [<args>...]
                    a step of the lane. A step is a program, not a shell
                    string: a step that needs a shell is a script in the repo
  on <pattern> <step>...
                    the steps a changed path matching the pattern builds (a
                    pattern ending in / or naming a path matches the paths
                    under or at it; one starting with * matches the paths
                    ending in the rest)
  needs <lane> <step>...
                    the steps a --test or --shots run builds first when no
                    changed path picked one of the lane's steps
  sources <lane>[:<name>] <folder>...
                    the folders that declare the lane's test classes; with
                    :<name>, the `test <lane>:<name>` line runs the classes
                    declared there
  test <lane>[:<name>] <program> [<args>...]
                    how the lane runs one test class, named in its {class};
                    a lane may have a named test line per kind of test (bae:
                    mac:shots for the shot test bundle)
  shots <lane> <program> [<args>...]
                    how the lane runs the shots (pictures of app views, each
                    checked against its board) whose names start with the
                    prefix in its {select}
  shots-source <folder>
                    the shots program's sources; their git tree at a commit
                    is the shots version stored findings are keyed by
  results <lane> <path>...
                    the folders a --test or --shots run on another host
                    copies back to this Mac
  here <step>...    steps that never run on another host (bae's signed macos
                    step)
  limit <step> <time>
                    the step's time limit (90s, 30m, 2h), in place of 45
                    minutes

A step that runs past its limit gets SIGTERM to its whole process group and
SIGKILL ten seconds later, and fails the build, which gives up the lock. Each
--test run is limited to 10 minutes and each --shots run to 20. `builds
build-app` and `builds lock` set no limit.

An app checkout may be on another host (`builds host`). Its lock, queue and
record of its last build stay on this Mac, under the entry <host>:<name>. A
build there sends the commit to the host's clone as a job ref (never to
GitHub), switches the checkout to it (the checkout must have no changes), and
runs each step through `builds remote step`, with the same time limits and
takeover; its output comes back behind [<lane> <host>:<name>]. After each
--test or --shots run there, passed or failed, the folders of the lane's
`results` lines are copied to /Volumes/Builds/<repo>/<host>:<name>/<path> here,
where agents read them. A mac lane checkout on a host needs Xcode there.
build-app, `builds lock` and a build that runs a `here` step never take a
checkout on a host.

Each --shots run's findings (what the shots program printed) are stored in the
project's store under the repo, the full commit, the lane, the prefix and the
shots version, and its report (index.html and pictures) is copied to the
store's folder, in shots/<commit>-<lane>-<prefix>-<version>/, the newest 30
runs, so the next run in the checkout cannot overwrite it. A run that died
before it made findings stores nothing, and a repo with no `shots-source` line
stores none. The "before" side of a shots check is read from the store, never
built again.

  builds app-build <repo> <ref> [--test <Class>]... [--shots <prefix>]... [--fresh]
                              build <ref> where it is needed; builds picks the
                              steps, lanes and hosts, and no caller names them.
                              The paths <ref> changes since its merge-base
                              with origin/main pick the steps through `on`
                              lines (a branch that changes only Rust builds
                              nothing); a --test class goes to the lane whose
                              `sources` folders hold it and a --shots prefix to
                              the lane it starts with (mac. or android.); a
                              lane with runs and no step builds its `needs`
                              steps; each lane takes the free app checkout on
                              the less loaded host. A --shots pick whose
                              findings are already stored prints them and
                              takes no lock; --fresh runs it anyway
  builds app-build <repo> <ref> <step>... [--test mac|android <Class>]... [--shots mac|android <prefix>]... [--fresh]
                              check out <ref> in a free app checkout of each
                              lane the steps are in, holding that checkout's
                              lock, and run the steps in the order given,
                              stopping at the first failure; then run the lane's
                              `test` line once per --test class and its `shots`
                              line once per --shots prefix (in any order, after
                              the steps; the lane must have the line). A class
                              or prefix is one argument, never read by a
                              shell. The lanes build at the same time, each
                              line of output behind [<lane> <checkout>]
                              ([<lane>] until it holds a lock), and the build
                              fails if either lane fails, saying which. A lane takes the free lock of the checkout
                              on the less loaded host first (load average per
                              core, this Mac counted; a host that does not
                              answer is skipped). Each lane's run goes to the
                              project's store when it ends: the ref, the claim
                              of the worktree it ran from, the checkout, its
                              wait in the queue, and each step's start, wall
                              time, CPU time and result; the dashboard shows
                              the last 12 hours
  builds app-build <repo> --lane mac|android <ref> [<step>...] [--test <lane> <Class>]... [--shots <lane> <prefix>]...
                              one lane's part of the above, in this process.
                              With no step named, only the --test and --shots
                              runs happen, and only when the app checkout's
                              last build finished and is of <ref>; otherwise it
                              refuses, naming what was built
  builds app-build <repo> --list
                              print the steps (lane, name, command) and each
                              lane's test and shots lines
  builds shots findings <repo> <ref> mac|android <prefix>
                              print the findings stored for <ref>'s commit,
                              the lane and the prefix, with a line on stderr
                              that says how old they are, which shots version
                              made them and where the run's report is. With
                              none stored, it fails and names the app-build
                              command that makes them
  builds build-app <repo> mac|android [<ref>]
                              holding one of the lane's locks, check out <ref>
                              (default origin/main, after a fetch) in that app
                              checkout, which must be clean, and run the
                              lane's build that .app-build names; for mac,
                              replace the app in ~/Applications/<repo>-test,
                              quitting the copy running. Opens nothing. This is
                              the person's own build; the dashboard runs it
                              from each lane's Build button, one run per lane
                              at a time
  builds lock <repo> [--lane mac|android] <command> [<args>...]
                              wait for one of the lane's locks (the mac lane's
                              unless named), then run the command holding it,
                              with the checkout in BUILDS_APP_CHECKOUT; run it
                              as a background task. The lock lasts until the
                              command's last process exits, and SIGTERM,
                              SIGINT and SIGHUP go to the command's whole
                              process group. It is for a command that is no
                              repo's build
  builds queue <repo> [--lane mac|android]
                              show each lane's holders and who waits, next
                              first
  builds queue <repo> top <pid>
                              move that waiter to right behind the builds that
                              hold a lock, in the lane it waits in
  builds takeover <repo> [--lane mac|android] [<pid>]
                              with every lock of the lane held, stop the build
                              that joined last of the holders (SIGTERM to its
                              process group), run the waiter <pid> (default
                              the first) next, and run the stopped command
                              again by itself straight after it (an app-build
                              lane reruns from its checkout); with a lock free,
                              the same as `top`. A pid names its lane; with no
                              pid and builds waiting in both lanes, --lane
                              does. The dashboard's queue has both as buttons
  builds app-checkout mac|android <checkout>
                              add the side worktree to the lane's app
                              checkouts (app-checkouts or
                              app-android-checkouts)
  builds app-checkout mac|android --host <host> <path>
                              record an app checkout on a host as the lane's
                              entry <host>:<name>. <path> ends in
                              dev/<repo>-worktrees/<name>, and the host's clone
                              ~/dev/<repo> must exist. Its first build makes
                              the checkout there as a side worktree is made
                              (the repo's post-checkout, build folders under
                              ~/builds-root and, for the android lane, a
                              local.properties naming the host's Android SDK
                              in each Gradle project)
  builds app-checkout remove mac|android <checkout>
  builds app-checkout remove mac|android --host <host> <path>
                              take it out again; refused while a build holds
                              its lock
  builds app-checkout reset <repo> <checkout> [--matching <rev>]
                              put an app checkout on origin/main, holding its
                              lock (it waits for the build holding it). Only
                              SIGKILL during a build's switch leaves new files
                              under the old HEAD, and reset is the way out. It
                              refuses unless every dirty path is exactly what
                              origin/main, HEAD or <rev> (the commit the switch
                              was heading to) holds there, names the paths
                              that are not, and never throws away work


HOSTS

builds can run jobs on other Macs, its hosts; this Mac is always one, named
local. A host keeps its clone of each repo at ~/dev/<repo>, its worktrees at
~/dev/<repo>-worktrees/, and its build roots in ~/builds-root in place of
/Volumes/Builds.

A host refuses jobs when it answers but cannot start one. builds finds this
two ways: a probe, which asks the host for its load and disk, also runs git
there, in the shell a job's push reaches, and git fails (as it does on a Mac
whose Xcode license is not accepted); or sending a job's commit or claiming a
worktree for it fails there. builds records each host that refuses jobs in
the folder host-refusals beside the file `hosts`, with when it first refused
and what it said, and every pick passes over it. `builds health` lists each
recorded host under "needs action", and the dashboard's load card for the host
says "refuses jobs" in place of its core count when git fails there. Fix the cause on the host; the next probe
that finds the host answering with git running removes the record, and builds
uses the host again. `builds host list` probes every host, and so does every
`builds cargo` and `builds remote run` that picks one.

  builds host add <name> <ssh target>
  builds host setup <name>
  builds host list

DISK

builds keeps disk use bounded: it deletes the build copies and builds that no
build uses, deletes a folder that is still over its cap, and keeps a free-space
floor on the volume. `setup`, which runs before every hook and build, and
`prune` do all of this, and `builds cargo` deletes the copies a build replaced
as it exits. Nothing deletes a folder that a process holds a file open in or
whose checkout's guard a build holds, and a deletion never fails a build: a
removal that fails warns and leaves the folder in the trash for the next
emptier.

Unused build copies. Cargo names each unit it builds (one crate target, for one
profile, target and feature set) by a hash of everything that build depends on,
so every dependency bump builds a new copy of each unit above it, and the old
copy stays. In each cargo folder (target, target-macos, ...) builds deletes
every file of a unit that no build used for BUILDS_UNUSED_DAYS days (default
3), and of a unit a newer copy replaced: a copy of the same package and target,
mode, features and profile, built from other sources (another version or git
revision of a dependency, or another compiler), that a build used after the
unit's last use. A unit is also replaced when a newer build of its package
(such as the library beside a test binary) was built against another copy of
something the unit was built against. Copies built from the same sources for
another package selection (`-p x` against the workspace) stay side by side, and
so does whatever a unit that stays was built against. A unit's last use is the
last build that reported it, rebuilt or up to date; a unit that no recorded
build used counts as used when cargo last built it.

Incremental folders. builds deletes the incremental folders that only deleted
units used. In main, whose builds compile incrementally, it also deletes every
incremental folder that nothing wrote anywhere inside for
BUILDS_INCREMENTAL_HOURS hours (default 6); in the other checkouts, whose
builds don't, it deletes every incremental folder, since no build reads them.

Object files. In every checkout, builds deletes the object files that no build
or debugger reads: an rlib's loose objects, and the objects a binary's debug
map doesn't name, which each incremental rebuild leaves behind under new names.
This needs split-debuginfo "unpacked", macOS's default; keep it, since packed
builds slower and larger, and off drops file and line from the top crate's
frames.

Separate builds inside one folder. A folder is aged by its newest write, so a
stale build beside a live one (last week's Xcode tree beside today's) would
never age out. builds finds the builds inside each folder and deletes each one
no build used for BUILDS_UNUSED_DAYS days, in main and the app checkouts too,
but keeps a build a process holds a file in and, in main and the app checkouts,
one a `keep` line names. It recognizes an Xcode tree (info.plist beside Logs,
and Build or ModuleCache.noindex, up to two levels below the folder) and a
SwiftPM <triple>/debug or <triple>/release folder in a .build that holds
workspace-state.json. A build's last use is the newest write inside it, since
xcodebuild and `swift build` write even when everything is up to date. dotnet's
and Gradle's folders are not split: an up-to-date `dotnet build` writes
nothing, and Gradle keeps no build per variant. `status` lists each build under
its folder with its last use (`status --json`: the folder's `trees`).

Builds and deletions never overlap. builds deletes a unit's files only while it
holds the checkout's guard (<build root>/.builds-cargo.lock) and cargo's lock
on that profile folder, both taken without waiting, and keeps any unit a
process holds a file of. `builds cargo` holds the guard, shared, from before
cargo starts until cargo has exited and its report is read, because cargo
decides which units are up to date before it runs anything and lets go of its
own lock before `cargo test` runs the tests. A build waits on the guard only
while a deletion holds it, a few seconds, and a build that starts after a
deletion rebuilds the unit, mostly from sccache.

Caps. A folder still over its cap is deleted whole (renamed into .trash,
removed in the background) and recreated empty, and the next build refills it,
mostly from sccache. A cap is about twice a fresh build of its folder. A
claimed worktree's folder is never deleted whole, since its agent is at work in
it: status shows it over its cap as "claimed, kept". Sizes, against caps and in
status, count each block once (`builds du`): cargo copies its libraries out of
deps/ as APFS clones, which du counts once per file, and rustc hard-links deps/
files into incremental/.

Free-space floor. Caps bound each folder, not the volume: a checkout with every
platform built takes 45-52 GB, and the build volume shares its APFS pool with
the main disk. So `setup` keeps a free-space floor of 30 GiB
(BUILDS_FREE_FLOOR_GIB). Under it, setup finishes emptying the trash, then
deletes the build roots of checkouts that are gone, DerivedData's idle entries,
then the incremental folders nothing wrote inside for 60 minutes in every
checkout (claimed ones, main and the app checkouts included), and then the
whole folders of unclaimed side worktrees that nothing wrote to for 30 minutes,
never main's or an app checkout's own lane's folders; each kind goes least
recently written first, until the floor is reached. If setup can't reach the
floor, it warns, naming the free space and the biggest folders, and the build
goes on: whoever runs the agents stops starting more. Only under the hard floor
of 10 GiB (BUILDS_HARD_FLOOR_GIB) does it fail, before the build starts, rather
than let the build run out of space halfway. It never deletes a shared cache.

DerivedData. bae passes -derivedDataPath into a .build folder in the checkout
(scripts/xcode-trees.sh is its one definition, and a pre-commit check refuses
the flag anywhere else), so DerivedData holds only what one-off xcodebuild runs
(-showBuildSettings, package resolves) and the Xcode app write: one
<project>-<hash> entry per project path, mostly SwiftPM checkouts of about 3
GB. It is one disposable cache with a 15 GiB cap. `setup` and `prune` delete its
entries, least recently written first, while it is over the cap; `prune` also
deletes entries nothing wrote to for a day, and the floor deletes its idle
entries first. Every deletion skips an entry written in the last 30 minutes or
one a process holds a file in.

Shared caches. Each tool keeps its downloads (sccache, its compiler outputs) in
caches/<name>, linked from where the tool looks, with a cap each:

  gradle   8 GiB  ~/.gradle
  npm      1 GiB  ~/.npm
  nuget    6 GiB  ~/.nuget
  swiftpm  3 GiB  ~/Library/Caches/org.swift.swiftpm
  sccache 30 GiB  ~/Library/Caches/Mozilla.sccache

`setup` and `prune` delete a cache that is over its cap, whole, once nothing
has written to it for 30 minutes and no process holds a file in it, and put
back the settings files it held (gradle.properties, Gradle's init scripts,
NuGet.Config). Nothing else deletes one: every checkout would download it all
again, and a SwiftPM fetch cut off halfway corrupts its cache. sccache keeps
its own cache under its cap; builds only shows it.

When xcodebuild fails with "Couldn't check out revision" or "file not found" on
a SwiftPM dependency (often Sparkle), its cache is corrupt: disconnect any VPN
(a VPN can cut fetches short), delete the app's Xcode build trees and its
SourcePackages folder and ~/Library/Caches/org.swift.swiftpm/repositories/
<dependency>*, and run the repo's build script again. Every script that
resolves packages and every script that builds after it must pass the same
xcodebuild flags, -derivedDataPath above all, or the packages land where the
later build can't find them.

Cargo's git checkouts. `setup` and `prune` delete each checkout in
~/.cargo/git/checkouts that no live checkout's Cargo.lock pins, holding cargo's
package cache locks. The git databases in ~/.cargo/git/db stay.

Build output in the temporary folders. A build pointed at /private/tmp or the
user's temporary folder writes 5-14 GB there that nothing else deletes. `setup`
and `prune` delete each cargo target, DerivedData or SwiftPM folder there, up
to four levels deep, that nothing wrote to for 30 minutes and no process holds
a file in; `status` lists them. They skip /private/tmp's claude-* (Claude Code
sessions' scratch, whose entries go three days after the session's last
change), com.apple.* and tmux-* (live sockets), and anything the user doesn't
own.

Never run `cargo sweep --time` or `--maxsize`: APFS doesn't refresh access
times, so sweep deletes the builds needed next. `cargo sweep --installed` after
a toolchain upgrade is fine.

COMMIT CHECKS

A repo's `.checks` at its root declares the checks its pre-commit hook runs,
one per line: `<kind> <name> <paths> <program> [<args>...]`. The kinds:

  check   a static check
  fix     a formatter; the files it changed are staged again
  whole   a check that reads the whole tree: the hook runs it when a path
          matches, and `builds land` runs it on every landing, since two
          commits that each pass the hook can break it together. It names
          neither {files} nor {crates}
  test    a checker's own test; CI runs it, never the hook

paths is a comma-separated list of globs over repo-relative paths: `*` stays
inside one path segment, `**` is any number of segments, and a glob with no `/`
matches the file name anywhere. The program is not run by a shell. As a whole
argument, {files} is the matching staged files that still exist, and {crates}
is `-p <crate>` for each workspace crate holding one (a root Cargo.toml or
Cargo.lock counts as every crate); a check with neither runs whole whenever a
matching file is staged.

  builds checks run [<worktree>]
                              what the pre-commit hook runs: the check and fix
                              lines the staged files match, in file order, from
                              the repo root, printing each one's name, time and
                              result (with a failing one's output) and the
                              total time. Every line runs even after one fails,
                              and the exit status is non-zero if any did. It
                              refuses before any line runs, naming each file,
                              when a staged file also has unstaged changes,
                              since the checks read the working tree;
                              unstaged changes to unstaged files are fine. It
                              records each run, a refused one as a failed run
                              with no checks, in the project's store: when,
                              repo, worktree, branch, the commit HEAD pointed
                              at when it started (its base), each staged file
                              (its change and lines added and removed), each
                              line (run with its time and result, or skipped),
                              the planning time and the total. A run it can't
                              record says so on stderr and ends as the checks
                              decided; a repo in no project records nothing
  builds checks whole [<worktree>]
                              run every `whole` line on the tree as it is (the
                              checks `builds land` runs on a landing), printing
                              each one's time and result, with a failing one's
                              output; the exit status is non-zero if any failed
  builds checks stats [--project <project>] [--repo <repo>] [--since <YYYY-MM-DD>] [--change <rev>]
                              read the recorded runs back, for the project of
                              the current repo unless --project names one,
                              each repo apart (or only --repo's): the passing
                              runs (every check passed) with their median and
                              slowest total; per check how often it passed and
                              was skipped, its median and slowest time over its
                              passes, and the median of its latest 10 passes
                              against the 10 before; the slowest passing runs
                              with their diffs; and each set of checks whose
                              newest passing run took over 45 seconds, the

                              print what `run` would run, without running it

LANDING AND REVIEW

A coordinator lands commits, putting them on origin/main, with `builds land`
in the worktree whose branch holds them, once that branch's agent is done
there. In a repo of a project with lists, every branch is reviewed against
agent-instructions' rules before it lands. No diff is reviewed more than once.
Each change gets one review; the coordinator reads the fixes for its confirmed
findings:

  1. The coordinator runs `builds review` on the branch's commits once.
  2. It judges each finding against the code and the rule, and settles it as
     confirmed or dropped, with why (`builds review settle`). The settled
     findings stay in the project's store as the record of what reviews catch
     and miss, and every settle feeds the review's scores (`review scores`).
  3. It has each confirmed finding fixed in a new commit, reads that commit
     against its finding itself, since builds does not review a fix, and
     names it (`builds review fixed`).
  4. It lands the reviewed commits with their fixes.

`builds review` refuses a second run of a change (one key), naming the run
that reviewed it. The one exception is a review in which a group gave no
answer (its reviewer failed): a later run asks only the groups that gave no
answer, over the diff the review read, and refuses once every group answered.

`builds land` refuses commits that lack this step. It takes them when one
change's review covers them: each commit whose paths a group covers is either
one the review read, and every such group answered over it, or the commit
named as the fix of one of the review's confirmed findings; every finding is
settled; and every confirmed finding names a fix among the commits landed. A
landing may hold some of the reviewed commits and leave the rest for later. A
landing whose changed paths no group covers needs no review, and neither does
a landing in a repo of no project with lists: there is nothing to record. A
design-only landing (`--design N` alone) follows the same rule.

A review matches a landing's commits by their changes, not by their SHAs. A
review records each commit it read with its patch id (`git patch-id
--stable`, over a diff whose options builds fixes); a commit that changes
nothing has none. Land reads the patch ids of the commits it was given. A
rebase or cherry-pick that keeps a commit's change keeps its patch id, so the
review still covers it. A fix is matched the same way: `builds review fixed`
records the patch id of the fixing commit.

A commit that is neither one the review read nor a named fix is new work: a
commit added after the review, a squash, or a commit whose patch id a rebase
changed (a conflict, or changed context lines). Land refuses it and names it.
Land the reviewed commits and their fixes without it, then review it as a
change of its own: once the first change has landed, `builds review` on the
branch opens a new change under the same key, and reads only the commits past
origin/main. When the commits after it need it, so the reviewed commits can't
land without it, the coordinator asks the person how to land them.

The rules are grouped in folders, and each group that covers a changed path
gets one reviewer, a `claude -p` run in a checkout of the reviewed commit with
only Read, Grep and Glob. Its system prompt holds the full text of the group's
rules, the project's projects/<project>.md, the brief of the first --item that
has one; its message holds the diff. It
answers with a verdict for every rule and, per finding, the rule's clause, the
code with its file and line, and what goes wrong. builds drops a finding whose
clause is not in the rule or whose code is not in the diff, and records it as
dropped. Every review goes in the project's store: the change's landing under
review (found by its key until the change lands), the commits the review read,
the group, rules, model, prompt, tokens, cost, verdicts, findings, how each was
settled and the commit that fixed each confirmed one. A call's prompt is its
system prompt without the project's instructions and the brief (the opening,
the group's question, how to answer and its rules' text), with its passes,
whether it reads the commit messages, and the answer schema; builds keeps the
text and names it by its hash. A group's model and prompt are its setup: two
calls with the same setup were asked the same way. Every audit and replay
records the same, with the commit of the rules checkout it read. A rule's `blocking` marks its
findings blocking in the reviewer's prompt and the report; every finding,
blocking or not, must be settled before the commits land.

After the push, land records the change's landing as landed, with its review
run. A sample of landed reviews is audited for findings they
missed. The person curates a confirmed miss into a case: a recorded change in
the review/cases folder of an agent-instructions worktree, with the findings
it must produce, which `review replay` runs a grouping over.

The settled findings score the reviews. A confirmed finding is a true positive
(TP), a dropped finding a false positive (FP), a candidate miss an audit raised
and the coordinator confirmed a false negative (FN), and a rule a reviewer
answered "none" for, over a diff with no confirmed miss in it, a true negative
(TN). Precision is TP / (TP + FP) and recall TP / (TP + FN). `review scores`
prints them per group and rule for each setup. `review replay --landing` asks
again over the diffs a landing's reviews read, under another model, rules
checkout or set of groups, and scores the replay against the same settled
findings: a confirmed finding it raises again is a TP and one it misses an FN,
and a dropped finding it raises again is an FP. A replay finding names the same
site as a settled one when both name the same rule and file (one path may be
shortened from the left) and one quote of code holds the other, once whitespace
and markdown marks are gone; failing that, when their lines are at most three
apart. Each settled finding pairs with one replay finding at most. A replay
finding that pairs with none is new, and nobody has judged it.

Every rule is in exactly one group. A group is a folder rules/<group-dir>/ of
agent-instructions that holds its group.toml; its rules are the .md files in
that folder and in projects/<project>-rules/<group-dir>/ (a project-rules
folder must name a group folder of rules/, and a group whose rules are all
project rules still has its group.toml under rules/). A rule's slug is its
file name without .md and is unique across all folders. `builds review groups`
checks this, and so does builds' test. The group.toml fields are top-level keys:

  name          the group's name, as `builds review` prints it
  question      the one design question the group's rules answer
  model         optional; opus, sonnet or haiku. The reviewer runs opus unless
                this overrides it
  instructions  optional; extra words for the reviewer
  enumerate     true when the reviewer lists every site of the diff that
                `sites` describes, one changed file per call, and judges each
                site against every rule of the group (the file's new text
                around each hunk is in the message)
  sites         what a site is, for an enumerate group: the end of "every site
                in the diff that ..."
  commit_text   true when the commit messages of the change are read as one
                more file named COMMIT_MESSAGE (an enumerate group)
  passes        how many times each call is made, default 1; the findings of
                all are kept, and the later calls read the first one's prompt
                from the cache
  project_facts true when the group also answers for the project facts that
                every commit keeps (the spec moves with the commit, bae writes
                as local), as one more verdict named project-facts

A group runs when at least one of its rules matches a path that a commit of
the change adds, changes or deletes. Its reviewer reads the full body of every
rule in the group, the project's always-loaded instructions
(projects/<project>.md), the diff and the landing's brief, and answers for
every rule. To test another grouping, change the folders in a worktree of
agent-instructions and run `review replay --rules-root` on it.

  builds land <worktree> [--done N]... [--part N]... [--design N] <sha>...
                              put the commits on origin/main from the
                              worktree whose branch holds them: a
                              fast-forward when origin/main is their base,
                              else a cherry-pick, trying a refused push again
                              from a fresh fetch up to five times. Before it
                              fetches anything, land refuses the worktree
                              while it has uncommitted changes (its agent is
                              not done there) and refuses a commit that is
                              not on its HEAD. It builds the result on a
                              detached HEAD at origin/main. One landing runs
                              in a worktree at a time; landings in different
                              worktrees run together, and the push retry
                              orders them. After the push the worktree stays
                              detached at the landed commit when its branch
                              has nothing left to land, else it goes back on
                              the branch; a refused landing goes back on the
                              branch too. Once every record is written, a
                              landing that leaves nothing to land and names
                              no --part releases the worktree (`builds
                              release`; a refusal keeps the claim and fails
                              nothing). The repo's `whole` checks and its
                              .land-compile (the compile check of the touched
                              crates) run on the result before the push,
                              fast-forward included, each whole check's time
                              printed; a failure names every failing check
                              with its output, pushes nothing and puts the
                              worktree back on its branch. --done N finishes
                              item N and --part N records a landed part of it
                              (checked before anything is fetched, recorded
                              after the push). Commits that change design
                              places need --design N, an approved design
                              change, and commits that are all design files
                              take it alone (`builds help lists`). In a repo
                              of a project, `review check-landing` runs before
                              anything is fetched and its refusal ends the
                              landing; `review landed` runs after the push,
                              beside the items' and the design change's
                              records. Each record names the worktree, and
                              land reads who landed from the worktree's
                              claim and passes it to each record as --by, so
                              in a repo of a project land refuses an
                              unclaimed worktree before it fetches anything.
                              `item check-landing` refuses an item that runs
                              in another worktree: landing there would move
                              that agent's HEAD
  builds review [run] <worktree> [<base>] [--landing <key>] [--item N]... [--head SHA] [--rules-root DIR] [--reviewer PROGRAM]
                              review the worktree's commits past <base>
                              (default origin/main) against the rules in
                              --rules-root (default the agent-instructions
                              checkout linked at ~/.codex/agent-instructions),
                              one reviewer per group, or per changed file for a
                              group that lists sites. PROGRAM (default claude)
                              runs each reviewer. <key> names the change and
                              defaults to the worktree's branch
                              (branch:<name>); a key opens a landing under
                              review, which stays open until its change lands.
                              No diff is reviewed more than once. Each change
                              gets one review; the coordinator reads the fixes
                              for its confirmed findings. A run on a key
                              reviewed already is refused, naming the review
                              and the commits it did not read, unless a group
                              gave that review no answer: then it asks only
                              those groups, over the diff the review read.
                              --head SHA reviews the commits up to SHA from a
                              copy of their files, not the worktree. Prints
                              the findings by group and a total line, then
                              what `builds land` would say of the branch's
                              commits, and exits 1 unless land would take
                              them. While
                              it runs it holds a lock file named for the
                              reviewed commit in the store folder's
                              reviews-running, which the dashboard reads
  builds review settle <finding> confirmed|dropped --why <text>
                              the coordinator's verdict on a finding, kept with
                              who and when
  builds review fixed <finding> <sha>
                              name commit <sha>, of the repo the command runs
                              in, as the fix of confirmed finding <finding>,
                              with who and when; a later call names another
                              commit in its place. builds does not review the
                              fix: the coordinator reads it against the
                              finding before it names it, and land takes it
                              with the reviewed commits. Refused for a finding
                              that is not confirmed, that an audit raised, or
                              whose change landed already
  builds review show <landing>
                              the review of a landing under review: the
                              commits it read, groups, findings, how each was
                              settled and fixed, and the run it landed with
  builds review check-landing <worktree> --project P <sha>... [--rules-root DIR]
                              what `builds land` asks before it fetches: says
                              that the commits need no review, or which
                              change's review takes them, or why the review
                              does not take them yet (exit 1): no review read
                              any of them, a group with no answer over a
                              reviewed commit, a commit that is neither
                              reviewed nor a named fix, an unsettled finding,
                              a confirmed finding with no fix or with a fix
                              outside the commits
  builds review landed <worktree> --project P <sha>... [--rules-root DIR] [--roll N] [--reviewer PROGRAM]
                              what `builds land` records after the push: the
                              landing under review whose review takes the
                              commits landed, with its review run, written by
                              --by, else the worktree's claim. A change
                              recorded already is left as it is, so the rerun
                              land prints is safe. It then decides whether the
                              landing is audited and, when it is, starts
                              `builds review audit` in the background, which
                              never fails a landing. About 5% of landings are
                              audited; 25% when a group the landing ran has
                              missed more in its latest 10 audits than before;
                              and every landing until 20 have been reviewed
                              under the current groups. --roll N (0 to 1)
                              replaces the random draw
  builds review groups [--rules-root DIR] [--project P] [--changed PATH]...
                              list the groups of rules, and fail naming every
                              rule outside a group folder (one with no
                              group.toml) and every project-rules folder that
                              names no group folder; with --changed, list instead the
                              groups a change to those paths runs, over
                              project P's rules (none: every project's)
  builds review replay [--case NAME]... [--source REPO] [--model <model>] [--rules-root DIR] [--reviewer PROGRAM]
                              run the grouping of the checkout (--rules-root)
                              over every case in its review/cases folder (a
                              change as `git format-patch` output, and
                              expected.toml: the findings it must produce by
                              rule and file, and the rules that must raise no
                              blocking finding on it). Prints each
                              case's findings found and missed, then recall,
                              false blocking findings on clean cases and
                              tokens, and for the sites an expected.toml
                              labels, the labelled sites found and the findings
                              on `none` sites, per group and rule; each
                              replayed case goes in its project's store.
                              --source REPO gives each reviewer the commit a
                              case came from, and --model runs every group on
                              one of opus, sonnet and haiku
  builds review replay --landing N... --repo-dir DIR [--group NAME]... [--model <model>] [--rules-root DIR] [--reviewer PROGRAM]
                              ask again over each diff the reviews of landing
                              N read, with the groups and rules of the
                              checkout (--rules-root), only the groups --group
                              names when given, every group on --model when
                              given, and no brief. DIR's repo gives the diff
                              by the run's base and head, or, when it lacks
                              them, by the commits among its newest 1000 that
                              carry the run's patch ids, one after another.
                              Prints each diff's new findings, then per group
                              and rule the counts of the recorded reviews
                              ("in use") beside the replay's, over the rules
                              the replay asked, with each side's setups,
                              calls, tokens and cost. Each replay goes in the
                              store. Exits 1 when a diff could not be read or
                              a call gave no answer
  builds review audit <landing> --repo-dir DIR [--rules-root DIR] [--reviewer PROGRAM]
                              audit a landing whose change landed, over the
                              commits of the run it landed with, read in DIR's
                              repo: one reviewer per rule that covers a changed
                              path, and one review with those rules shuffled
                              into other groups. A finding in a rule and file
                              that the landing's reviews did not raise is a
                              candidate miss, printed with the command that
                              settles it. A confirmed miss becomes a case
                              (`review case add`) and a fix item
  builds review misses        the candidate misses nobody has settled
  builds review rates [--rules-root DIR]
                              each group's audited miss rate: audits, confirmed
                              misses, and the latest 10 audits
  builds review scores        the reviews' scores from every settled finding
                              and confirmed miss in the store: per group, each
                              setup (model and the first 8 digits of its
                              prompt's hash) with the rules commits it read,
                              its calls, tokens and cost, its TP, FP, FN, TN,
                              unsettled findings, precision and recall, then
                              the same per rule; then what audits and
                              replays cost. A call made before builds
                              recorded cost counts as "cost not recorded"
  builds review case add <landing> <finding> --repo-dir DIR --rules-root DIR [--name NAME]
                              add the change of a confirmed finding as a case
                              expecting it, written in the review/cases folder
                              of the agent-instructions worktree --rules-root
                              names (never a default: the main checkout is the
                              person's)
  builds review case add --rule SLUG --file PATH --commits BASE..HEAD --project P --name NAME --repo-dir DIR --rules-root DIR
                              add a confirmed miss the same way; --clean-for
                              SLUG in place of --rule and --file adds a change
                              that rule must stay quiet on

  builds install              copy builds onto PATH in one rename (a failed
                              build leaves the installed one), create the
                              shared caches and their links (moving a real
                              folder already there onto the volume), write the
                              sccache config, run the sccache server under
                              launchd (restarting it only when its settings
                              changed, since a restart fails every compile in
                              flight), point Xcode's default DerivedData at the
                              volume, and restart a running dashboard so it
                              runs the new code. Run it from a fresh build
                              (install.sh does), never from the installed
                              binary, which can't copy itself onto itself
