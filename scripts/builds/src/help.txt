builds: runs this Mac's build volume (/Volumes/Builds), the repos' side
worktrees and their builds, the app build lanes, the pre-commit hook's checks,
the review of each branch against the rules, and landing. Agents run every
cargo command, app build and landing through it.

More help:

  builds help workflow  how work moves through worktrees, builds and landing,
                        and how a coordinator runs agents
  builds help lists     a project's decision stack, work queue, decision log
                        and design changes, and their commands (builds
                        lists, question, item, next, area, decision, design)
  builds help briefs    the instructions a coordinator gives an agent that
                        writes implementation briefs

builds is a Rust program in agent-instructions (scripts/builds).
agent-instructions' install.sh builds it from the main checkout's committed
HEAD, never from the working tree, with the libraries it is built with: the
shots checker, which `builds shots` runs (scripts/shots), and the boards
library (scripts/boards). install.sh then runs `builds install`, which puts
builds on PATH as ~/.local/bin/builds. Agents change
agent-instructions the way they change bae and coven: on a branch in a side
worktree from `builds new ~/dev/agent-instructions --for <who> --project
builds` (or `--project bae` for bae's rules and project file), reviewed and
landed (`builds help workflow`).
The main checkout is the person's, and it is the live copy: install.sh links
its files into ~/.claude and ~/.codex. Its post-commit and post-merge hooks run
install.sh again when a commit or merge on its main branch changes what
install.sh consumes, scripts/builds/ included. A commit on a side worktree's
branch installs nothing; it goes live once it is on main and the main
checkout's main moves to it, which `builds land` does after each landing, as
it does in every repo (LANDING AND REVIEW). To try an edit to builds before
`builds land` puts it on main, run the binary your worktree built
(scripts/builds/target/debug/builds).


ACKNOWLEDGING THE RULES

builds refuses every command an agent runs, except `help`, `ack`, `agent`,
`install`, `dashboard` and `version`, until the agent has read the text every agent reads
before it works and has acknowledged it with `builds ack`. The text is
~/.claude/CLAUDE.md, the CLAUDE.md of the repo the command runs in, `builds
help workflow` (without its WHAT REVIEWS CONFIRM MOST OFTEN section, which
changes with each settled finding), the overview that opens `builds help
lists`, and the rules of agent-instructions whose paths cover every file
(those under rules/ and under the project's projects/<project>-rules/). An
edit of any of them changes the text's version. Each repo's text holds that
repo's CLAUDE.md, so builds keeps an agent's acknowledgement of each repo's
text apart: an agent that acknowledged the texts of bae and coven runs
commands in either repo without reading again, until that repo's text
changes, 12 hours pass or Claude Code compacts the agent. The rest of this
help, and of `builds help lists` and `builds help briefs`, is for looking up
what a command does.

  builds ack [--agent ID] [--project P]
      Start a reading: say the text's version and how many parts it comes
      in, and pick the words to blank in every part. builds keeps the
      sections of the 20 versions of the text that agents acknowledged most
      recently. When builds keeps the version of this repo's text that the
      agent last acknowledged, and the agent acknowledged it at most 12
      hours ago, the reading holds only the sections that changed since,
      each in full, and says which ones changed. Otherwise the reading holds
      the whole text.
  builds ack PART [--agent ID] [--project P]
      Print part PART of the reading. Each part blanks one word in each
      third of its lines, in running prose, as the word's first letter and an
      underscore for each other letter; no line holds an answer, so the agent
      reads the text around each blank to know the word. Reading a part again
      blanks the same words.
  builds ack VERSION WORD... [--agent ID] [--project P]
      Acknowledge version VERSION, giving the blanked words of every
      part, in the order they appear. When a word is missing or wrong,
      builds refuses the acknowledgement and names the parts to read again.
  builds ack --compacted
      Claude Code's SessionStart hook runs this after Claude Code compacts
      an agent (claude/settings.json in agent-instructions). builds deletes
      every acknowledgement and the reading of that agent in every project's
      store, and tells the agent its id again, so the agent reads the text
      again before its next builds command and every other agent keeps its
      acknowledgements. builds refuses an agent no hook registered, and
      deletes nothing.
  builds agent start
      Claude Code's SessionStart hook (when a session starts, resumes,
      clears or forks) and its SubagentStart hook run this. builds reads the
      hook's input, registers the agent's id in the session, and adds "Your
      builds agent id is ID. Pass --agent ID to every builds command ..." to
      the agent's context.

builds never refuses the person's own commands: it tells an agent's command by
the Claude Code session id in its environment (CLAUDE_CODE_SESSION_ID), which
the person's terminal lacks. No agent commits in a repo's main checkout, so
builds also passes the pre-commit hook's `builds checks run` there, even when
the person's Claude Code session makes the commit, and `builds status --json
--no-folders`, which the hook against unlocked app-checkout moves runs before an
agent acknowledges. The agents a session dispatches share its session
id, and no shell of an agent sees anything that tells the agents apart, so
builds names an agent by the session and the id Claude Code gives the agent. A
subagent's id is the id the hooks' input names (agent_id); the main agent has
none, and its id is its session id. `builds agent start` registers each id in
<the lists folder's parent>/agents/<session>/<id>, which every project reads.
An agent passes its id to every builds command with --agent ID, anywhere
before a `--`, or sets BUILDS_AGENT=ID in front of a script that runs builds
(BUILDS_AGENT=ID scripts/cargo.sh test). builds refuses a command that names
no id, or an id no hook registered in the session, and says where the agent
finds its id. builds keeps the acknowledgement in the store of the project
whose repo the command runs in, else of the project --project names. builds
refuses an agent whose acknowledgement there of the repo's text is missing,
is of another version, or is more than 12 hours old, and names what changed
since the agent's last acknowledgement of that text. A builds command that
passed lets the builds commands it runs pass too, such as a commit hook's
checks or the install after a landing.


BUILD VOLUME

Every build on this Mac writes to the build volume, and builds owns everything
on it:

  <repo>/<checkout>/    one build root per checkout (main or side-N)
  <repo>/app-checkouts  the mac lane's app checkouts, one per line: the name
                        alone for one a person added, and the name, `builds`,
                        the time and why for one builds added
  <repo>/app-checkouts-removed
                        the checkouts builds removed from the lane in the
                        last 12 hours, one per line: the time, the name and
                        why
  <repo>/app.locks/     one lock per app checkout (app.locks/side-N), held by
                        the build that runs there, and beside each lock the
                        record that build keeps (side-N.run): when it joined
                        the queue, how long it waited, and the step it runs;
                        and when the last build there let the lock go
                        (side-N.ended)
  <repo>/app.queue/     the builds waiting for the lane's locks: `order` holds
                        one ticket per line, next first, the holders' tickets
                        among them, and each process in line holds a ticket
                        file named <pid>-<n>-here|hosts|anywhere, for where
                        its build may run
  <repo>/app-android-checkouts, app-android-checkouts-removed,
  app-android.locks/, app-android.queue/
                        the same for the android lane
  .app-hosts/<host>     a lock builds holds while it counts the host's app
                        checkouts and adds one there, so builds of two lanes
                        never pass the cap of checkouts on a host together
  DerivedData/          Xcode's default DerivedData location
  caches/<name>/        the download caches every checkout shares
  shots/<repo>/runs/    the output of each shots run (APP BUILDS), one folder
                        per run under <commit>/<lane>/<prefix>/<version>/
  shots/<repo>/pictures/
                        the board pictures shots runs drew, by board hash,
                        and the shots the apps took, by app source tree (APP
                        BUILDS)
  review-texts/<project>/<run>/
                        the texts of each review run (DISK), one file per
                        text, named for the text's hash
  .trash/               folders being deleted in the background
  .trash.lock           taken shared by each deletion into .trash, and
                        exclusive only by the floor and prune, to rename
                        .trash to .trash-emptying.<random>/ and empty it

`builds status` lists each of these and flags anything else on the volume as
UNKNOWN (it leaves out macOS's own volume metadata, such as .Spotlight-V100 and
.fseventsd). Something UNKNOWN is either a new kind of build output that builds
should own or a leftover to delete: find out which.


BUILD FOLDERS

Each checkout has one build root, /Volumes/Builds/<repo>/<checkout>/. The repo
lists its build output folders in `.build-dirs` at its root (cargo's target,
Xcode and SwiftPM .build folders, Gradle's build and .gradle, dotnet's obj and
bin, Lean's .lake), and each listed path is a symlink in the checkout to the
same path under the checkout's build root (target ->
/Volumes/Builds/bae/main/target). `.build-dirs` has one line per folder, a
`keep` line for each build that must stay, an `installed` line for each
tool the repo's scripts install into the user's cache home, a `prepare` line
for each program that puts in place what the checkout's builds need, a
`tool` line for each tool the repo builds from its own sources (BUILT TOOLS),
a `linux-package` line for the Debian packages a Linux host needs to build the
repo, and a `macos` line for the repo's packages that only a Mac builds:

  <path> <cap>              the folder and its size cap
  <path> <cap> app <cap>    a second cap, for the folder in the repo's app
                            checkouts
  ... lane mac|android      after the caps: only that lane's app checkout
                            builds into the folder, keeps it built and takes
                            its app cap; in the other lane's app checkout it
                            is an ordinary side worktree's folder. A folder
                            with no lane (host target) is every app
                            checkout's
  keep <path>               a build inside a folder that never ages out in
                            main and the app checkouts, where the person runs
                            the app built there (bae:
                            bae-macos/bae/.build/runApp)
  installed <folder> <file> a tool a script installs once per version into
                            <folder> in ${XDG_CACHE_HOME:-~/.cache}, one entry
                            per version, named after it; <file> in the
                            checkout names the version it runs (bae:
                            owner-construction-check
                            scripts/owner-construction-check.sh)
  prepare <program>         a program of the checkout that `builds setup`
                            runs in its top folder, and `builds cargo` before
                            cargo on whichever host runs cargo. The program
                            puts in place what the checkout's builds need
                            beyond their folders, such as a toolchain
                            component or a source that builds compile against
                            (coven: tools/typed-lints/prepare-build.sh). It
                            finishes at once when all of it is in place, runs
                            again each time, so it notices a moved toolchain
                            pin, never runs `builds cargo`, which would run it
                            again, and never asks for a password, since nobody
                            is at a host's screen. When it fails, setup and
                            `builds cargo` fail, naming it. A `builds cargo`
                            that a pre-commit hook check runs (COMMIT CHECKS)
                            runs no prepare program, since a hook installs and
                            fetches nothing: when a piece is missing, the
                            check's build fails and the check names `builds
                            setup` (coven: tools/typed-lints/cargo.sh names
                            the missing path)
  tool <name> <program> <link>
                            a tool the repo builds from its own sources for
                            its toolchain, which builds keeps once per key on
                            each host and links at <link> in the checkout
                            (BUILT TOOLS)
  linux-package <name>...   Debian packages a Linux host needs to build the
                            repo, such as clang for a crate that runs
                            bindgen; `builds host setup` installs them on
                            each Linux host (HOSTS)
  macos <package>...        cargo packages part of whose code compiles only
                            for macOS: on Linux, a cargo job that builds one
                            compiles and checks other code than on a Mac, so
                            `builds cargo` sends it to no Linux host (CARGO)

Tools always write through <checkout>/<path>, so the path a build sees never
changes, however often builds deletes and recreates the folder behind the link.
sccache's keys and cargo's fingerprints stay valid, and two checkouts never
share a folder, so their builds never wait on each other's locks. Every build
follows these rules:

  - Never set CARGO_TARGET_DIR, in the shell profile or on a command: the
    checkout's target link is the target folder. Two checkouts that build
    into one folder wait on cargo's lock and then rebuild what the other
    changed.
  - Never set another CARGO_* variable on a command or in a script (such as
    CARGO_INCREMENTAL or CARGO_PROFILE_*). sccache keys every CARGO_*
    variable, the working directory and the paths cargo passes, so a build
    with another path or another variable gets no cache hits. A setting goes
    in a --config argument or in Cargo.toml.
  - Never set RUSTC_WRAPPER="": it turns sccache off, and nothing on macOS
    needs that.
  - Never point a build at /private/tmp or the user's temporary folder (a
    -derivedDataPath there, a probe crate built where it was made): build in
    a checkout, whose paths lead to the volume.
  - A build script in a linked worktree finds shared refs through `git
    rev-parse --git-common-dir`: the worktree's own git dir has no refs/tags,
    and a build script that watches a missing path reruns on every build.

A link whose folder is gone breaks every tool (cargo fails with os error 20,
xcodebuild with code 74, Gradle with "Could not open file hash cache"), so the
repo's scripts/build-layout.sh runs `builds setup`, which recreates the folder,
and the hooks and every build script run that script first. Without builds (in
CI) the script does nothing and the tools write into real folders.

The Claude Code session's rust-analyzer, which agent-instructions'
rust-analyzer plugin (claude/plugins/rust-analyzer) starts, builds into
target-ra, a .build-dirs entry with its own cap in bae and coven, and checks
nothing on save: its `cargo check --workspace` of everything held main's target
over its cap. A Rust repo with no target-ra entry gets a real target-ra folder
in its checkout. The plugin passes these options at initialization, because
rust-analyzer reads a repo's rust-analyzer.toml only after its first build has
started into target.

  builds setup [--no-prepare] [<checkout>]
                              link the checkout's build folders, recreate any
                              that is missing, delete folders an older layout
                              left behind, apply the disk rules (DISK, below)
                              to the checkout, DerivedData and the shared
                              caches, delete idle build output in the
                              temporary folders, keep the free-space floor,
                              and then run the checkout's `prepare` programs,
                              install elan and the toolchain each of its Lean
                              packages pins (LEAN), put the build of each of
                              its tools in place and copy those builds to
                              each host that lacks them (BUILT TOOLS). builds
                              runs it when `builds new` hands out a worktree,
                              on a host before each job, and from each repo
                              script that calls it. --no-prepare leaves out
                              the prepare programs, the Lean toolchains and
                              the tools: a host's setup for a job that a
                              pre-commit hook check started takes it


LEAN

A Lean package of a checkout is a folder whose .lake build folder the repo's
`.build-dirs` lists and which holds a lean-toolchain file, the toolchain that
lake builds the package with (coven: crates/sqlive/proofs and each package in
spec/proofs). `builds setup` installs elan, Lean's toolchain manager, under
~/.elan on the Mac it runs on when that Mac has none (elan 4.2.4), and then
each toolchain the checkout's packages pin that elan does not list. Setup runs
on a host before each job, so every host that builds a checkout with Lean
packages has their toolchains. elan downloads each toolchain once per Mac,
and every checkout shares it. A Mac that already has another version of elan
keeps it. A `.lake` folder with no lean-toolchain beside it pins nothing.

`builds lake build` runs lake build in the package of the working directory,
on the host with the most room, as `builds cargo` runs a test (CARGO): builds
skips the same hosts, sends the checkout's HEAD plus its working tree, and
runs lake in the matching folder of the host's remote worktree, whose .lake
folder stays between jobs in the host's builds root. The host's setup for the
job installs the toolchains, so a host needs nothing else. One line on stderr
names the host, and the command prints lake's output and exits with lake's
status. These stay on this Mac: every command in a main checkout, a command
run outside a checkout, and a command with an argument that is an absolute
path. On the Mac that runs lake, builds first installs the checkout's
toolchains, unless a pre-commit hook check runs it, and holds the checkout's
guard while lake runs, so no prune deletes the .lake folder under it.
BUILDS_CARGO_HOST picks the host for one command, as for `builds cargo`.

A cargo test that runs a Lean executable, such as coven's narrowing
differentials, which run the runner that SQLIVE_NARROWING_LEAN names, names it
in BUILDS_CARGO_LEAN instead of building it first:

  BUILDS_CARGO_LEAN=SQLIVE_NARROWING_LEAN=crates/sqlive/proofs:narrowingRunner \
    scripts/cargo.sh nextest run -p sqlive --all-features --run-ignored only \
    -E 'test(term_matches_lean)'

The Mac that runs cargo, a host or this Mac, builds the runner from the same
working tree with `lake query`, under the checkout's guard, and gives cargo
the runner's path there, so the tests and the runner they run always come
from one Mac. The host gets BUILDS_CARGO_LEAN as it is, since it names the
package by its folder in the checkout.

  builds lake build [<args>...]
                              run lake build with these arguments in the Lean
                              package of the working directory, on this Mac or
                              the host with the most room; builds refuses
                              every other lake command: run those with lake
                              itself (~/.elan/bin/lake)


BUILT TOOLS

A `tool <name> <program> <link>` line names a program the repo builds from its
own sources for its toolchain, such as coven's typed lints' driver, a build of
clippy's driver with coven's lints added. builds keeps one build of the tool
for each key on each host, shared by every checkout of every repo whose key is
the same, and builds it on a host only when no other host of its platform has
it. A platform is an OS and a processor, such as macOS on arm64 or Linux on
x86_64: a build runs only on its own platform.

The repo's <program> answers two requests in the checkout's top folder:

  <program> key             print the checkout's key: two words, the
                            toolchain's id (coven: the commit its rustc was
                            built from) and a hash of the tool's sources
  <program> build <folder>  build the tool into <folder>, an empty folder
                            builds made, and write
                            <folder>/check: a program that makes the build
                            ready to run on the host it is on and fails unless
                            the tool runs there. BUILDS_TOOL_WORK names a
                            folder, one per toolchain on each host, where the
                            program keeps what the next build can reuse, such
                            as a fetched source and a cargo target folder, so
                            a new key compiles only what its sources changed

Each key's build is the folder caches/tools/<name>/<toolchain>/<sources> on
the build volume (a host's builds root on a host), and <link> in the checkout
points at it. To put a key in place, builds copies the folder from another
host of the same platform that has it, else builds it, holding the toolchain folder's lock so one
build at a time uses the work folder. When it builds, it says why no copy
served: each host lacked the key, did not answer, or sent a copy that failed.
Each copy and each build goes into a staging folder of its own, and takes its
place only once its check passes on the host it lands on. builds deletes a
rejected staging folder before it tries the next way, and when it cannot, it
stops with an error that says both why it rejected the folder and why the
deletion failed. `builds setup` copies each key of the checkout that this Mac
has to each host of this Mac's platform that lacks it, and so does a `builds
cargo` job before it runs on such a host, and each copy runs its check on the
host; when that fails, builds says so and the host builds the key in the job's
setup. A host of another platform, such as a Linux host, builds each key in
the job's setup itself. A pre-commit hook
check installs, fetches, copies and builds nothing, so the first `builds
cargo` after a change to a tool's sources puts the new key's build in
place on the Mac that runs cargo, before cargo, and the hook's checks find it
(a run inside a tool's own build, BUILDS_TOOL_WORK set, builds no tool, since
that build holds the key's lock): a `builds cargo` the hook runs
sends no key to the host, the host's setup for its job prepares nothing, and
`builds tool` only points the link at a build the Mac already has. `builds setup` and `builds prune` delete each key's folder,
and each toolchain's folder with its work folder, that no live checkout's key
names. They delete nothing of a tool whose key a checkout fails to print, and
nothing of any tool while a checkout's `.build-dirs` cannot be read.

A repo's script may run a tool as cargo's workspace wrapper through the tool's
link: coven's clippy sets RUSTC_WORKSPACE_WRAPPER to
tools/typed-lints/built/typed-lints-driver. cargo puts the wrapper's path
into the name of each workspace crate's output, and when a crate's sources
have not changed it prints that crate's last warnings again instead of
compiling it. The link's path stays the same when the link moves to a new
key's build, so cargo would print the old build's lints for each crate whose
sources did not change. So `builds cargo`, on the machine that runs cargo and
after the BUILDS_CARGO_BEFORE program, gives cargo the same file in the
key's build folder that the link points at. A new key lints every crate
again, with no source file touched, and a second run with the same key prints
the warnings cargo kept. A wrapper under a link that points at no build fails
the command, naming `builds tool`.

  builds tool <name> [<checkout>]
                              put the checkout's key of tool <name> in place
                              on this machine, point the checkout's link at it and
                              print its folder. A repo's script runs it before
                              it runs the tool, wherever cargo runs: coven's
                              clippy names a script that runs it in
                              BUILDS_CARGO_BEFORE. Run by a pre-commit hook
                              check (BUILDS_HOOK_CHECK set), it only points the
                              link at the build this machine has for the key,
                              and when it has none it fails at once, naming
                              `builds setup`


WORKTREES AND CLAIMS

Each repo has a main checkout, the person's, and side worktrees for agents at
<parent>/<repo>-worktrees/side-N. side-1 is long-lived; `builds new` hands out
the others and `builds prune` retires them once they are idle.

A claim records who works in a side worktree, so that no other session takes
it: whoever hands out the worktree (a coordinator dispatching an agent, or the
person) claims it. A landing that leaves nothing to land releases it (`builds
land`); whoever handed it out releases it when the work stops, once the
worktree holds nothing origin/main lacks: release refuses a worktree when
releasing it would leave its work with no claim and no item (`builds item stop`
keeps the work with its item instead). A local branch with commits waiting to
land that no worktree checks out and no open item names is work left behind
too: `builds health` lists it, with `builds new <repo> --resume <branch>` to
check it out in a worktree. A claim is a file in the worktree's git dir, so
retiring the worktree deletes its claim; `status` shows it, and `retire`
refuses a claimed worktree. A claim is not a lock: an agent runs a series of
separate commands, so nothing could hold one, and a session that ends without
releasing leaves its claim behind, with its age in `status`. Exclusive use for
one command, such as a build in an app checkout, takes a real lock.

A claim may carry a one-line note that says what its work waits on ("waiting on
Linux CI"), which `status` and the dashboard show, and the note may carry a
state that git can't show:

  waiting-on-you  the work waits on a question or a step only the person can
                  take
  winding-down    the agent is on its last item, then its handoff
  starting        `claim` and `new` set it, with the note "claimed; its item
                  is not yet taken", on a claim for an item that `item take`
                  has not started there; take clears it, `note` never sets
                  it, and `health` never releases a claim that carries it
  held            the worktree is kept on purpose with no work running, such
                  as uncommitted work waiting for another change to land; the
                  note says why and until when. A held worktree needs a
                  running item that waits on an open record, and `health`
                  doesn't call it idle while that record stays open; once the
                  record closes, `health` lists the worktree

A note set without --state has no state, so writing the next note clears the
state. Claiming the worktree again for the same <who> renews the claim's date
and keeps the note.

The dashboard gives each side worktree the first state that matches: Waits met
(no claim, and an open item keeps the worktree with every wait met: land its
commits or resume its agent), Waiting (no claim, and an open item keeps the
worktree while it waits on an open record: the card names each), Ready (no
claim, and an open item with no waits keeps the worktree with its unfinished
work: `builds item stop`, `builds help lists`), Can't read what this worktree waits on (the daemon could
not read what a running item waits on, and the card says why), Waiting on you
(the claim's note says so, a running item waits on a question or on a design
change the person has not approved, or the worktree's commits are a design
change the person has not approved whose rules review takes them), Paused (the claim's note has --state
held: the card says what its running items wait on), Ready to land (commits
waiting to land, claimed or not: an unclaimed worktree with such commits holds
work an agent left behind; a claimed one waits for its agent to land it),
Winding down, Working (claimed) and Free. Commits
waiting to land show as Ready to land only when `builds land` would take them
as far as the rules review goes; until then the card shows the review's
progress instead: Needs review (no review read these commits, or a group still
has to answer: the branch's agent runs `builds review`), Reviewing (a review
of the branch's newest commit runs), Findings to settle (with the count, and
whether they wait on the judge or, with no judge listening, the coordinator),
Open
findings (confirmed findings that wait for a review that closes them) or
Unreviewed changes (with the count of files that changed since the last
review, which `builds review` reads as a new run of the review). A commit
waits to land while origin/main has no commit with the same change (`git log
--cherry-pick --right-only origin/main...HEAD`), because landing rebases or
cherry-picks it.
The dashboard daemon records each change of a card's state, at most every 5
seconds, in the store of the card's project: the time, the state and the items
the card lists. The daemon judges the state with the same code that draws the
card, and records nothing until it has read the processes once. `builds item
times` reads these records.

  builds new [<repo>] [-b <branch> | --resume <branch>] [--for <who>]
             [--project P]
                              hand out a free side worktree with a fresh
                              branch from origin/main, or add the next side-N
                              when none is free; link it and run its
                              post-checkout, which builds nothing. A free
                              worktree is not an app checkout, has no claim,
                              and passes the check `release` makes: no item of
                              any project runs in or keeps it, its tree is
                              clean, no `git commit` runs there, and every
                              commit on its HEAD and on each branch it left
                              since its last claim began is on origin/main by
                              patch. new checks every worktree before it
                              changes one, and it moves and deletes no
                              branch: -b refuses a branch name that exists.
                              new claims the worktree for <who> (default
                              "builds new") under a lock on the repo, so two

                              the worktree's host target is empty, new fills

                              little. --project P records which project's work

                              left on a branch goes back into a worktree this
                              way

                              record that <who> works in the side worktree

                              worktree left from that claim's start

                              the worktree held, or ends its hold, starts or

                              (`builds item times`)
  builds release <checkout>   remove its claim; refused while an item of any
                              project runs in the worktree, and while it holds

                              on HEAD, on a branch the worktree left since its

                              person throws work
                              away, by dropping its item. `new` hands out no
                              worktree that this check would refuse

CARGO

Run every cargo command through `builds cargo`; in bae and coven,
scripts/cargo.sh runs it, and the hooks and build scripts use that script.
builds reads cargo's report of each build to record the build copies it used
(DISK, below). cargo typed by hand records nothing, so builds deletes what only
it uses three days after cargo last built it.

`builds cargo` runs every build with --locked, unless the command passes
--locked or --frozen itself. When a commit's Cargo.lock disagrees with its
Cargo.toml files, cargo fails, names the cause and leaves the lock as the
commit has it.

`builds cargo update` rewrites Cargo.lock: run it after you change a
dependency's version, or a git dependency's rev, in a Cargo.toml, and name each
package whose entries change (`builds cargo update -p coven`). builds runs
cargo update as given, on this Mac in the working directory, without --locked,
and refuses an update that names neither a package nor the workspace (-w), since
cargo would then move every dependency in the lock to its newest compatible
version. An update builds nothing, so builds records no run and no build
copies for it.

`builds cargo mutants` runs cargo-mutants (scripts/cargo.sh mutants in bae and
coven) on the host with the most free cores, placed as the runs below are
(HOSTS says which hosts take a run), except that no host counts as warm for it:
cargo-mutants copies the workspace and builds the copy afresh. builds caps the run's `--jobs` by the
room under the chosen host's load band: the band's high end less the host's
5-minute load average, rounded down, and at least one (this Mac's band when the
run stays here or the host refuses it). A run that asks for more
jobs gets the cap, and one line on stderr says so; a run that names no jobs
keeps cargo-mutants' one. Each job builds and tests a whole copy, so a run
over the whole workspace takes hours: scope it to the code that changed with
`--file`, once for each file (`scripts/cargo.sh mutants --file
src/queue.rs --file src/queue_tests.rs -p bae-queue`), or with `--in-diff
FILE` for a diff, and look at what a run would test first with `--list`.
cargo-mutants has no cargo message format for builds to read, so builds
records no build copies for it. builds skips a host without cargo-mutants at
the one version builds installs (27.1.0, installed by `builds install` on this
Mac and by `builds host setup` on each host, compiled there with `cargo install
--locked`), as it does for nextest below.

`builds cargo` also runs the subcommands that only read the workspace: tree,
metadata, locate-project, pkgid and verify-project. builds runs each on this
Mac in the working directory with --locked, as it runs a build: without
--locked, cargo rewrites a Cargo.lock that disagrees with the manifests.
builds adds nothing else to a read, and records no run and no build copies for
it. builds refuses every other subcommand that builds nothing, such as fmt and
clean: run those with cargo itself.

Every checkout but main builds without incremental compilation (`builds cargo`
passes --config build.incremental=false), the app checkouts included. sccache
refuses every incremental compile, so with incremental off sccache keeps each
workspace crate a checkout built, and the checkout gets it from the cache when
it builds the same sources again, as an app checkout does when agents move it
back to a branch it built before. sccache's key holds the folder cargo compiles
a crate in and every CARGO_* variable, CARGO_MANIFEST_DIR among them, and cargo
compiles each workspace crate in the checkout's top folder, so a workspace
crate one checkout built never serves another checkout. A crate from a
registry or a git source compiles in cargo's shared source folders, so its
cached build serves every checkout. The only incremental folders are those a
repo's lint wrapper keeps for the crates it lints (DISK). A full build without
incremental output is smaller, so the app checkouts' folders take lower caps.
Main, the person's checkout, stays on one branch and keeps incremental. To turn
incremental on in a profile, set profile.dev.incremental in Cargo.toml, never
CARGO_INCREMENTAL=1, with which sccache refuses every compile.

In a side worktree, `builds cargo` runs test, clippy, check, doc and nextest
run|list on the host that ran the checkout's last run of the same subcommand,
which `builds cargo` reads from the runs it records, while that host can take
the run. Each host keeps its own build folder for the checkout, and only the
host of the last run has that run's build. Another host's folder for the
checkout may be cold, and there cargo compiles again everything that changed
since that host's last build for the checkout. When no host ran the
subcommand for the checkout, or that host cannot take the run now, builds
runs it on the host with the most free cores, each counted at the host's core
speed. builds skips a host that does not answer, is under the free-disk
floor, refuses jobs (HOSTS), has no measured core speed (`builds host setup`)
or has no clone of the repo. A job that builds a package that a `macos` line of
the checkout's `.build-dirs` names (BUILD FOLDERS) skips every Linux host: the
job builds the packages its -p arguments name, with none every package with
--workspace, else the package of the folder it runs in, or every package in
the workspace's own folder. One line on stderr names each host the job skips
for that reason. For a nextest run, builds also skips a host
without cargo-nextest at the version builds installs (0.9.143, installed by
`builds install` on this Mac and by `builds host setup` on each host), and
names the host and the version it has (a mutants run skips a host the same way
for cargo-mutants); `BUILDS_CARGO_HOST` naming such a host
fails. A host's free cores are its cores minus its
one-minute load, less the host's cores again for each `builds cargo` or
`builds lake` run that started there in the last minute and still runs: cargo
and lake run a compile job per core, and the load average shows a run only
after a while. A host's core
speed is this Mac's time divided by the host's time for one fixed compile on
one core, which `builds host setup` times on both, so a job goes where it
finishes first.
This Mac wins a tie. When several runs start at
the same time, builds picks a host for one run at a time, so the runs go to
different hosts. The load average never shows the compiles that wait in
sccache's queue on a host whose cores are all busy, so builds also counts the
`builds cargo` runs it placed on each host that still run. Each host's share
of those runs and the new one is their number split by the hosts' cores,
rounded up, and a host that would pass its share takes no new run, not even a
run whose last run went there, while another host stays within its share. builds sends the checkout's HEAD plus its working tree (staged and unstaged edits, deletions,
and files git neither tracks nor ignores) as a commit to the host's clone only,
runs cargo in a remote worktree there that keeps its build between runs, in the
folder that matches the one the command ran in (cargo picks the package of the
folder it runs in), prints the same output and exits with the same status. The host's cargo gets
BUILDS_CARGO_LEAN, CLIPPY_ARGS, RUSTDOCFLAGS, RUSTFLAGS, RUST_BACKTRACE,
RUST_LOG and RUST_TEST_THREADS from the caller's environment; one line on stderr names the
host. When the host refuses the job before cargo starts there (sending the
commit or claiming a worktree fails there), builds records the host as
refusing jobs, says so on stderr with what the host said, and runs the command
on this Mac. A stop signal stops cargo on the host, and so does the end of
`builds cargo` by any other signal, SIGKILL included, or a connection to the
host that closes: no job on a host outlives the command that started it. A
connection that fails mid-run fails the command, naming the host and each
sleep either Mac recorded meanwhile (HOSTS); builds never runs the command
again here, since cargo may have run part of it there. A landing's
compile check runs `builds cargo`, so it follows the same rules. These stay on
this Mac:

  - every other subcommand (build, rustc, run, bench, install, update, and the
    reads, such as tree and metadata)
  - a command with --message-format, --target, --release or a path argument
    (--manifest-path, --target-dir, an absolute path)
  - a command run with CARGO_TARGET_DIR or FFMPEG_DIR set, or with
    RUSTC_WRAPPER, RUSTC_WORKSPACE_WRAPPER or BUILDS_CARGO_BEFORE set to a
    path outside the checkout (a wrapper given as a bare name, such as
    sccache, is the host's own)
  - every command in a main checkout

To test builds itself, run `builds cargo nextest run --bin builds -E
'test(/^trees::/)'` with a filter for the modules you changed. nextest runs
each test in a process of its own. `cargo test` runs the tests of a binary as
threads of one process, which share one descriptor table: a child that one
test starts holds a copy of every file another test has open, locks included,
until the child execs, so a test that takes a lock without waiting can find it
held and fail only in a run with other tests.

One sccache server serves every checkout. launchd runs it
(local.sccache-server) on sccache's default port, 4226, with the system's
TMPDIR and no idle timeout; its cache is caches/sccache, capped in
~/Library/Application Support/Mozilla.sccache/config. `builds install` writes
both here and on every host, `builds host setup` writes them on a host (whose
cache is sccache's default folder, ~/Library/Caches/Mozilla.sccache on a Mac
and ~/.cache/sccache on Linux). On a Linux host the user's systemd runs the
server from the unit ~/.config/systemd/user/local.sccache-server.service, with
/tmp as its TMPDIR, and its config is ~/.config/sccache/config. `builds status`
flags a config that no longer holds builds' cap, and `builds health` names each
host whose server launchd or systemd does not run, whose config does not hold
builds' cap, or
whose server runs with another cap than its config's: a server reads its
config when it starts, so one that started before builds wrote a new cap keeps
the old one until it starts again.
Never start a server any other way: a server inherits the TMPDIR of the client
that starts it and fails every compile once that folder is deleted, and the
Unix-socket mode (SCCACHE_SERVER_UDS) races when clients start at once and
leaves orphaned servers. sccache never caches build scripts, an incremental
compile or a crate clippy lints, and a crate that reads OUT_DIR misses in each
new checkout. sccache also hashes the bytes of each library a crate names,
and a crate that includes a file its build script wrote, as serde does,
records the OUT_DIR path in its library. So `builds cargo` gives cargo
~/.local/bin/builds-rustc as RUSTC_WRAPPER (a symlink to builds that `builds
install` and `builds host setup` make), unless the caller names a wrapper
other than sccache. builds-rustc runs sccache, and for a crate whose build
script wrote files into its OUT_DIR it adds
`--remap-path-prefix=<OUT_DIR>=/OUT_DIR`, so that crate's library is the same
bytes in every checkout and the crates above it come from the cache. A
repo's own wrapper, such as bae's clippy wrapper, runs builds-rustc where it
would run sccache. sccache hashes each proc-macro a crate names, and ld names a
dylib by its path, so `builds cargo` links this Mac's own target with
~/.local/bin/builds-linker (a symlink to builds that `builds install` and
`builds host setup` make): it runs cc and names each proc-macro dylib
@rpath/<its file name>, so one proc-macro built in any checkout is the same
bytes and the crates above it come from the cache. A cdylib, such as
bae-bridge's, keeps the name ld gives it. `builds help workflow` says when to
restart the server.

APP BUILDS

An app build runs only the test classes and the shots of the screens a change
touches: name each class with --test, and each screen's shots with --shots and
a prefix (mac.welcome. for the Mac welcome screens). CI runs the full suites.
`builds app-build` refuses a --shots prefix that selects every shot of a lane
(mac. or android.) and a step that a `ci-only` line names, and says why.

To run every shot of one lane, pass `--all-shots mac` or `--all-shots android`.
Run it to check a change to the shots program; for a
change to screens, name their prefixes with --shots instead. builds runs the
lane's `shots` line once, with the prefix that every shot of the lane starts
with (mac.), so the run goes where any --shots run of the lane goes: it waits in
the lane's queue, holds a lock of the lane, and takes a free app checkout (for
a `shots` line that passes --windows, only one on a host, as below). builds caches its findings and report
under that prefix like any other shots run's (below), and `builds shots
findings <repo> <ref> mac mac.` prints them again. The shots program takes a
window's shot on the display of the host it runs on, whose size may differ
from that of CI's runner, so a window that fits one display and not the other
can pass on one and fail on the other.

App builds (an Xcode app, a Gradle app, a bridge cross-compiled for a platform)
take 10-20 GB per platform per checkout, so a repo keeps them built only in
main, for the person's installs and releases, and in its app checkouts, one or
more per lane: the long-lived ones a person records with `builds app-checkout`
(side worktrees here, or worktrees on a host), and the ones the builds tool
adds on a host while other builds wait for the lane and removes once no build
uses them.
Every other side worktree builds host output only (for Rust, target, which
tests, clippy and the hook use).

The builds tool adds checkouts to a lane while other builds wait in its queue,
and removes the ones it added that no build uses. A build that joins a lane's
queue and has to wait adds a checkout `builds-<lane>-<n>` on a host, and so
does a build that may run only on a host in a lane with no checkout there.
builds picks the host with the most free cores (its cores less its one-minute
load) among those with at least one core free, free disk above the floor
(BUILDS_FREE_FLOOR_GIB) by one checkout of the lane (about 22 GB for mac and 10
GB for android, as measured on the M1), and fewer than 6 app checkouts in all;
a lane has at most 4. The new checkout's first build makes it on the host, as for one `builds
app-checkout --host` records. A build that waits adds a checkout only on a
host. A build that may run only on this Mac (the android build-app, a mac
build-app or app-build that runs a `here` step) and finds the lane with no
checkout on this Mac adds a new side worktree of ~/dev/<repo>, set up as `builds
new` sets one up and recorded in the lane as the person's, so no `builds new`
hands it out and builds never removes it. A build that joins a lane's queue, and `builds prune`, remove each
checkout builds added that no build has used for 60 minutes, with its worktree
and build folders on the host. A checkout a person added stays until a person
removes it. builds reads and changes a lane's set of checkouts, and a build
takes a checkout's lock, only under the lane's queue lock, so two builds never
add the same checkout and no build takes one that builds is removing. `builds
queue` and the dashboard show when and why builds added or removed each one.

A lane is the part of a repo's app builds that shares no build output with the
other: in bae the mac lane is Xcode and target-macos, and the android lane is
Gradle and target-android. Each lane has its own app checkouts, locks and
queue, so a Mac build and an Android build never wait on each other, and each
app checkout keeps only its own lane's folders built. A checkout is one lane's,
never both. A lane with several app checkouts builds in as many at once, and
its queue gives each free checkout to the first build in line that may use it:
waiters go in the order they came, a waiter takes a free checkout it may use
even when a waiter ahead of it may not (a build that runs only on this Mac
passes one that waits for a host's checkout, and the reverse), and one that
dies in line never lets anyone past the holders. A ticket's name ends in the
words here, hosts or anywhere, which say where its build may run.

An app checkout's working tree belongs to whoever holds its lock, and only for
the command they run holding it: nobody edits there or leaves changes behind.
Commit on your branch in your own worktree, then run `builds app-build`, which
takes the lock, checks out your commit (detached, because your branch stays
checked out in your worktree) and builds. Put everything that needs the build
(its tests, launching the app) in that one command; the next holder moves the
checkout. To change something, commit or amend in your worktree and run the
command again. A dirty app checkout fails the command rather than carry
someone's changes into your build: find out whose they are before deleting
them. After its steps, `builds app-build` checks the checkout again. When a
step changed a file your commit holds, or added a file that no ignore rule
covers, the build did not build your commit as it is: builds puts the checkout
back on your commit and fails the build, naming the files.

Another checkout may keep an app build while a wave of work needs it (the
person asks for an app build in a worktree, or parallel agents each need one).
Clear it once that work has moved on: retire the worktree, or delete the
folders behind its app links while nothing builds there.

A repo's `.app-build` at its root says what its app builds run, one line each:

  step <lane> <name> <program> [<args>...]
                    a step of the lane. A step is a program, not a shell
                    string: a step that needs a shell is a script in the repo
  on <pattern> <step>...
                    the steps a changed path matching the pattern builds (a
                    pattern ending in / or naming a path matches the paths
                    under or at it; one starting with * matches the paths
                    ending in the rest)
  needs <lane> <step>...
                    the steps a --test or --shots run builds first when no
                    changed path picked one of the lane's steps
  sources <lane>[:<name>] <folder>...
                    the folders that declare the lane's test classes; with
                    :<name>, the `test <lane>:<name>` line runs the classes
                    declared there
  test <lane>[:<name>] <program> [<args>...]
                    how the lane runs test classes: builds runs the line
                    once for all of a build's classes that the line runs,
                    and copies the word that holds {class} once for each
                    class; a lane may have a named test line per kind of
                    test (bae: mac:shots for the shot test bundle)
  shots <lane> <program> [<args>...]
                    how the lane runs the shots (pictures of app views, each
                    checked against its board) whose names start with the
                    prefix in its {select}: `builds shots run`, to which
                    builds adds --before <findings.json> when the run
                    compares with another (below)
  shots-<setting> ...
                    a setting of the shots checker (`builds shots`), which
                    reads these lines itself: the parser of the other lines
                    skips them

                    the folders a --test or --shots run on another host
                    copies back to this Mac
  here <step>...    steps that never run on another host (bae's signed macos
                    step)
  opens-windows <lane>[:<name>]...
                    the test lines whose runs open windows (bae's mac:ui line,
                    for its UI tests); a --test run of such a line never runs
                    on this Mac, where the windows would cover the person's
                    screen, only on a host, and one such run at a time on each
                    host (APP BUILDS)
  ci-only <step>...
                    steps that only CI runs, such as a whole test suite
                    (bae's macos-tests-all); app-build refuses such a step
                    when a caller names it,
                    leaves it out when it runs every step of a lane, and
                    refuses an `on` or `needs` line that names it

                    the step's time limit (90s, 30m, 2h), in place of 45
                    minutes

A step that runs past its limit gets SIGTERM to its whole process group and
SIGKILL ten seconds later, and fails the build, which gives up the lock.
builds limits each run of a test line, with all of its classes, to 10 minutes,
and each --shots or --all-shots run to 20. `builds build-app` and `builds
lock` set no limit.

SIGTERM, SIGINT or SIGHUP stops an app build. `builds app-build` passes the
signal to each lane, and each lane passes it to the process group of the step
that runs; a step on a host stops there. A lane that waits for its turn in the
queue or for a host's display stops waiting, and a lane between two steps
starts no other. The lane puts the checkout back on its commit when the steps
changed it and gives up its lock and the host's window lock. When the lane had
taken a checkout, builds records its run as stopped, with the step that the
signal ended as stopped. Once every lane has ended, app-build exits and says
which signal stopped it.

The same signals stop `builds build-app` and `builds lock`. Each passes the
signal to the process group of the command that runs, and a build on a host
stops there. Each stops waiting for its turn in the queue, starts nothing
after the signal (build-app copies, installs and quits no app), gives up its
lock and exits saying which signal stopped it, with the exit status 128 plus
the signal, as a shell gives a program that a signal ended. The dashboard shows
a build-app run that exits so as Stopped, and one that exits with any other
nonzero status as Failed.

An app checkout may be on another host (`builds host`). Its lock, queue and
record of its last build stay on this Mac, under the entry <host>:<name>. A
build there sends the commit to the host's clone as a job ref (never to
GitHub), switches the checkout to it (the checkout must have no changes), and
runs each step through `builds remote step`, with the same time limits and
takeover; its output comes back behind [<lane> <host>:<name>]. After each
--test or --shots run there, passed or failed, the folders of the lane's
`results` lines are copied to /Volumes/Builds/<repo>/<host>:<name>/<path> here,
where agents read them. A step on a host ends with its exit status as soon as
its command exits: builds stops the processes the command left in its process
group, and a process it left elsewhere (a build daemon) cannot keep the step
running, since the command's output reaches ssh through relays that builds
ends. A connection to a host that stops answering ends within a minute and
fails the step, and builds keeps this Mac awake while a build holds a
checkout on a host, since a sleep here ends the connection (HOSTS). A mac
lane checkout on a host needs Xcode there. The lane's list of checkouts stays
on this Mac, so builds writes the lane's name to the file builds-app-lane in
the checkout's git dir on the host: when a person adds
a checkout the host already has, and when a build makes a new one there. The
host's own `builds setup` and `builds prune` read the file and keep the
checkout's builds warm, as this Mac does for its own app checkouts.
The android build-app, a mac build-app whose build is a `here` step, `builds lock` and a build that runs a `here` step never
take a checkout on a host. A build that runs a test class through a line an
`opens-windows` line names, or a --shots or --all-shots run of a `shots` line
that passes --windows (bae's mac line), takes only a checkout on a host, never one on this
Mac. When the lane has none, builds adds one on a host as for a build that
waits, and the build fails when no host can take one (in bae, the M1's mac
lane checkouts run the UI tests). A build cannot run both a `here` step and a test class from an
`opens-windows` line; it fails and names one of each. A host runs UI tests only
with the settings HOSTS names, since nobody is at its screen to type a
password.

Each host has one display, so a step that opens windows (a test run of an
`opens-windows` line, or a --shots or --all-shots run of a `shots` line that
passes --windows) holds the host's window lock while it runs, and no second
such step runs on that host: UI tests of two builds, in two app checkouts, never
share the display. The lock covers the host across repos, lanes and checkouts,
and a step on another host takes its own. A step that finds the lock held waits
for it and prints that it waits, naming the run that holds it. The build keeps
its app checkout and its place in the lane while it waits, and a takeover ends
the wait. Steps that open no windows never wait for it. builds cannot tell
whether the command of a `builds remote run` job opens windows, so every such
job on a Mac holds that Mac's window lock from before it sends its commit
until it ends, and waits for it the same way; a job on a Linux host takes no
lock. `builds cargo` jobs open no windows and take no lock.

A --shots or --all-shots run of a `shots` line that passes --windows draws each
scene on the host's screen, and macOS makes the shot display only when the Mac
has a display to add it to. A Mac whose lid is closed has none unless another
display is attached. Before such a run takes a checkout on a host, builds asks
the host once (`ioreg` for the lid, `system_profiler` for the displays) and
takes no checkout of a host whose lid is closed with no display listed. Of the
hosts that can draw, it takes the one with the least load. When none can, the
run fails at once, naming each checkout it skipped and why ("its lid is closed
and it lists no other display"), and a run that asks again after the lid opens
goes through. A host that does not answer is skipped and named the same way.
Runs of UI tests and every other step ignore the lid.

When a host's Xcode cannot start, every xcodebuild run there fails, whatever
code it builds: xcodebuild prints "A required plugin failed to load" and names
the fix (as after someone updates Xcode and nobody runs its first launch, which
installs its system content). When a mac lane step fails after printing that
line, builds records the host (this Mac included) in the folder
host-xcode-failures beside the file `hosts`, and the lane runs again from its
place in the queue in a checkout on another host. The mac lane skips a recorded
host's checkouts, and `builds health` lists the host under "needs action" with
xcodebuild's fix, until `builds host clear-xcode <name>` removes the record. A
step that fails without that line failed because of its code, and fails the
build. A mac lane step that fails after XCTest printed "Timed out while
enabling automation mode" failed because the host lacks the settings that UI
tests need (HOSTS): builds records the host in the folder host-ui-automation-failures
beside the file `hosts` and runs the lane again on another host in the same
way, until `builds host setup <name>` finds the settings on and removes the
record.

An app build runs the builds it started with from its start to its end,
here and on each host, whatever an install puts on PATH meanwhile, so its
merge base's shots runs and its own come from one version of the shots
checker; the next build uses the installed builds. Each version keeps its
builds in ~/.local/lib/builds/<version>/, named by `builds version`'s hash.
The first app build of a version copies the builds it started from into
that folder, once the copy says that version (when an install replaced the
program before the build copied it, the build copies nothing and runs the
installed builds in its place). The build holds the folder while it runs,
starts its lanes from the folder's builds and puts the folder first on PATH,
so `builds shots run` in a `shots` line runs the folder's builds. Before each step on a host, the lane copies the folder
to the same place on the host when the host lacks it, and runs the step
under `<folder>/builds programs hold`, which holds the host's folder and
puts it first on PATH there. `builds install` removes each other version's
folder here that no build holds, then has each host remove each version's
folder there that no step holds and that this Mac no longer keeps, so a
host keeps the folder of every build that runs here.

builds caches each --shots and --all-shots run on the build volume, in
/Volumes/Builds/shots/<repo>/runs/<commit>/<lane>/<prefix>/<version>/, so
the next run in the checkout cannot overwrite it: run.json (when the run
ended and its exit status), output.txt (all that the shots program printed)
and report/ (the report's index.html, the pictures it shows and
findings.json, the findings as records). The folder's path is the run's
key: the repo, the full commit, the lane, the prefix and the shots version.
A later run of the same key replaces the folder whole. The shots version is
the version of the shots checker that builds is built with (`builds shots
version`): a hash of the checker's sources, the boards library's and the
versions of the packages they use, so a change to builds alone keeps every
cached run. Each run's findings.json names the version, and builds caches no
run whose findings.json names another version. A run that died before it
made findings caches nothing.
The cache is build output on the build volume: builds holds each repo's folder
in shots under its cap, deletes the runs and pictures that agents used least
recently first (DISK), and makes a deleted run again when an agent asks for it.

Beside the runs, builds caches each repo's board pictures in
/Volumes/Builds/shots/<repo>/pictures/boards/, as <board hash>.png with its
element list <board hash>.json. A board hash is the hash of everything the
board's picture depends on: the board's file and the parts it mounts (for a
component shot, the preview page and the shot's name), its frame on the
canvas, the design system's built files, the canvas runtime copy, the copies
of React, the pinned Chrome, the version of the shots checker, and the
shots-unshot and shots-preview lines. app-build passes the folder to each shots run
on this Mac (`run --pictures`), and the run draws only the boards whose hash
the folder lacks and adds each new drawing to it, so builds draws a board
once for its inputs.

The same folder caches the app's shots by the lane's app source tree, in
pictures/<platform>/<app tree>/: a hash of the git objects, at the commit,
of each path the `on` lines name for a step of the lane, of .app-build, and
of the Rust the app builds from: every file of each crate whose folder an
`on` line of the lane matches or that a matched script builds with `-p
<crate>`, of every workspace crate those depend on (from the manifests at
the commit), and of Cargo.toml, Cargo.lock, rust-toolchain(.toml) and .cargo/.
app-build passes the lane's app tree to each shots run on this Mac (`run
--app-tree`). When the folder caches every shot the run selects for that
tree, the run takes the shots from it and runs no capture command;
otherwise it captures them and caches them there. A commit that changes no
path of the lane's app takes no shot again. Once a run has cached every shot
a prefix selects, the shots checker marks the prefix taken for the tree (and
whether the run took the shots shown in a window). When an app-build asks a
lane only for shots, no changed path needs a step of the lane, and the
folder holds a mark for each prefix (a mark of mac. covers mac.welcome.),
the lane runs no step: it checks out the commit and runs the shots line with
--no-capture, which takes every shot from the folder and fails rather than
capture from an app nobody built. The output says which lanes build nothing
and why. For a shots run on a host,
app-build copies the board pictures and the shots cached for the lane's app
tree to a temporary folder on the host, passes that folder to the run, and
afterwards moves the pictures the run added into the folder here.

The key is the lane's whole app tree, not one key for each shot, on Mac and
Android alike: a commit that changes any file of the lane's app retakes
every shot the lane selects. builds does not narrow it to the files a shot is
drawn from, because the compilers' dependency output cannot say so. Swift's
`-emit-dependencies` .d file of each source lists every source of the module
and the SDK interfaces, so it holds no per-shot set. The .swiftdeps files
are the incremental build's binary record of declaration names each file
provides and uses: they name types of another module (BaeKit) only by
mangled name, and they cannot see what a shot reads when it runs
(resources, strings, assets). A key built on them could reuse a shot that
should be taken again, which is worse than taking it again. builds reads no
such record from Kotlin, so Android keeps the lane key too.

A shots run of a commit that origin/main lacks compares with the run of its
merge base with origin/main: builds passes the findings.json of that run to
the `shots` line as --before, and the run fails only on the pairs it makes
new or worse, a pair the merge base's run did not check or one with a
finding that run lacks for it, and lists the pairs whose findings the merge
base's run has too. The run it compares with is the newest cached run of the
merge base in the same lane, by the same shots version, whose prefix starts
the run's own (a run of mac. stands in for a run of mac.welcome.), and whose
report holds findings.json. When builds has none cached, `builds app-build` builds
the merge base first in the lane, with the lane's `needs` steps, and runs the
same prefixes there. That run compares with nothing, so it fails on every
pair with findings, and builds caches its findings all the same and runs
every other prefix the build names; only a step or a shots run that fails
without failing pairs, as when it cannot render, stops it. A run of a
commit on origin/main compares with nothing. A lane's process (`--lane`)
builds no merge base: it fails, naming the command that makes the run it
lacks. A shots check's "before" side is read from the cached runs, never
built again.

HOSTS

builds can run jobs on other machines, its hosts: other Macs, and Linux
machines that run Debian or Ubuntu, such as a rented server or a cloud
instance. This Mac is always one, named local. A host keeps its clone of each
repo at ~/dev/<repo>, its worktrees at ~/dev/<repo>-worktrees/, and its build
roots in /Volumes/Builds when it is a Mac with that volume, else in
~/builds-root.noindex on a Mac and ~/builds-root on Linux. A Linux host takes
`builds cargo` jobs, except a job that builds a package only a Mac builds
(CARGO). App builds run only on Macs, and `builds remote run` picks only Macs.

To add a Linux host, give it a user that this Mac reaches over ssh by key and
that may run sudo, then run `builds host add <name> <user>@<address>` and,
with a person at this terminal to type the sudo password, `builds host setup
<name>`. Setup installs everything else the host needs (below).

A host refuses jobs when it answers but cannot start one. builds finds this
two ways: a probe, which asks the host for its load and disk, also runs git
there, in the shell a job's push reaches, and git fails (as it does on a Mac
whose Xcode license is not accepted); or sending a job's commit or claiming a
worktree for it fails there. builds records each host that refuses jobs in
the folder host-refusals beside the file `hosts`, with when it first refused
and what it said, and every pick passes over it. `builds health` lists each
recorded host under "needs action", and the dashboard's load card for the host
says "refuses jobs" in place of its core count when git fails there. Fix the cause on the host; the next probe
that finds the host answering with git running removes the record, and builds
uses the host again. `builds host list` probes every host, and so does every
`builds cargo` and `builds remote run` that picks one. A host whose Xcode
cannot start, or whose UI tests timed out turning on automation mode, refuses
mac app builds only (APP BUILDS).

While builds works on a host over ssh, in a lane's app checkout there or in
a job of `builds remote run` or `builds cargo`, it keeps this Mac awake with
two of macOS's power assertions, which `pmset -g assertions` lists under
builds' name: PreventUserIdleSystemSleep keeps the Mac from sleeping when
nobody uses it, on battery or on power, and NetworkClientActive also keeps
it awake through a maintenance wake while it runs on power. A Mac that sleeps
answers nothing on its connections, and the host ends a connection that
gets no answer for about twenty seconds, which stops the command there.
Neither assertion keeps a Mac on battery awake once its lid closes or
through a maintenance wake. Work on this Mac alone holds no assertion, since
a sleep only pauses it. When ssh to a host exits 255, the status it gives
when its connection fails, builds reads the power log (`pmset -g log`) of
this Mac and of the host, and says on stderr each sleep either one recorded
while the command ran: when it began, how long it lasted, the reason macOS
gave, such as Clamshell Sleep or Idle Sleep, and whether the Mac ran on
battery.

A Mac runs UI tests with nobody at its screen only with three settings on.
Without them, XCTest asks for a password on its screen, or says "Timed out
while enabling automation mode" (and `automationmodetool` says the device
requires user authentication), and the test class runs no tests. Each
setting has a check that only reads and a command that turns it on:

  - Automation Mode without a password: `automationmodetool` says the device
    does not require authentication;
    `sudo automationmodetool enable-automationmode-without-authentication`
  - developer mode: `DevToolsSecurity -status` says enabled;
    `sudo DevToolsSecurity -enable`
  - the user in the _developer group:
    `dseditgroup -o checkmember -m <user> _developer` says yes;
    `sudo dseditgroup -o edit -a <user> -t user _developer`

`builds host setup` checks the three on the host and runs the commands for
the ones that are off through sudo there when a person is at this terminal to
type the password (over `ssh -t`); with nobody at the terminal it fails and
names the commands to run on the host. `builds health` checks them on every
host, this Mac included, and lists each host that lacks one under "needs
action" with the commands.

Spotlight's indexer reads every file a build writes where it indexes, so
builds keeps Spotlight off each Mac's build root. Spotlight skips a folder
whose name ends in .noindex, so a host's build root in its home folder,
~/builds-root.noindex, needs nothing more. A .metadata_never_index file in a
folder does not keep Spotlight out. A build volume's indexing is a setting of
the whole volume: `mdutil -s /Volumes/Builds` reads it, and
`sudo mdutil -i off /Volumes/Builds` turns it off. `builds host setup` checks
it on the host and runs that command through sudo there when a person is at
this terminal; with nobody at the terminal it fails and names the command.
builds never runs mdutil on a build root that is a folder, because the
folder's volume holds other files. `builds status` says whether Spotlight
indexes the build root.

DISK

builds keeps disk use bounded: it deletes the build copies and builds that no
build uses, deletes a folder that is still over its cap, and keeps a free-space
floor on the volume. `setup`, which runs before every hook and build, and
`prune` do all of this, and `builds cargo` deletes the copies a build replaced
as it exits. The dashboard runs `builds prune` every 6 hours, and `builds
health` says when a prune last finished. Nothing deletes a folder that a process holds a file open in or
whose checkout's guard a build holds, and a deletion never fails a build: a
removal that fails warns and leaves the folder in the trash for the next
emptier.

Unused build copies. Cargo names each unit it builds (one crate target, for one
profile, target and feature set) by a hash of everything that build depends on,
so every dependency bump builds a new copy of each unit above it, and the old
copy stays. In each cargo folder (target, target-macos, ...) builds deletes
every file of a unit that no build used for BUILDS_UNUSED_DAYS days (default
3), and of a unit a newer copy replaced: a copy of the same package and target,
mode, features and profile, built from other sources (another version or git
revision of a dependency, or another compiler), that a build used after the
unit's last use. A unit is also replaced when a newer build of its package
(such as the library beside a test binary) was built against another copy of
something the unit was built against. Copies built from the same sources for
another package selection (`-p x` against the workspace) stay side by side, and
so does whatever a unit that stays was built against. A unit's last use is the
last build that reported it, rebuilt or up to date; a unit that no recorded
build used counts as used when cargo last built it.

Incremental folders. builds deletes the incremental folders that only deleted
units used, and every incremental folder that nothing wrote anywhere inside
for BUILDS_INCREMENTAL_HOURS hours (default 6), in every checkout: main's
builds compile incrementally, and in the others a repo's lint wrapper may keep
an incremental folder for the crates it lints (bae's
scripts/clippy-rustc-wrapper.sh). The build folder's cap bounds the rest.

Object files. In every checkout, builds deletes the object files that no build
or debugger reads: an rlib's loose objects, and the objects a binary's debug
map doesn't name, which each incremental rebuild leaves behind under new names.
This needs split-debuginfo "unpacked", macOS's default; keep it, since packed
builds slower and larger, and off drops file and line from the top crate's
frames.

Separate builds inside one folder. A folder is aged by its newest write, so a
stale build beside a live one (last week's Xcode tree beside today's) would
never age out. builds finds the builds inside each folder and deletes each one
no build used for BUILDS_UNUSED_DAYS days, in main and the app checkouts too,
but keeps a build a process holds a file in and, in main and the app checkouts,
one a `keep` line names. It recognizes an Xcode tree (info.plist beside Logs,
and Build or ModuleCache.noindex, up to two levels below the folder) and a
SwiftPM <triple>/debug or <triple>/release folder in a .build that holds
workspace-state.json. A build's last use is the newest write inside it, since
xcodebuild and `swift build` write even when everything is up to date. dotnet's
and Gradle's folders are not split: an up-to-date `dotnet build` writes
nothing, and Gradle keeps no build per variant. `status` lists each build under
its folder with its last use (`status --json`: the folder's `trees`).

Builds and deletions never overlap. builds deletes a unit's files only while it
holds the checkout's guard (<build root>/.builds-cargo.lock) and cargo's lock
on that profile folder, both taken without waiting, and keeps any unit a
process holds a file of. `builds cargo` holds the guard, shared, from before
cargo starts until cargo has exited and its report is read, because cargo
decides which units are up to date before it runs anything and lets go of its
own lock before `cargo test` runs the tests. A build waits on the guard only
while a deletion holds it, a few seconds, and a build that starts after a
deletion rebuilds the unit, mostly from sccache.

Caps. A folder still over its cap is deleted whole (renamed into .trash,
removed in the background) and recreated empty, and the next build refills it,
mostly from sccache. A cap is about twice a fresh build of its folder. A
claimed worktree's folder is never deleted whole, since its agent is at work in
it: status shows it over its cap as "claimed, kept". Sizes, against caps and in
status, count each block once (`builds du`): cargo copies each library and
binary it builds for you out of its build copy's files as an APFS clone, which
du counts once per file, and rustc hard-links a build copy's files into
incremental/.

Free-space floor. Caps bound each folder, not the volume: a checkout with every
platform built takes 45-52 GB, and the build volume shares its APFS pool with
the main disk. So builds keeps a free-space floor of 30 GiB
(BUILDS_FREE_FLOOR_GIB), and frees space up to a target of the floor plus a
margin of 20 GiB (BUILDS_FLOOR_MARGIN_GIB), so that the next build's writes
don't take the volume under the floor again at once. `setup` starts deleting
when the volume has less free than the floor, and `prune` starts as soon as
the volume has less free than the target. Each finishes emptying the trash,
then deletes the build roots of checkouts that are gone, DerivedData's idle
entries, then the incremental folders nothing wrote inside for 60 minutes in
every checkout (claimed ones, main and the app checkouts included), and then
the whole folders that nothing wrote to for 30 minutes in the side worktrees no
agent claims and in a host's job worktrees no job claims, never main's or an
app checkout's own lane's folders. Each kind goes least recently written first,
until the volume has the target free. builds says what it deletes and why, and
a last line gives the space it freed and the free space after. If builds can't
reach the floor, it warns, naming the free space and the biggest folders, and
the build goes on: whoever runs the agents stops starting more. Only under the
hard floor of 10 GiB (BUILDS_HARD_FLOOR_GIB) does setup fail, before the build
starts, rather than let the build run out of space halfway. These deletions
never touch a shared cache.

DerivedData. bae passes -derivedDataPath into a .build folder in the checkout
(scripts/xcode-trees.sh is its one definition, and a pre-commit check refuses
the flag anywhere else), so DerivedData holds only what one-off xcodebuild runs
(-showBuildSettings, package resolves) and the Xcode app write: one
<project>-<hash> entry per project path, mostly SwiftPM checkouts of about 3
GB. It is one disposable cache with a 15 GiB cap. `setup` and `prune` delete its
entries, least recently written first, while it is over the cap; `prune` also
deletes entries nothing wrote to for a day, and the floor deletes its idle
entries first. Every deletion skips an entry written in the last 30 minutes or
one a process holds a file in.

Shared caches. Each tool keeps its downloads (sccache, its compiler outputs) in
caches/<name>, linked from where the tool looks, with a cap each:

  gradle   8 GiB  ~/.gradle
  npm      1 GiB  ~/.npm
  nuget    6 GiB  ~/.nuget
  swiftpm  3 GiB  ~/Library/Caches/org.swift.swiftpm
  sccache 50 GiB  ~/Library/Caches/Mozilla.sccache

`setup` and `prune` delete a cache that is over its cap, whole, once nothing
has written to it for 30 minutes and no process holds a file in it, and put
back the settings files it held (gradle.properties, Gradle's init scripts,
NuGet.Config). Nothing else deletes one: every checkout would download it all
again, and a SwiftPM fetch cut off halfway corrupts its cache. sccache keeps
its own cache under its cap; builds only shows it.

Shots runs. The folder shots caches each repo's shots runs, board pictures
and app shots (APP BUILDS), with a cap of 2 GiB for each repo's folder.
`setup` and `prune` delete a repo's whole runs, board pictures and app
source trees' shots while its folder is over the cap, least recently used
first. A run's last use is when it ended or when builds last read it (to
print its findings or to compare a branch's run with it). A board picture's
is when a run last drew or took it. An app source tree's shots of one
platform go together, and their last use is when a run last captured or took
one of them. Whatever a run used in the last 30 minutes stays. `setup` and
`prune` also delete each staging folder and half-written picture file that a
run which died left behind, and each folder the deleted runs left empty. A
run fills its staging folder at the top of the folder shots and makes the
folders of its key only when it puts the run in place, so a run that stops,
or that builds does not keep, leaves no folder under runs.
They delete nothing in the folder while a shots step reads or writes it,
which a step on this Mac does while it runs and a step on a host does while
builds copies a before run and pictures to the host and the new pictures
back. `status` shows each repo's folder's
size against the cap.

Review texts. The folder review-texts holds what each review run sent its
reviewers and what they answered, one folder per run, with a cap of 2 GiB; the
project's store holds only the findings, verdicts and settles, and the hash of
each text. `setup` and `prune` delete whole runs' texts while the folder is
over its cap, least recently used first, as they do shots runs: a run's last
use is when it was recorded or when builds last read a text of it, and a run
used in the last 30 minutes stays. Once a run's texts are gone, a command that
needs one (`builds review audit`, `propose`) says so and goes on to the next.
`status` shows the folder's size against its cap.

When xcodebuild fails with "Couldn't check out revision" or "file not found" on
a SwiftPM dependency (often Sparkle), its cache is corrupt: disconnect any VPN
(a VPN can cut fetches short), delete the app's Xcode build trees and its
SourcePackages folder and ~/Library/Caches/org.swift.swiftpm/repositories/
<dependency>*, and run the repo's build script again. Every script that
resolves packages and every script that builds after it must pass the same
xcodebuild flags, -derivedDataPath above all, or the packages land where the
later build can't find them.

Cargo's git checkouts. `setup` and `prune` delete each checkout in
~/.cargo/git/checkouts that no live checkout's Cargo.lock pins, holding cargo's
package cache locks. The git databases in ~/.cargo/git/db stay.

Installed tools. A repo's script may install a tool once per version into a
folder in the user's cache home, for every checkout on the Mac to share (bae's
ownership checker, about 10 MB per coven revision), and a `.build-dirs`
`installed` line names the folder and the file that names the version a
checkout runs. `setup` and `prune` delete each version in the folder whose name
no live checkout's file contains, reading the file in every live checkout,
whether or not its own `.build-dirs` has the line. An entry whose name starts
with a dot is one a script is still installing, and `setup` and `prune` leave
it. When builds cannot read a checkout's `.build-dirs`, the folder or one of
the files, it deletes nothing there and says why. When no live checkout has
the file a line names, builds deletes nothing in that folder and says so.

Build output in the temporary folders. A build pointed at /private/tmp or the
user's temporary folder writes 5-14 GB there that nothing else deletes. `setup`
and `prune` delete each cargo target, DerivedData or SwiftPM folder there, up
to four levels deep, that nothing wrote to for 30 minutes and no process holds
a file in; `status` lists them. They skip /private/tmp's claude-* (Claude Code
sessions' scratch, whose entries go three days after the session's last
change), com.apple.* and tmux-* (live sockets), and anything the user doesn't
own.

Agent registrations. `builds agent start` registers each agent in
<the lists folder's parent>/agents/<session>/, and only a command that an
agent of that session runs reads it. `prune` (not `setup`) deletes each
session's folder once Claude Code's record of running sessions (~/.claude/
sessions) no longer names the session. When builds cannot read that record, it
deletes none and says so.

Never run `cargo sweep --time` or `--maxsize`: APFS doesn't refresh access
times, so sweep deletes the builds needed next. `cargo sweep --installed` after
a toolchain upgrade is fine.

COMMIT CHECKS

A repo's `.checks` at its root declares the checks its pre-commit hook runs,
one per line: `<kind> <name> <paths> <program> [<args>...]`. The kinds:

  check   a static check
  fix     a formatter; the files it changed are staged again
  whole   a check that reads the whole tree: the hook runs it when a path
          matches, and `builds land` runs it on every landing, since two
          commits that each pass the hook can break it together. It names
          neither {files} nor {crates}
  test    a checker's own test; CI runs it, never the hook

paths is a comma-separated list of globs over repo-relative paths: `*` stays
inside one path segment, `**` is any number of segments, and a glob with no `/`
matches the file name anywhere. The program is not run by a shell. As a whole
argument, {files} is the matching staged files that still exist, and {crates}
is `-p <crate>` for each workspace crate holding one (a root Cargo.toml,
clippy.toml or .clippy.toml counts as every crate, since each configures the
workspace's lints, and so do a root rust-toolchain.toml or rust-toolchain,
which picks the compiler and the clippy of every crate, and .cargo/config.toml
or .cargo/config, cargo's settings for every crate; a root
Cargo.lock counts as each crate whose resolved dependencies changed against
HEAD, or against the commit `builds checks tests --since` names: its own lock
entry or one it depends on at any depth); a check with neither runs whole
whenever a matching file is staged. A glob written `every:<glob>` marks files
that configure the check of every crate, such as the sources of a lint driver
the line runs: a staged file it matches hands {crates} every crate, for that
line alone, and builds refuses the mark on a line that names no {crates}.

  builds checks run [<worktree>]
                              what the pre-commit hook runs: the check and fix
                              lines the staged files match, from the repo root:
                              the fix lines first, one at a time in file order,
                              then every check line at the same time, since
                              the checks only read the tree the fixes left.
                              `builds checks run` prints each line's name, time
                              and result (with a failing line's output) in
                              that order, and the total time. Every line runs
                              even after one fails, and the exit status is
                              non-zero if any did. It
                              refuses before any line runs, naming each file,
                              when a staged file also has unstaged changes,
                              since the checks read the working tree;
                              unstaged changes to unstaged files are fine. It
                              records each run, a refused one as a failed run
                              with no checks, in the project's store: when,
                              repo, worktree, branch, the commit HEAD pointed
                              at when it started (its base), each staged file
                              (its change and lines added and removed), each
                              line (run with its time, its result and this
                              Mac's cores and one-minute load when it started,
                              or skipped), for a line that failed an excerpt
                              of its output (the lines from the first test
                              panic or compiler error, else the last lines)
                              and the staged files it was handed that its

  builds checks run --since <rev> [<worktree>]

WAITS

builds records how long agents wait on four kinds of work. `builds waits`
prints, and the dashboard's "waited today" figure opens, the time of each kind
per local day and per band of load per core, with each row's count, median and
total, so a person can see which kind of work agents wait on longest and how
load changes the wait for each kind. Every wait counts, whatever its result.
The kinds:

  commit hook      each `builds checks run`, passed or failed, from its start
                   to its last check's end, with this Mac's load when its
                   first check started (COMMIT CHECKS)
  test run         each `builds cargo test` and `builds cargo nextest` run
                   that no hook check started, from the start of `builds
                   cargo` to cargo's exit, with the load of the host that ran
                   cargo when builds picked it (CARGO). Days before builds
                   recorded every `builds cargo` run have no test runs
  app build queue  each lane run's wait in its lane's queue, a wait after a
                   takeover included, with the load of the checkout's host
                   when the run took the checkout (APP BUILDS)
  app build step   each step of a lane run, its test lines and shots runs
                   included, with the load its run recorded

Load per core is the one-minute load average over the host's cores, in four
bands: under 1, 1 to 2, 2 to 4, and 4 and over. A wait whose record holds no
load counts under "not recorded": a hook run from before builds kept each
check's starting load, an app build run from before builds kept its host's
load, or one whose host did not answer.

  builds waits [--project <project>] [--since <YYYY-MM-DD>]
                              print the time of each kind of wait per local
                              day and per band of load per core, for the
                              project of the current checkout unless
                              --project names one: for each kind and day, a
                              row for all loads, then a row for each band;
                              --since counts waits from that local day on.
                              The dashboard shows the same for today and
                              yesterday


LANDING AND REVIEW

A branch's agent puts its commits on origin/main by running `builds land` in
the worktree whose branch holds them, once its work is done there. In a repo of
a project with lists, the agent first reviews the branch against
agent-instructions' rules with `builds review`, and the judge settles each
finding (`builds judge listen`). `builds help workflow` (REVIEW) says how an
agent reviews its branch and how the judge settles each finding, which files
each group reads in a later run, and how long a confirmed finding stays open.

Each branch's change has one review, which builds finds by its repo and its
key (by default the branch, such as `branch:work`) and which stays open until
the change lands. Branches of the same name in two repos are two changes, each
with its own review.
The review is a series of runs. builds records which run is the last review:
the run whose net change (`git diff` from the branch's common ancestor with
main to its head) the review has read. A later run asks only what the review
lacks: the groups that gave no answer (their reviewer failed), over the diff
they did not answer, and, in a new run that becomes the last review, the
changes since the last review (`builds help workflow`, REVIEW). The run asks
the groups that cover a changed path, the groups that hold an open confirmed
finding, over every changed file, whether or not their rules cover it, and,
when a commit message changed, each group that reads commit messages
(commit_text) and whose rules cover a path the branch changes. A group that
holds an open confirmed finding reads every change since the run that raised
it, with the finding: when a run read some of those changes without the
finding (the judge confirmed it later, for example), a run of that group alone
reads the changes since the last net change the group read with the finding,
even when nothing changed since the last review. A reviewer reads the commit
messages as one more file, named COMMIT_MESSAGE. Only groups whose rules judge
what a message says read the messages (in agent-instructions, the group
Commits and repo contents, whose rules ask whether the text is accurate).
When nothing is unread and a confirmed finding stays open, `builds review`
asks each group that holds one again, over the whole net change at the
branch's head, so that the group can close a finding that a commit it read
fixed in place. The finding stays a true positive: only a run that closes it
ends it. `builds review` refuses the run, naming the last review, when the
review lacks nothing and no confirmed finding is open.

`builds review` checks code and whether text is accurate, never word choice,
grammar or style: it never asks a copy group (copy, below), whose rules judge
wording. In agent-instructions the copy group is Text people read. The person
reviews copy by hand, and may run the copy review (`builds review copy`),
which asks only the copy groups. No landing waits on the copy review.

builds finds the changes since the last review by replaying the net change
the last review read onto the branch's current common ancestor with main, in
a tree of git's own (`git merge-tree`, which checks nothing out), taking the
lines of that net change where main changed the same lines, and diffing that
tree against the branch's head. A file the replay cannot write (one side
deleted it, for example) shows its whole net change, and so does every file
when the repo no longer has the commits the last review read. The commit
messages the run reads are those the last review's net change did not hold.

Each reviewer reads the changes since the last review, and raises findings
only on lines those changes add or remove. builds drops a finding whose code
sits only on the lines around them, which the diff shows for context: a later
run never flags a line that the fix did not change. The reviewer may read the
whole branch as it is now, for context. The reviewer also gets each open confirmed finding of its group's
rules, with its file, line, quoted code and problem, reads the code at that
place as it is now, and names each one whose problem is gone. builds closes each finding it names,
with the run that closed it.

`builds land` refuses a branch until its review takes it: nothing on a path
a group's rules cover changed since the last review (the net change of the
worktree's HEAD past origin/main against the net change the last review
read), and no commit message that a group reads changed since then; every
group asked over a diff a run read answered over it; every
finding is settled; and no confirmed finding is open. Land finds the review
by the change's repo, the repo of the worktree it lands from, and its key: the
branch land started on, which land reads before it starts and passes to
`review check-landing` and `review landed` as `--landing`. When land refuses, it names what is unreviewed (the paths that
changed since the last review, and COMMIT_MESSAGE when a message changed),
the groups that gave no answer, the
unsettled findings and the open ones. A landing may hold some of the
branch's commits and leave the rest for later, once the review takes the
whole branch: while commits of the branch wait to land, the change stays
under review. A landing whose changed paths no group covers needs no review,
and neither does a landing in a repo of no project with lists: there is
nothing to record. A design-only landing (`--design N` alone) follows the
same rule. `builds review` and land find the changes since the last review
with one function, so they never disagree. Once a change has landed, `builds
review` on the branch opens a new change under the same key, and reads the
branch's net change past origin/main.

The rules are grouped in folders, and each group that covers a changed path
gets one reviewer, a `claude -p` run in a checkout of the reviewed commit with
only Read, Grep and Glob. Its system prompt holds the full text of the group's
rules, the project's projects/<project>.md, the brief of the first --item that
has one; its message holds the diff. It
answers with a verdict for every rule and, per finding, the rule's clause, the
code with its file and line, and what goes wrong. builds drops a finding whose
clause is not in the rule, that is on COMMIT_MESSAGE when its group reads no
commit message, that is on a design file when its rule judges no design file
(below), whose code is on no line the diff adds or removes, or whose
code sits only on comment lines when the group of its rule judges no code
comment (skips_comments), and records it as dropped with that reason. A
comment line
is a line whose first characters past its indent are a comment's mark in the
file's language: `//`, `/*` or `*/` in Rust, Swift, Kotlin and C# (and `*` in
a block comment of all but Rust), `#` in Python, shell and TOML, and `--` in
SQL. Every review goes in the project's store: the change's landing under
review (found by its key until the change lands) with its last review, the
net change each run read, the group, rules, model, prompt, tokens, cost,
verdicts, findings, how each was settled (both settles of a finding settled
again), and the run that closed each closed one. A call's prompt is its
system prompt without the project's instructions and the brief (the opening,
the group's question, how to answer and its rules' text), with its passes,
whether it reads the commit messages, and the answer schema; builds keeps the
text and names it by its hash. A group's model and prompt are its setup: two
calls with the same setup were asked the same way. Every audit and replay
records the same, with the commit of the rules checkout it read. A rule's `blocking` marks its
findings blocking in the reviewer's prompt and the report; every finding,
blocking or not, must be settled before the commits land.

The review checks design files only against the rules about how a screen,
board or component looks, never against the rules about code (decision
#364). The design files of a repo are the boards, the design system and
canvas.json: the paths its design globs give (`builds lists design-globs`),
the same files `builds design only` accepts. A rule that judges how things
look says so in its front matter with `design: true`. Every other rule covers
no design file, whatever its paths match. So a group runs for a design file
only when one of its rules judges design files and covers the file, and a
group reads a design file only then, even when it holds an open finding.
builds drops a finding of a rule without `design: true` on a design file, and
records it as dropped with that reason. The copy review, audits and replays
follow the same rule, with the design files of the change's repo.

The review checks screenshot capture files the same way, only against the
rules about shots, never against the rules about code (decision #397). The
capture files of a repo are the files below each folder that a `shots-declared`
line of its .app-build names, which the checkout holds. A rule that judges
capture files says so in its front matter with `capture: true`. Every other
rule covers no capture file, whatever its paths match, and builds drops a
finding of such a rule on a capture file and records it as dropped with that
reason. Groups run and read capture files as they do design files. The shots
run checks that a moved shot gives the findings it gave before. `builds review
groups --changed` and `builds review replay` know no checkout of the repo, so
they treat no file as a capture file.

Before an agent starts on a brief, `builds item take` checks the brief against
the product spec with the same reviewer runner, in each worktree the take names
whose repo has spec files (`builds lists design-globs --spec-files`). The
reviewer runs the model of the group that holds the rule
every-change-agrees-with-its-product-spec, and its system prompt holds that
rule's text. The reviewer quotes each sentence of the brief that states a
behavior the spec states otherwise (a conflict), with the spec file and the
spec's text, and each sentence that states a behavior the spec doesn't state
(unstated). Storage the brief adds that the spec's schema text does not list,
such as a new column, is unstated, since the commit adds it to the spec. builds
looks for each quote in the brief and in the spec file, finds the line the
spec's text starts on, and sets aside a finding whose quote it does not find.
When the reviewer finds a conflict, take refuses the items unless
--spec-decided names the decision or question that records the person's
choice; take prints each unstated behavior and takes the items. take records
every check in the project's store: the brief's text, the spec files and the
commit the reviewer read them at, the model, prompt, answer,
tokens and cost, each finding, and the --spec-decided record (`builds help
lists`, item take). Before the spec check, take runs the rulings check over
the brief with a reviewer that has no tools, and refuses a brief whose
sentence states a ruling of the person's or a standing prohibition and names
no source that records it (`builds help lists`, RULINGS).

Every review command but `review groups` without --changed reads or writes a
project's store:
the one --project names, else the project of the worktree or current
directory; `review replay` of cases writes each case's project's store. When
that project has no store, the command fails with "there is no store for
project P" and asks no reviewer.

After the push, land records the commits it pushed, and, once the branch has
nothing left to land, the change's landing as landed, with its review run.
`review landed` then starts an audit of a sample of the landed reviews, never
of a landing of design files only, which looks for findings they missed. A second model (opus) checks each candidate
miss the audit raises against the text of its rule, and the audit settles the
miss with the model's answer: confirmed, or dropped with the model's reason.
Nobody settles a candidate miss by hand. `review case propose` turns each
confirmed miss into a case: a recorded change in the review/cases folder of an
agent-instructions worktree, with the findings it must produce, which `review
replay` runs a grouping over. The same command builds the rest of that test
set from landed reviews.

The settled findings score the reviews. A confirmed finding is a true positive
(TP), a dropped finding a false positive (FP), a candidate miss an audit raised
and the coordinator confirmed a false negative (FN), and a rule a reviewer
answered "none" for, over a diff with no confirmed miss in it, a true negative
(TN). Precision is TP / (TP + FP) and recall TP / (TP + FN). A finding counts
as its last settle, so one settled again as dropped is an FP, and a confirmed
finding that a later review closed stays a TP.
`review scores` prints them per group and rule for each setup. `review replay --landing` asks
again over the diffs a landing's reviews read, under another model, rules
checkout or set of groups, and scores the replay against the same settled
findings: a confirmed finding it raises again is a TP and one it misses an FN,
and a dropped finding it raises again is an FP. A replay finding names the same
site as a settled one when both name the same rule and file (one path may be
shortened from the left) and one quote of code holds the other, once whitespace
and markdown marks are gone; failing that, when their lines are at most three
apart. Each settled finding pairs with one replay finding at most. A replay
finding that pairs with none is new, and nobody has judged it.

Every rule is in exactly one group. A group is a folder rules/<group-dir>/ of
agent-instructions that holds its group.toml; its rules are the .md files in
that folder and in projects/<project>-rules/<group-dir>/ (a project-rules
folder must name a group folder of rules/, and a group whose rules are all
project rules still has its group.toml under rules/). A rule's slug is its
file name without .md and is unique across all folders. `builds review groups`
checks this, and so does builds' test. The group.toml fields are top-level keys:

  name          the group's name, as `builds review` prints it
  question      the one design question the group's rules answer
  model         optional; opus, sonnet or haiku. The reviewer runs opus unless
                this overrides it
  instructions  optional; extra words for the reviewer
  enumerate     true when the reviewer lists every site of the diff that
                `sites` describes, one changed file per call, and judges each
                site against every rule of the group (the file's new text
                around each hunk is in the message)
  sites         what a site is, for an enumerate group: the end of "every site
                in the diff that ..."
  commit_text   true when the commit messages of the change are read as one
                more file named COMMIT_MESSAGE: one more call for an enumerate
                group, and the end of the diff for any other
  skips_comments
                true when the group's rules judge no code comment: builds
                drops a finding of such a rule whose code sits only on
                comment lines
  copy          true when the group's rules judge word choice, grammar and
                style: only the copy review (`builds review copy`) asks the
                group, and `builds review`, its audits and its replays never
                do
  passes        how many times each call is made, default 1; the findings of
                all are kept, and the later calls read the first one's prompt
                from the cache
  project_facts true when the group also answers for the project facts that
                every commit keeps (the spec moves with the commit, bae writes
                as local), as one more verdict named project-facts

A group runs when at least one of its rules covers a path that a commit of
the change adds, changes or deletes: a path the rule's paths match that is no
design or capture file, or such a file when the rule judges files of its
kind (`design: true`, `capture: true`). Its reviewer
reads the full body of every rule in the group, the project's always-loaded
instructions (projects/<project>.md), the diff and the landing's brief, and
answers for every rule. No group reviews the test cases in the review/cases folder: a
case holds old code on purpose, so builds leaves that folder out of every diff
and list of changed paths that a review or `builds land` reads. To test
another grouping, change the folders in a worktree of agent-instructions and
run `review replay --rules-root` on it.

                              records who made the call and the check, and
                              lets `builds land` take the branch whole, of any
                              size, while its net change keeps its patch id,
                              and say both. Without --kind builds refuses,
                              except for a pure rename, a design-only change
                              and a change of capture files only, which it
                              already knows.
                              A branch whose diffs add more than 2,000
                              lines (the cap: in bae's last 200 main
                              commits, a commit added a median of 27
                              lines, 351 at the 90th percentile and 1,843
                              at the 99th) starts no reviewer. When its
                              commits change design files only
                              (`builds design only`), or git's rename
                              detection (-M) pairs its renamed files and the
                              lines that still differ differ by renamed
                              identifiers only, `review` records that the
                              branch needs no review, and `builds land`
                              takes its commits with no review and says
                              why, while the net change keeps its patch id
                              (`git patch-id --stable`). For any other branch
                              `review` asks the person on the decision
                              stack whether to review it, naming the branch,
                              its size and the cap, and `builds land` refuses
                              the commits while the question is open. When the
                              person answers it, the next `review` reviews
                              the branch; when they close it any other way,
                              nothing reviews or lands the branch.
                              A run on a key that has a review already asks
                              only what the review lacks (above), and asks the
                              groups that hold open confirmed findings again
                              when it lacks nothing; builds refuses the run
                              when nothing is open either.
                              --head SHA reviews the commits up to SHA from a
                              copy of their files, not the worktree. Prints
                              the findings by group and a total line, then
                              what `builds land` would say of the branch's
                              commits, and exits 1 unless land would take
                              them. While
                              it runs it holds a lock file named for the
                              reviewed commit in the store folder's
                              reviews-running, which the dashboard reads.
                              When the review leaves findings that nobody has
                              settled, builds tells the judge of them (`judge
                              listen`), once, in a message that names the
                              landing, the findings and the worktree. When no
                              judge listens and an agent that a session
                              dispatched runs the review, builds tells that
                              session, the agent's coordinator, instead. When
                              the person or a session's main agent runs it
                              with no judge listening, builds tells nobody.
                              builds records the dispatched agent that ran
                              each run as the agent of the branch

INSTALLING

  builds install              wait for another install to put its builds on
                              PATH, then read each store's schema. When every
                              store already has this builds' schema, move no
                              store, wait for no command, and copy builds onto
                              PATH as below. Otherwise (a store has another
                              schema, or no store has one yet), wait until no
                              builds command will write a store with the
                              schema it started with, naming each and when it
                              started. Wait for every hook run (`checks
                              run`), review that asks reviewers, and landing
                              (`land`) until it records its run, each of which
                              records after long work, except a landing that
                              waits for the app landing lock or runs the app
                              build of its result, which holds no use
                              meanwhile; then for every other command's open
                              store connection, which lasts one transaction.
                              Install neither stops nor waits for an app
                              build: each lane builds to its end on the
                              programs its build started with, and writes its
                              run once, when it ends. A lane whose store an
                              install moved meanwhile writes its run to a new
                              store of its own schema and runs the installed
                              builds, which moves that store to its schema and
                              records the run in the project's store. While
                              install waits, hook runs, reviews and landings
                              that start wait for it and then run the
                              installed builds; other commands keep working. A
                              builds command started by a hook run, review or
                              landing runs under it, and an install that would
                              wait refuses to run under one. Then
                              move the stores to this builds' schema (builds
                              refuses to compile when its schema's stamp
                              differs from the one migrate.rs records, so each
                              schema change records the new stamp beside its
                              move from the schema before), copy builds onto
                              PATH in one rename (a failed build leaves the
                              installed one), link
                              ~/.local/bin/builds-linker and
                              ~/.local/bin/builds-rustc to it, and let the
                              waiting commands start. Then create the
                              shared caches and their links (moving a real
                              folder already there onto the volume), write the
                              sccache config, run the sccache server under
                              launchd (restarting it only when its settings
                              changed, it runs with another cap than its
                              config's, or another server holds sccache's
                              port,
                              and only once the compiles of the server it
                              stops finish, since a restart fails every
                              running compile; `builds install` fails, with
                              what launchd and the server's log say, unless
                              launchd's server then listens on the port),
                              remove each other version's folder that no app
                              build holds (APP BUILDS), point
                              Xcode's default DerivedData at the
                              volume, restart a running dashboard so it runs
                              the new code, and copy the same builds to every
                              recorded Mac host (HOSTS),
                              build builds on every Linux host from the
                              sources this builds was built from, and run
                              `builds host setup-here` on each host, naming
                              the versions whose folders this Mac keeps,
                              to remove the host's folders of the other
                              versions that no step holds, write the
                              sccache config and run the server under
                              launchd or systemd as here. When builds
                              cannot reach a host or install on it, builds
                              installs on every other host first, then fails
                              the install and names that host, and `builds
                              health` lists it until its builds names this
                              Mac's sources (`builds version`) and its config
                              holds builds' cap. Run it from
                              a fresh build (install.sh does), never from the
                              installed binary, which can't copy itself onto
                              itself
  builds version              print `builds` and a hash of the sources this
                              program was built from. A build of the same
                              sources prints the same hash on macOS and on
                              Linux, so `builds host setup` and `builds
                              health` compare it to tell whether a host runs
