builds: owns this machine's build volume, /Volumes/Builds, and everything
on it:

  <repo>/<checkout>/    one build root per checkout; checkout = main | side-N
  <repo>/app-checkouts  the names of the repo's mac lane app checkouts
                        (side-N), one per line
  <repo>/app.locks/     one lock per app checkout (app.locks/side-N), the
                        lock agents hold to build in it
  <repo>/app.queue/     who waits for the lane's locks: `order` (one ticket
                        per line, next first, the holders' at the head: one
                        per app checkout) and a ticket file per waiting
                        process
  <repo>/app-android-checkouts, app-android.locks/, app-android.queue/
                        the same for the android lane. The lanes build
                        output that is not shared (Xcode and the macOS
                        bridge; Gradle and the Android bridge), so each has
                        its own app checkouts, locks and queue and the two
                        never wait on each other. A lane with several app
                        checkouts builds in as many at once; the queue gives
                        a free lock to the next in line
  DerivedData/          Xcode's default DerivedData location
  caches/<name>/        download caches every checkout shares, each linked
                        from where its tool looks (~/.gradle -> caches/gradle)
  .trash/               folders being deleted in the background
  .trash.lock           held shared by a deletion into .trash, and exclusive
                        by the floor and prune only to rename .trash to
                        .trash-emptying.<random>/, which they then empty

`builds status` lists each of these and flags anything else on the volume as
UNKNOWN; it leaves out macOS's own volume metadata (.Spotlight-V100,
.fseventsd, .Trashes, ...).

Build roots. The repo lists its build-output paths and their size caps in
`.build-dirs` at its root, one `<path> <cap>` per line; `<path> <cap> app
<cap>` gives the folder a cap of its own in the repo's app checkouts, and a
`lane mac|android` field says that only that lane's app checkout builds into
it, keeps it warm and takes its app cap (a folder with no lane is every app
checkout's); in the other lane's checkout it is an ordinary side worktree's
folder. Each listed path is a symlink in the checkout to the same path under the
checkout's build root (target -> /Volumes/Builds/bae/main/target).

The path a tool sees never changes: cargo, xcodebuild, Gradle, dotnet and
lake always write through `<checkout>/<path>`, so sccache keys and cargo
fingerprints stay valid however often the folder behind the link is deleted
and recreated. Two checkouts never share a folder, so their builds never
wait on each other's locks.

DerivedData. bae's build scripts pass -derivedDataPath into a `.build` folder
in the checkout, so no checkout's build lives here: only what one-off
xcodebuild runs (-showBuildSettings, package resolves) and the Xcode app
write, one <project>-<hash> entry per project path, mostly SwiftPM checkouts
of about 3 GB. It is one disposable cache with a cap: entries are deleted,
least recently written first, while the folder is over its cap, when nothing
wrote to them for a day (`prune`), and first of anything under the floor.

Shared caches. Gradle, npm, NuGet, SwiftPM and sccache keep their downloads
and compiler outputs here for every checkout. Each has a cap; a cache over
its cap is deleted whole by `setup` and `prune` once nothing has written to
it for 30 minutes, and nothing else deletes one: deleting it makes every
checkout, warm ones included, download it all again, and a SwiftPM fetch cut
off halfway corrupts its cache. sccache keeps its own cache under the cap
`install` writes into its config; this tool only shows it.

Build output in the temporary folders. A build pointed at /private/tmp or
the user's temporary folder (CARGO_TARGET_DIR, -derivedDataPath, a probe
crate built where it was made) writes 5-14 GB there that nothing else
deletes. `setup` and `prune` delete each cargo target, DerivedData or
SwiftPM folder there that nothing wrote to for 30 minutes
and no process holds a file in; status lists them. They skip
/private/tmp's claude-* (Claude Code sessions' scratch, whose entries go
after three days), com.apple.* and tmux-* (live sockets). Nothing on this
machine points a build there: build into the checkout, whose paths lead to
the volume.

Commands:

                              missing folder, delete its unused build copies
                              and builds inside a folder (below), apply the caps to it, to DerivedData
                              and to the shared caches, delete idle build
                              output in the temporary folders, then make
                              sure the volume has the free-space floor.
                              The repo's hooks and build scripts run this.
  builds new [<repo>] [-b <branch>] [--for <who>]

                              the next side-N from it; link it, run its
                              post-checkout. It claims what it hands out,
                              for <who> (--for) or "builds new", under a lock
                              on the repo (claims: below)
  builds claim <checkout> <who>

  builds note <checkout> [--state waiting-on-you|winding-down|held] [<text>]
                              set the claim's one-line note, what its work

                              person, is finishing its last item, or is
                              held on purpose with no work running; a note
                              without it has no state
  builds release <checkout>   remove its claim
  builds retire <checkout>    remove a side worktree and its build root
  builds app-checkout mac|android <checkout>
                              add the side worktree to its repo's app

                              /Volumes/Builds/<repo>/app-checkouts (mac) or

  builds app-checkout remove mac|android <checkout>
                              take it out again (it refuses while a build

  builds app-checkout reset <repo> <checkout> [--matching <rev>]
                              put an app checkout on origin/main, under its
                              own lock (waits for the build holding it), for
                              one a checkout left halfway (new files, old
                              HEAD). It refuses unless every dirty path is
                              exactly what origin/main, HEAD or <rev> (the
                              commit the switch was heading to) holds there,
                              and names the paths that are not; it never
                              throws away work
  builds status               every entry on the volume: size per folder vs
                              cap, last write, links; and build output in
                              the temporary folders
  builds status --json [--no-folders]
                              the repos' checkouts and the volume's free
                              space, as JSON; --no-folders leaves out each
                              checkout's build folders, whose sizes and last
                              writes take nearly all of its time (half a
                              minute or more while agents build)
  builds health [--json]      what is stuck or needs acting on: load, free
                              space against the floor, whether sccache
                              finished compiles since the last readings
                              while clients wait 10+ min, the agent shells
                              running and which are junk (pid, age,
                              worktree, reason, command: waits, whole-disk
                              searches, duplicates of an older shell's
                              command in a worktree, idle for 20+ min; it
                              kills nothing), each claimed worktree (claim, branch,
                              uncommitted files, commits waiting to land,
                              minutes since a change, build processes there
                              or under an app lock for it), each lane's app
                              lock's holder (the build's top process when its

                              with commits waiting to land is a finding, as
                              are a lists store that fails its check and a
                              running item whose worktree is gone or has no
                              claim;
                              exits 1 when something needs acting on. Asks the daemon when one runs
  builds lists ...            the decision stack, work queue, design changes
                              and decision log of a project, in a store
                              outside every repo: `builds help lists`
  builds design render DIR BOARD [--theme light|dark]
                              a board of worktree DIR as one page of HTML,
                              drawn with DIR's design system, to open and
                              look at while drawing; the dashboard serves a
                              design change's boards the same way:
                              `builds help lists`
  builds dashboard [--port <port>]
                              run the daemon until killed: it follows the
                              volume and the checkouts through FSEvents,
                              keeps every folder's size and last write and

                              serves the page at http://127.0.0.1:7787/ and

                              wrote to for a day, build output in the

                              main, side-1, the app checkout, a claimed

                              main and the app checkout unless --include-warm
  builds cargo <subcommand> [<args>...]
                              run cargo (build, check, clippy, doc, rustc,

                              it used; the rest of its output, a program's or
                              the tests', passes through. It holds the
                              checkout's guard while cargo runs, and as it
                              exits starts `units after-build`, which deletes
                              the build copies the build replaced. Outside
                              main it builds without incremental compilation
                              (--config build.incremental=false)
  builds lock <repo> [--lane mac|android] <command> [<args>...]
                              run the command holding one of the repo's app
                              locks for the lane (the mac lane's unless
                              named: /Volumes/Builds/<repo>/app.locks/<checkout>,
                              one per app checkout; the command finds its
                              checkout in BUILDS_APP_CHECKOUT), waiting for
                              one to be free; the lock lives until the last process of the
                              command exits, and SIGTERM, SIGINT and SIGHUP go
                              to the command's whole process group; waiters go
                              in the order they came, a dead one never lets
                              anyone past the holders
  builds queue <repo> [--lane mac|android]
                              show each lane's holders and who waits, next first
  builds queue <repo> top <pid>

                              hold a lock, in the lane it waits in
  builds takeover <repo> [--lane mac|android] [<pid>]
                              with every lock of the lane held, stop the
                              build that joined last of the holders (SIGTERM
                              to its whole process group), run the waiter

                              stopped command again straight after it, by
                              itself; with a lock free, the same as `top`; a
                              pid names its lane, and with none and builds
                              waiting in both lanes, --lane does.
                              The dashboard's queue has both as buttons
  builds app-build <repo> <ref> [<step>...] [--test mac|android <Class>]...
                              check out <ref> in a free app checkout of each
                              lane the steps are in (every step's lane when

                              one argument, never read by a shell

  builds app-build <repo> --lane mac|android <ref> [<step>...] [--test <lane> <Class>]...

Commit checks. A repo's `.checks` (at its root) declares the checks its
pre-commit hook runs, one per line, `<kind> <name> <paths> <program>
[<args>...]`: kind is `check` (a static check), `fix` (a formatter; the files
it changed are staged again) or `test` (a checker's own test; CI runs it,
never the hook). paths is a comma-separated list of globs over repo-relative
paths: `*` stays inside one path segment, `**` is any number of segments, and
a glob with no `/` matches the file name anywhere. The program is not run by a
shell. As whole arguments, `{files}` is the matching staged files that still
exist and `{crates}` is `-p <crate>` for each workspace crate holding one (a
root Cargo.toml or Cargo.lock counts as every crate); with neither the check
runs whole whenever a matching file is staged.
  builds checks run [<worktree>]
                              what the pre-commit hook calls: runs the
                              check and fix lines the staged files match, in
                              file order, from the repo root, printing each
                              one's name, time and result (a failing one's
                              output too) and the run's total time. Every
                              line runs even after one fails; the exit
                              status is non-zero if any did. A fix
                              stages again the files it changed, but refuses,
                              naming the file and staging nothing, when a
                              file it changed also had unstaged changes.
                              The run is recorded in builds.sqlite in the
                              project's store folder (beside lists.json): when,
                              repo, worktree, branch, each staged file (change
                              and lines added and removed), each check or fix
                              (ran with its time and result, or skipped with
                              the files not picking it), the planning time and
                              the total. A run that can't be recorded says so
                              on stderr and ends as the checks decided; a repo
                              in no project records nothing
  builds checks stats [--project <project>] [--since <YYYY-MM-DD>]
                              read the recorded runs back (the project of the
                              current repo unless --project names one): the
                              runs, failures and the median and slowest total
                              time; per check how often it ran, failed and was
                              skipped, with its median and slowest time; and
                              the slowest runs with their diffs. --since
                              counts the runs from that local day on. The
                              dashboard shows the same, and the latest runs
  builds checks list [<worktree>]
                              print what `run` would run, without running it
  builds checks tests --since <rev> [--run]
                              the test lines whose paths match the files
                              changed in <rev>..HEAD; --run runs them and
                              fails if any fails. A <rev> that is not in the
                              history selects every test, and says so
  builds install-hook <repo>  write the repo's pre-commit hook, a script
                              that runs `builds checks run`: in
                              core.hooksPath when it is set, else in the git
                              common dir's hooks, which worktrees share;
                              running it again overwrites the file

Claims. A claim records who works in a side worktree, so another session
doesn't take it: whoever hands out the worktree (a coordinator dispatching an
agent, a person) claims it and releases it when the work lands or moves on.
It is a file in the worktree's own git dir, so it goes when the worktree
does; `status` shows it, and `retire` refuses a claimed worktree. A claim is
not a lock: agents are a series of separate commands, so nothing could hold
one, and a session that ends without releasing leaves its claim behind
(status shows its age). Short exclusive use, one build at a time, stays a
real lock, like the app lanes' locks (app.locks). A claim may carry a one-line
note of where its work stands ("waiting on Linux CI"), which `note` sets and
status and the dashboard show, and the note may carry a state the dashboard
can't read from git: waiting-on-you (a question or step only the person can
take), winding-down (the agent's last item, then its handoff) or held
(kept on purpose with no work running, the note saying why; health doesn't
flag it as idle). A claim
whose <who> ends in "(landing)" is the worktree its coordinator lands
commits from.

By default a side worktree builds host Rust only, and a repo with app builds
keeps them warm in main and in one or more side worktrees per app lane, its
app checkouts, which agents take turns in by holding a checkout's lock
(/Volumes/Builds/<repo>/app.locks/<checkout> for the mac lane); see
principles/worktree-build-priming.md. Nothing here enforces who builds what:
the caps bound whatever a checkout builds, and the floor below bounds every
checkout's idle incremental folders and the whole folders of every checkout
but main and the folders an app checkout's lane builds into (a `lane
<lane>` field in .build-dirs says which lane builds into a folder).

Side worktrees' cargo builds, the app checkout's included, run without
incremental compilation: `builds cargo` passes `--config
build.incremental=false` in every checkout but main. sccache refuses every
incremental compile; without it sccache keeps each workspace crate any
worktree built, so a build of the same sources in another worktree, or in
the app checkout, which agents move between their branches, comes from the
cache, and no incremental folders pile up. A full build takes less space
without it, so the app checkout's folders can take lower caps (`app <cap>`
in .build-dirs). Main, the person's checkout, keeps incremental.

Unused build copies. Cargo names each unit it builds (one crate target, for
one profile, target and feature set) by a hash of everything that build
depends on, dependency versions included: every dependency bump builds a new
copy of each unit above it, and the old copies stay. `cargo` records each
unit a build reports, whether it rebuilt it or found it up to date, by
setting its fingerprint folder's modification time to the moment that
build's cargo began reporting; a unit no recorded build has used counts as
used when cargo last built it. `setup` and `prune` delete, in each cargo
folder (target, target-macos, ...), every file of each unit nothing used for
BUILDS_UNUSED_DAYS days (default 3), and of each unit a newer copy replaced:
a copy of the same thing (package and target, mode, features, profile)
built from other sources (a dependency's version or git revision, or the
compiler) was used by a build that began after the unit's last use, or the
unit was built against something a unit of its package that such a build
used was built against another copy of. Copies built from the same sources
for another package selection (`-p x` against the workspace) stay side by
side, and so does whatever a unit that stays was built against. They also
delete the incremental folders only those units used, and every incremental
folder nothing wrote anywhere inside for BUILDS_INCREMENTAL_HOURS hours
(default 6) in main, whose builds compile incrementally, and every one in
the other checkouts, whose builds don't, so no build there reads them.

They delete a unit's files only while holding the checkout's guard
(<build root>/.builds-cargo.lock) and cargo's lock on that profile folder,
both taken without waiting, and keep any unit a process holds a file of.
`builds cargo` holds the guard, shared, from before it starts cargo until
cargo has exited and its report is read: cargo holds its own lock only
while it compiles, and `cargo test` runs the tests after letting go of it.
Cargo decides which units are up to date for its whole build before it
runs any of it, and nothing outside cargo can see which those are, so no
unit is deleted while a build runs; a build that starts after a deletion
finds the unit's fingerprint gone and builds it again. As it exits, `builds
cargo` starts `builds units after-build`, which deletes the checkout's
replaced copies the same way, so they go moments after the build that
replaced them. The repo's hooks and build scripts run cargo through `builds
cargo`.

Under the same locks they delete, in units still in use and in every
checkout, the object files no build or debugger reads. rustc leaves each
unit's object files beside its outputs (split-debuginfo "unpacked", macOS's
default) and a binary's debug map names the ones it was linked from: an
rlib's members, never its loose objects, and only the newest of the sets
each incremental rebuild or each build of a library with no hash in its name
leaves under new names. One busy coven checkout piled up 22 GB of them in
three hours.

A folder still over its cap is deleted whole and recreated empty; the next
build repopulates it, mostly from sccache. A folder that any process holds a
file open in, or whose checkout's guard a build holds, is never deleted.

A claimed worktree's folder is not deleted whole, since its agent is at work
in it: it is kept over its cap ("claimed, kept"). Its builds run without
incremental compilation, so its incremental folders, which grew one coven
checkout to 50 GB against a 45 GB cap, go with its unused build copies.

Separate builds inside one folder. A folder is aged by its newest write, so a
stale build beside a live one (an Xcode tree from last week beside today's)
would never age out. So `setup` and `prune` find the builds inside each
folder and delete each one no build used for three days, as they do cargo's
copies; main's and the app checkout's too, and a build a process holds a
file in is kept, and so is one the manifest names in a `keep <path>` line, in
main and the app checkout only (the person runs the app built there). Two kinds are recognized: an Xcode tree (info.plist beside
Logs and Build, up to two levels below the folder) and a SwiftPM
<triple>/debug or <triple>/release folder in a `.build` that holds
workspace-state.json. Last use is the newest write inside the build: xcodebuild
and `swift build` write on a build that finds everything up to date, which
`dotnet build` does not, and Gradle keeps no build per variant, so those
folders are not split. status lists each build under its folder with its last
use, and `status --json` as the folder's `trees`.

Sizes, against caps and in status, count each block once:
du counts the blocks of an APFS clone once per file, and cargo uplifts its
libraries out of deps/ as clones.

Caps bound each folder, not the volume: a checkout with every platform built
is 45-52 GB, and the build volume shares its APFS pool with the main disk.
So `setup` also keeps a free-space floor: under it, it deletes DerivedData's
idle entries, then the incremental folders nothing wrote anywhere inside for
60 minutes in every checkout (claimed ones, main's and the app checkout's
too; far shorter than the 6 hours above, since one costs only an
incremental rebuild of its crate and the alternative is a whole folder's
cold rebuild), under cargo's locks and keeping any a process holds a file
in, then whole idle folders across every checkout but main and the app
checkout, whose builds stay warm on purpose, and but claimed worktrees, each
least recently written first. If it still can't reach the floor it warns, naming the biggest
folders, and the build goes on: whoever runs the agents frees space or runs
fewer of them. Only under the hard floor does it fail, rather than let the
build run out of space halfway. It never deletes a shared cache.
