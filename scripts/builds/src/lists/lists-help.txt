builds lists: a project's lists, kept in a store outside every repo.

A project is a set of repos that share lists (bae holds bae and coven). Its
lists are:

  decision stack  what waits on the person: questions, work only they can
                  do, and work held until they start it (builds question)
  work queue      what the coordinator and its agents can do (builds item,
                  builds next, builds area)
  decision log    every decision, with who made it and why (builds decision)
  design changes  product design changes (a board or a design-system
                  component, not a software plan) that wait on the person's
                  review or to land (builds design)

The store is ~/Library/Application Support/builds/lists/<project>/, or
$BUILDS_LISTS/<project>/: builds.sqlite, one SQLite database, which also holds
the hook's run records, the review records and the app build records. It is
outside every repo, so no commit can carry it. Nothing edits it by hand: every
change is a command, and every command refuses a step that lacks what it needs.

Every record (a question, an item, a decision or a design change) has an id
from one counter per project, printed #N. Commands take ids as bare numbers
(`builds item take 12`), because an unquoted #12 is a comment in the shell.

Every write records who wrote it: `--by WHO` when given, else the claim of the
worktree the command runs in; with neither, the command is refused ("say who
you are with --by"). The records builds land writes after its push (`item
landed`, `design landed`, `review landed`) take the claim of the worktree they
name instead, wherever they run; builds land reads that claim before it starts
and passes it to each as --by. The project comes from `--project P`, else from
the repo of the folder the command runs in; the command refuses a repo in no
project or in two. Long text comes from a file (--details-file F; `-` is
standard input), and a compound write takes one JSON request (--request F); the
command refuses a request that does not parse or holds a field the command does
not take, and names the field that is wrong. Each write prints what it did and
what follows, such as the stack's new top and what it blocks, or the items an
answer made ready.

A question or an item may name its origin (`--origin N`), the record it came
from: a question, an item, a decision or a design change. An item that a
decision or a design change makes comes from it, and a question that `question
ask --from-item N` creates comes from item N. A record can't come from itself,
and a chain of origins can't loop. A record's trail is its chain of origins
from the first record to it. builds prints a trail as the tags of the records
on it, then each record's number, with the title of the record it came from,
such as `screen-reads audit → #3 → #50 Read each chained screen value at once →
#51`.

A question or an item may carry tags (`--tag T`, repeatable), each naming the
audit or group it came from, such as "screen-reads audit". A tag is one line
with no spaces at its ends. Only the first record of a trail that has a tag
carries it, and every later record's trail has the tag. A command refuses a tag
that an earlier record of the trail carries, and names that record. When a
command sets an origin or tags an earlier record, it removes from each later
record every tag that an earlier record of its trail now carries. `question
show`, `item show`, `question list`, `item list` and `lists show` print each
record's trail, and the list commands take `--tag T` to show only the records
whose trail has T, each question keeping its place in the stack. The dashboard
shows each row's trail, and a bar of every tag, where choosing a tag shows that
tag's entries together. A record keeps its origin and its tags when it closes,
and `edit --origin N`, `edit --tag T` and `edit --untag T` change those of an
open or a closed record; an edit of any other field needs an open one.

Every write is one SQLite transaction, taken as the write lock: the command's
own changes, the line of the write log, and the check below, then commit. A
write lands whole or not at all, and a refused command leaves every table and
the version as they were. Two commands at once both land, one after the other,
and a reader sees the last committed state while a write runs.

The tables hold most of what must always be true: ids are unique across the
four kinds of record; a reference (a wait, a closing's decision or question, a
decision's replaced decision, a design change's places) names an existing
record of the right kind, open or closed; an origin names an existing record of
any kind other than the record itself; titles are one line; every item's area
exists; a running item's worktrees are side worktrees
(<parent>/<repo>-worktrees/side-N) of project repos, one per repo; a record
leaves only the ways its kind can; and a decision has a YYYY-MM-DD date, a
decider and a body, and replaces only an older decision. A check run on every
read and before every commit holds the rest: the project has a repo; every open
question has an open item waiting on it or says why it is asked anyway, never
both; no open
item waits on a record that closed in a way that never meets a wait (dropped,
deferred, moved to the stack); no open items wait on each other in a circle; a
closed item runs nowhere; a worktree holds one branch of work; a landed closing
or part has a commit; no chain of origins loops; no record carries a tag that
an earlier record of its trail carries; and the project row names the folder's
project. A store that fails the check makes every command fail, naming each
fault, and nothing repairs it. The command that writes them checks the rest:
item titles of five to seven words, and git, files and GitHub.


DECISION STACK

The stack is asked from the top, one entry at a time: first the entries placed
first, in the person's ranked order, then the rest by how many open items each
unblocks, directly or through chains of open items (ties oldest first), then the
entries placed last. `question list`, `question show`, `lists show` and the
dashboard's Waiting on you tab all show this one order. Each of them shows, on
an entry's first lines (on the dashboard, in the row before anyone opens it),
who asked the entry and when, why it sits where it does (where someone placed
it, whether the person did and why, or that the stack orders it by what it
unblocks), and what it blocks. Each view works out what an entry blocks from the open items
that wait on it, every time it shows the entry: each item that waits on the
entry directly, with the item's priority (first, last or none), how many open
items wait behind it (on it directly or through chains of open items) and when
it opened. An entry that no open item waits on shows the reason it stays on
the stack anyway. The opened dashboard row adds the entry's plan and details.

To rank the stack as the person orders it, place each entry first, from the
person's last choice to their first: each `place N first` puts N above every
entry placed first before it. `place N --above M` and `place N --below M` put N
directly next to M, an entry already in the ranked order, and every other entry
keeps its place in that order. Placing an entry again moves it, and `place N
auto` takes it out of the ranked order.

  builds question ask --title T --kind question|your-step|held
                      --details-file F (--blocks N[,N] | --blocks-nothing WHY)
                      [--from-item N | --origin N] [--first WHY]
                      [--plan PATH --plan-number Qn] [--tag T]...
      Puts an entry on the stack: a question, work only the person can do
      (your-step), or work held until they start it (held). It needs what the
      entry blocks, open items that gain a wait on it (a running item may be
      blocked: its agent is held on the answer), or why it is asked though
      nothing waits; a --blocks item that is unknown or closed is refused.
      --first puts it on top of the ranked order, with why. --from-item N closes item N as moved
      to the stack (it was the person's work), every item that waited on N
      waits on the new entry instead, and the entry comes from N, so its trail
      has N's tags. ask refuses --from-item for a running item, and refuses
      --blocks-nothing when an item waited on N. --origin N names the record
      the entry came from when no item moves. --plan and --plan-number tie it
      to a plan's open question, and its answer carries the link.

  builds question answer N --request F
      The request: {"decision": {"title", "body", "by", "replaces"?},
      "blocked": {"ITEM": "proceeds" | {"edit": {fields}} | {"drop": WHY}},
      "work": [item drafts] | "no_work": WHY}. In one write: the decision
      (linked to the question and its work), every new item (made by the
      decision), each blocked item's edit or drop, and the question's close.
      `blocked` names every item waiting on N and no other; `work` or
      `no_work`, never both or neither; the decision's body is not empty. Only
      for a question-kind entry. Prints the items now ready and the stack's
      new top.

  builds question settle N --request F
      The request: {"by_rule": the rule or code that settles it, "blocked",
      "work" | "no_work"}. Records no decision: a question that rules settle
      is not the person's.

  builds question done N --request F
      For your-step and held entries: {"blocked", "work" | "no_work"}.

  builds question drop N --why WHY
  builds question defer N --issue URL
      Takes the entry off; refused while an item waits on it (the message
      names each and the `item wait ITEM --off question:N` that frees it).
      defer needs an open GitHub issue (`gh issue view URL --json state`,
      asked before the write lock).

  builds question place N (first|last|auto | --above M | --below M) --why WHY
                          [--by-person]
      Places it on top of the ranked order (first), at the bottom of the
      stack (last), directly above or below M in the ranked order, or by
      what it unblocks (auto, which removes its placement). The command
      refuses --above and --below when M is not in the ranked order.

  builds question edit N [--title T] [--details-file F]
                         [--blocks-nothing WHY]
                         [--origin N] [--tag T]... [--untag T]...
      --blocks-nothing replaces the why of an entry that no open item waits
      on, and edit refuses it while one does (`item wait ITEM --off
      question:N --blocks-nothing WHY` removes the last open item's wait on N
      and gives the why).
      --untag refuses a tag the entry does not carry.

  builds question show N | builds question list [--tag T]
      One entry with its details and trail (a closed one shows how it left), or
      the stack in the order it is asked.


WORK QUEUE

An item waits on records (REF: item:N, question:N, design:N or condition:TEXT).
A wait is met when its question was answered, settled or done, or its item or
design change landed; a condition is met only when someone removes it. A wait
on a question waits on the person until the question closes as answered,
settled or done. A wait on a design change waits on the person until they
approve the change, and then only on its landing. The dashboard lists a
running item's work under Waiting on you while a wait of the item waits on the
person. An open item is then, in order: running; the design session's (shown
apart, never dispatched); waiting (on a wait not met, or placed last while any
other open coordinator item that is not placed last exists); or ready. The
command looks up a relative brief path in the main checkout of the repo it
runs in (plans are in no commit); an absolute path is itself.

  builds item add --title T --area A --details-file F [--for design-session]
                  [--wait REF]... [--brief P] [--priority first|last --why WHY]
                  [--origin N] [--tag T]...
      Needs a title of five to seven words, a known area (otherwise refused,
      naming the areas and `area add`), details, waits on open records, and a
      brief that exists.

  builds item edit N [--title T] [--area A] [--details-file F] [--brief P]
                     [--for F] [--origin N] [--tag T]... [--untag T]...
      An item draft in a request (an answer's `work`) may carry "tags" too.

  builds item note N TEXT
      A lasting progress line on the item (`builds note` is the claim's).

  builds item wait N --on REF | --off REF [--blocks-nothing WHY]
      Refused when it would make items wait on each other in a circle, or on
      a closed record. A wait on a question, from `item wait --on`, `item add
      --wait` or an item draft, clears the reason the question blocks
      nothing in the same write. --off question:N on the last open item that
      waits on N needs --blocks-nothing WHY, the reason N stays open, and wait
      refuses --blocks-nothing while another open item waits on N.

  builds item take N [M...] --worktree W --branch B [--worktree W2 --branch B2]
                    --brief P [--as design-session] [--held WHY]
                    [--spec-decided N] [--rules-root DIR] [--reviewer PROGRAM]
      Marks the items running. W is a claimed side worktree of a project repo
      (the claim names the agent; the item stores none) and B a branch of it.
      Work that spans repos names one worktree and branch per repo, the nth
      --branch for the nth --worktree, and the item runs in all of them.
      Refused for an item that waits, one already running (stop it first), a
      design-session item without --as design-session, a worktree already
      running another branch, and two worktrees of one repo. --held WHY takes
      an item that waits on an open question, item, design change or
      condition (and only such an item), and notes each worktree held with WHY
      in the same write: work kept for an answer, with no agent running.
      Before the items start, take checks brief P against the product spec of
      each W whose repo has spec files (`lists design-globs --spec-files`),
      with a reviewer that runs in W with read-only tools, as `builds review`
      runs one (LANDING AND REVIEW in `builds help`). The reviewer lists each
      sentence of P that states a behavior the spec states otherwise (a
      conflict) or doesn't state (unstated). When the reviewer finds a
      conflict, take refuses the items and quotes the brief's sentence and
      the spec's text with its file and line: the person decides each
      conflict. Once they have, take the
      items again with --spec-decided N, the decision or question that records
      their choice, and take records N on the check. take prints each unstated
      behavior and takes the items: the coordinator tells the agent to add it
      to the spec. When the check gives no usable answer, take refuses the
      items. take
      records every check in the project's store, and `item show` lists the
      checks of each item. A take in a project with no spec files for W's repo
      runs no check and refuses --spec-decided. --rules-root names the
      agent-instructions checkout that holds the spec rule (default
      ~/.codex/agent-instructions), and --reviewer the program take runs in
      place of claude.

  builds item park N --worktree W --branch B [--worktree W2 --branch B2]
      The item keeps its work in W on B with no agent, and waits in the queue
      until an agent takes it there. A running item parks where it runs and
      stops running. park removes W's claim, since no agent works there, and
      keeps its project. A parked worktree belongs to its item: take refuses
      another item there and refuses the parked item anywhere else, and
      `builds new`, `prune` and `retire` never hand it out or remove it.
      park refuses an item parked elsewhere, a worktree another item runs or
      is parked in, and a worktree on another branch of work. A park of an
      item parked in the same worktrees writes nothing and removes the claims
      a failed park left. `item take` in W moves the item from parked to
      running; claim W for the agent first.

  builds item handoff N --brief P
      Sets a running item's brief for its next agent, in every worktree it
      runs in.

  builds item stop N --why WHY
      Puts the item back in the queue, out of every worktree; the why is a
      note.

  builds item finished N --made WHAT
      Closes an open item whose work made no commits (an audit, research) as
      finished, with what it made (items, stack entries, notes), and removes
      it from every worktree it runs in. finished refuses a parked item,
      whose worktree holds its work. A finished item frees the items that
      wait on it, as a landed item does.

  builds item drop N --why WHY | builds item defer N --issue URL
      drop and defer refuse an item while an open item waits on it (the
      message names them and the `item wait --off` that frees each), or when
      it is the last item an open question blocks (`item wait N --off
      question:Q --blocks-nothing WHY` frees it). defer also refuses an item
      that runs or is parked, and needs an open GitHub issue. The person drops
      an item to throw its work away. drop refuses an item while another open
      item of any project runs or is parked in one of its worktrees, since the
      work there is that item's too: `builds item stop N` ends the item's run
      and leaves the work to the other items, and a drop of an item that runs
      nowhere throws nothing away. For each worktree the item runs or is
      parked in, drop first closes the item and records on it the branch,
      the commits on it and on HEAD that origin/main lacks and the files not
      committed, in one store write that saves all of it or none. Then drop
      detaches the worktree at origin/main, discards those files (ignored ones
      stay), deletes the branch and, last, removes the worktree's claim. When
      git fails, drop says what failed; running the same drop again throws
      away the rest of the recorded work. `item show` prints what a dropped
      item held, and git keeps the commits until it removes unreachable
      objects.

  builds item place N first|last|none --why WHY
      Sets an open item's priority as `item add --priority` does: first goes
      ahead of the queue, last waits until nothing else is open, and none
      gives it back to the order of area and age. The why is kept.

  builds item check-landing DIR [--done N]... [--part N]... SHA...
  builds item landed DIR [--done N]... [--part N]... SHA...
      What builds land runs. check-landing, before builds land fetches
      anything: each N is open and running in DIR itself, the worktree whose
      branch holds the commits (an item that runs in worktrees of two repos
      accepts a landing from either), and each SHA is on the branch of one of
      them. landed, after the push: each SHA is on origin/main; --part records
      a landed part and leaves the item running, and --done closes the item as
      landed and ends its running everywhere, so an item that spans two repos
      takes --part in the landing from one repo and --done in the landing from
      the other. The same call twice records once; landed refuses a different
      set of commits for an item already closed as landed. landed records who
      landed as --by, else DIR's claim. When --done ends the last item running
      in a worktree with nothing left to land, landed releases that worktree.

  builds item show N | builds item list [--running] [--ready] [--area A] [--for F]
                                      [--tag T]
      list --running prints each running item's marker line, one per
      worktree it runs in (agent, repo, worktree, branch, brief); show prints
      them all.

  builds next
      The ready coordinator items in dispatch order: items placed first
      (oldest first), then by area order and age, and items placed last once
      nothing else is open. The design session's items never appear. A parked
      item names the worktree and branch its work waits in.

  builds area add NAME [--after AREA] | rename OLD NEW | move NAME --after AREA
              | remove NAME
      remove is refused while an item, open or closed, is in the area; rename
      follows the items, open and closed.


DECISION LOG

The log is never closed: a decision is revised only by a later decision that
replaces it.

  builds decision add --request FILE [--by WHO]
      Records a decision, dated today. The request is JSON: title, by (who
      decided: person, coordinator, design-session, ...), body, and either
      `work` (item drafts the decision makes, each waiting as its draft says)
      or `no_work` with the reason there is none; optionally `replaces` (the
      id of an earlier decision it revises) and `plan` ({path, number}).
      Refused: both or neither of work and no_work; an empty body; a replaces
      that is not a decision; a draft the item rules refuse; a brief that is no
      file under the repo's main checkout. A question's answer is recorded by
      `question answer`, not here.

  builds decision edit N [--title T] [--body-file FILE|-] [--by WHO]
      Changes a decision's title or body. Refused when it changes nothing.

  builds decision find WORD...
      The decisions whose title or body holds every word, ignoring case,
      newest first, one line each.

  builds decision show N
      One decision in full: who decided and recorded it, the question it
      answered, the items it made and where they are, what it replaces and
      what replaces it, and its body.

  builds decision list [--plan PATH] [--since YYYY-MM-DD]
      The log, newest first, one line each; --plan keeps the decisions
      recorded against that plan, with their plan numbers.


DESIGN CHANGES

The design session records a design change when its boards are drawn, and the
change waits on the person's review until they approve it; `builds help
workflow` says how the session and the person work through one. builds land
--design N refuses the change before approval, and landing closes it. When the
commits hold several changes, builds land takes --design once for each and
closes each one.

A repo's design files are the globs given to `lists init` or `lists
design-globs`:

  --design-places   a board file (design/mocks/*.dc.html) is a place, and so
                    is a component folder (design/system/components/*/),
                    counted once however many of its files change
  --design-sources  the shared design-system sources (the component sources,
                    tokens.json); a path that matches both counts as a
                    source, not a place, and a change to one can change any
                    component's drawing, so the design change lists the
                    components whose drawing changes
  --spec-files      the spec files: each section (by heading) a design
                    change's commits touch is a place, written
                    spec/bae.md#Heading; a spec file alone is no design change.
                    `item take` checks each brief against them too

Other changed files under design/ are shared design files. Commands that read
git take a worktree DIR and find the project from its repo (or --project).
You may rebase the commits: builds compares a design change with commits by
the paths they change and by the bytes of the boards, components and sources
at the change's last commit and at the commits' last one, never by commit
hash.

The review page shows the change's words under their headings, with every board
of the change drawn twice, side by side, in frames the person can zoom (never
an image): now, the board as it stands on origin/main, and proposed, the board
at the last commit of the change's range, each drawn with its own commit's
design system. A board the change adds says it has no now; a board it deletes
shows only its now. The dashboard serves the page at /design/N, the change's
card in the Waiting on you tab opens it, and the page draws each board again on
every request from the files at those commits, read with git, so a worktree
with another branch checked out does not change what it shows.

The page's Approve button records the approval as `builds design approve N
--by-person` does, and the card then says "approved, waiting to land". The
button works only from the page served at 127.0.0.1 or localhost on this Mac:
the daemon refuses an approval from another address. The approval then sends
"Design change #N of project P approved: land it." once to the inbox of the
session that recorded the change, which `design record` and `design amend` keep
from the session's environment (CLAUDE_CODE_MESSAGING_SOCKET and
CLAUDE_CODE_MESSAGING_TOKEN; a session that bypasses permission prompts holds a
message unless its token comes with it). The token is that session's secret: it
stays in the store, and nothing prints it, logs it, puts it on a page or a
board, or returns it in JSON. When no session listens on the socket any more,
the card says the session that recorded the change has ended, and nothing is
sent again.

  builds design places DIR REV...
      Each REV is a commit, or a range (A~1..A) that stands for its commits;
      the command refuses a REV that names no commit. Here and in `only` and
      `check`, the commits are those the REVs name.
      Prints every design path the commits change, one per line: `place
      PATH` (a component folder once, with a trailing /), `source PATH`,
      `deleted PATH` (a board file the commits delete), `spec PATH#HEADING` or
      `shared PATH`; nothing when there is none. builds land requires
      --design N whenever this prints anything, once for each design change
      that resolves some of it.

  builds design only DIR REV...
      Prints nothing and succeeds when the commits are a design change and
      every path they change is a design file (boards, the design system,
      spec sections); otherwise names the paths that are not. Only then does
      builds land take --design N alone, once for each change, with no
      --done or --part: the design changes hold the app work.

  builds design record --request FILE       (`-` for standard input)
      FILE: {"title", "details", "worktree", "range": "origin/main..HEAD",
      "places": {PLACE: {"item": N} | {"new": ITEM_DRAFT} | {"matches": HOW}},
      "boards": {BOARD: {"link": CANVAS_URL}},
      "review": [{"heading": H, "words": WORDS,
                  "boards": [{"board": BOARD_PATH, "caption": C,
                              "theme": "light" | "dark"}]}],
      "no_app_place": WHY, "fix": WHAT}.
      `places` answers every design place the range changes (a board, a
      component folder, a spec section) with an open item that does the app
      work, a new item (which waits on this design change, so no one can take
      it before the board lands), or how it was checked that the app already
      matches. When the range changes shared design-system sources, `places`
      also lists each component folder whose drawing changes, changed by the
      range or not (it must exist), answered the same way; `no_app_place`
      says instead that no component's drawing changes (a comment in the
      source, or a design system with no components), and `places` still
      answers each board the range changes. Record rejects `no_app_place`
      when the request lists a component or the range changes one. Shared
      files that are no source (a README, a build script) change
      no drawing. For these files, the request gives only `no_app_place`,
      unless `places` answers a place.
      `boards` gives every board place its canvas link in a project that
      publishes a canvas (`lists design-globs --canvas yes`); a request of
      any other project has no `boards`, and its change holds no links.
      `fix` says what a change that changes no design fixes: boards made to
      follow the design system's measures, or a drawing mistake corrected.
      Such a change needs no `review` and is approved when recorded. An amend
      without `fix` makes the change wait on the person's review again.
      `review` is the review page, in order: each section is a heading, the
      words under it (optional; `code`, **bold**, paragraphs and `-` lists)
      and its boards (optional), each a board file of the repo's design
      places that exists at the range's last commit, with its caption and the
      theme it is drawn in (a board may be on the page twice, once per theme,
      and a board the change did not touch may be there to compare). Every
      board place of the change must be on the page. A board file the range
      deletes needs no answer, link or place on the page: it is listed as
      deleted, and the page shows only its now.
      `worktree` and the range's last commit are stored with the change, and
      the page reads each board from that repo at that commit, so the commit
      must stay in the repo while the change is open. A change recorded
      before the last commit was kept draws nothing until it is amended. That
      commit needs the design system's sources (design/system/tokens.json,
      and the design/system/build-bundle.py that writes
      design/system/components/bundle.css and bundle.js) and each board's
      size in design/mocks/canvas.json.
      Refused, naming each, when a changed place is left unresolved, an
      answer names a place the range does not change, `matches` has no how,
      an item is closed or missing, a board of a project that publishes a
      canvas has no link, a project that publishes none gives `boards`,
      `review` is missing,
      empty or has a heading with no text, a board of it is no file, no board
      place or has no caption, a board of the change is not on it, or the
      range changes no design files.

  builds design amend N --request FILE
      The same over a new range, which N then holds to: a stored place the
      range no longer changes (a board renamed before landing) drops out with
      its board link and its place on the review page, and a place the range
      does change needs an answer. `title` and `details` are optional;
      `worktree` replaces the one stored; `review`, when given, replaces the
      whole page (left out, the page stays, and must still hold every board
      of the change). The amend stores the new last commit and clears the
      record that builds sent the recording session the approval message.
      The amend keeps the person's approval when the change keeps its
      places, deleted boards and review page, and the new last commit holds
      every board, component and changed source byte for byte as the commit
      they approved did, as after a rebase onto a moved main that changed
      none of them. Otherwise the amend clears the approval, since the person
      approved the boards the session drew before; an amend of a fix without
      `fix` clears it too.

  builds design approve N --by-person
      Records the person's approval, which only they give: pass --by-person
      once they have said to land the change, never on your own judgment. The
      same approval again writes nothing, and the command sends nothing to
      any session.

  builds design check N[,N...] DIR REV...
      Succeeds when one of the open changes N resolves each place the
      commits change; one change that holds each changed board or component
      (any of them, for a changed source) holds the same bytes for it at its
      last commit as the commits' last commit does; one of them answers for
      the shared files and sources; each change resolves or answers for
      something the commits change; and the person has approved each.
      Otherwise it names what does not hold. builds land runs it once with
      every change its --design flags name.

  builds design landed N DIR SHA...
      What builds land runs after the push, with SHAs on origin/main: records
      them and closes N, which frees the items waiting on it. The same commits
      again record once; other commits for a landed change are refused. Who
      landed is --by, else DIR's claim.

  builds design drop N --why WHY
      Closes open change N, which will not land, and records WHY as the
      reason. The change leaves the Waiting on you tab and the open lists,
      and `builds design show N` prints the reason. The command refuses a
      change that is already closed, and a change that an open item waits
      on: it names each such item and the `builds item wait ITEM --off
      design:N` command that removes the item's wait.

  builds design show N | builds design list
      `show` prints one design change, whether open, landed or dropped;
      `list` prints the open ones, one line each.

  builds design render DIR BOARD [--theme light|dark] [--now | --at REV]
      Prints board BOARD of worktree DIR as one page of HTML, the way the
      design canvas draws it, dark unless asked: from DIR's files as they
      are, with --now as the board stands on origin/main, or with --at REV at
      that commit or branch, read with git, each with the design system at
      that commit. BOARD is the name (mac.welcome.open-failed) or the path
      (design/mocks/mac.welcome.open-failed.dc.html). It follows the boards
      the board mounts (dc-import), applies each board's own values
      (renderVals), sc-if and sc-for, and uses DIR's design system: the
      bundles build-bundle.py wrote (design/system/components/bundle.js and
      bundle.css), and the stylesheet that the builds tool writes from
      design/system/tokens.json, as `design tokens-css` does. A board names a
      component with its bundle's namespace (Bae.MacButton is window.Bae's
      MacButton). Redirect it to a file and open that; it loads React and
      Roboto from the net. The review page's frames load this page. Reads no
      store.

  builds design tokens-css DIR
      Writes worktree DIR's design/system/tokens.css from its tokens.json: a
      block of color properties per theme of `color.themes`, the first on
      :root too; one :root block of the other families' tokens and a
      --font-<key> property per stack of `type.families`; and a class per
      text style of `type.groups`. builds draws boards with the same
      stylesheet; this command writes it for other tools that load it, such
      as a repo's screenshot checks. Reads no store.


PROJECTS

  builds lists init PROJECT --repos R,R [--canvas yes|no]
                    [--design-places R:GLOB,...] [--design-sources R:GLOB,...]
                    [--spec-files R:GLOB,...] [--by WHO]
      Makes the project's store. --repos names the repo folders the project
      covers, as their main checkouts' folders. --canvas yes says the
      project publishes its boards as a claude.ai canvas, so its design
      changes give each board's canvas link; without it the project
      publishes none. --design-places, --design-sources and --spec-files
      give each repo's design files, one REPO:GLOB each (DESIGN CHANGES,
      above). Refused when the store exists.

  builds lists design-globs PROJECT [--canvas yes|no]
                    [--design-places R:GLOB,...] [--design-sources R:GLOB,...]
                    [--spec-files R:GLOB,...] [--by WHO]
      Sets the design files of a project whose store exists, with the same
      REPO:GLOB entries as init, and with --canvas whether the project
      publishes its boards as a canvas (bae does; builds does not). Each
      glob flag given replaces that kind's globs for each repo it names; the
      other kinds and repos keep theirs. `builds
      health` names a repo whose main checkout has a design folder and that
      no project gives --design-places globs, since the design session cannot
      record a design change in that repo. A repo two projects hold needs
      the globs in one of them: the one whose design files it holds.

  builds lists add-repo PROJECT REPO [--by WHO]
      Adds a repo to the project, so its worktrees run items, land commits
      and resolve to the project from their folder (agent-instructions is in
      bae this way: its work is tracked on bae's lists). Refused when the
      project already has the repo. Two projects may hold one repo
      (agent-instructions is in bae and builds); a worktree of it then must
      name its project with `builds claim --project` or `builds new --project`,
      and a command outside a claimed worktree takes --project.

  builds lists show [--json | --tag T] [--project P]
      The stack in the order it is asked, then the queue, as text, each record
      with its trail; with --tag T only the records whose trail has T; with
      --json the whole state with its derived fields (each item's state, what
      each question blocks, each record's trail, the flow of the last 14
      days), the JSON the dashboard reads. The dashboard adds, to each
      worktree a running item runs in, the agent, note, note state and
      commits waiting to land of its claim.

  builds lists project-of DIR
      Prints the project DIR's repo belongs to, or nothing. Refused when the
      repo is in two projects and the worktree names neither (`builds claim
      --project`).
