builds lists: the lists of a project, kept in a store of their own.

A project is a set of repos that share lists (`bae` holds bae and coven). Its
store is ~/Library/Application Support/builds/lists/<project>/, or
$BUILDS_LISTS/<project>/: lists.json (the whole state) and lists.lock. It is
outside every repo, so no commit can carry it. Nothing edits it by hand:
every change is a command, and every command refuses a step that lacks what
it needs.

Every record has an id from one counter per project, printed #N. Commands
take ids as bare numbers (`builds item take 12`): an unquoted #12 is a
comment in the shell.

Every write records who wrote it: `--by WHO` when given, else the claim of the
worktree the command runs in, else the command is refused ("say who you are
with --by"). The project comes from `--project P`, else from the repo of the
directory the command runs in (a repo in no project, or in two, is refused).

Writes take an exclusive lock, read the state, apply the command, run the
whole-state check, and replace lists.json by an atomic rename: a write lands
whole or not at all, and a refused command leaves the file byte for byte as it
was. Two commands at once both land, one after the other.

The whole-state check runs on every load and before every write. It holds
that: ids are unique and below the counter; every reference (waits, an item's
origin, a decision's question, work and replaced decision, a design change's
places, how a record left) names a record of the right kind that exists, open
or closed; no item waits on itself through a chain of items; no open item
waits on a record that closed in a way that never meets a wait (dropped,
deferred, moved to the stack); every open question has an open item waiting
on it or says why it is asked anyway; titles are one line and item titles are
five to seven words; every open item's area exists; a running item's worktree
is a side worktree (<parent>/<repo>-worktrees/side-N) of a project repo; a
record left only the ways its kind can; decisions have a YYYY-MM-DD date, a
decider and a body; the version is the log's last line. A store that fails it
makes every command fail naming each fault. Nothing repairs it.

Commands in this part:

  builds lists init PROJECT --repos R,R [--design-places R:GLOB,...]
                    [--design-sources R:GLOB,...] [--spec-files R:GLOB,...]
                    [--from FILE] [--by WHO]
      Makes the project's store. --repos names the repo directories the
      project covers (as `Checkout` names them: the main checkout's folder).
      --design-places gives each repo's design globs, one REPO:GLOB each; a
      path a commit changes that matches one is a design place;
      --design-sources and --spec-files give the shared design-system sources
      and the spec files (see Design changes below). --from loads
      a whole state from FILE (`-` for standard input) instead of an empty
      one, and runs the whole-state check on it; --repos and the glob flags
      must then match what the file holds. Refused when the store exists.

  builds lists add-repo PROJECT REPO [--by WHO]
      The project carries the work of one more repo, so its worktrees run
      items, land commits and resolve to the project from their directory
      (agent-instructions is added to bae this way: its work is tracked on
      bae's lists). Refused when the project already has the repo or another
      project holds it.

  builds lists show [--json] [--project P]
      The stack in the order it is asked, then the queue, as text; with
      --json the whole state with its derived fields (state of each item,
      what each question blocks, the flow of the last 14 days), the JSON the
      dashboard reads. The dashboard adds, to each running item, the agent,
      note, note state and commits waiting to land of its worktree's claim.

  builds lists project-of DIR
      Prints the project DIR's repo belongs to, or nothing. Refused when the
      repo is in two projects.

Design changes (a product design change: a board or a design-system
component, not a software plan). A design change is recorded when its boards
are drawn and waits on the person's review: it shows in the sidebar's Waiting
on you tab as a light card (its title, the items it blocks, who recorded it)
with a Details toggle that opens its review page in a modal over the dashboard,
until the person approves it. The review page is the change's words under
their headings, with every board of the change drawn live from the change's
worktree in a frame the person can zoom (never an image); the dashboard serves
it at /design/N and draws each board again on every request, so a redraw shows
on reload. land.sh --design N refuses it before approval; landing closes it, so
it leaves the tab. The design session lands through land.sh like everyone else,
from bae's landing worktree (side-7).

A repo's design files are the globs given to `lists init`. --design-places:
a board file (`design/mocks/*.dc.html`) is a place, and so is a component
folder (`design/system/components/*/`), counted once however many files in it
change. --design-sources: the shared design-system sources (the component
sources, tokens.json, tokens.css); they win over a place glob, and a change to
one can change any component's drawing, so the design change lists the
components whose drawing changes. --spec-files: the spec files; in a design
change, each section (by heading) its commits touch is a place, written
`spec/bae.md#Heading`; a spec file alone is no design change. Other changed
files under `design/` are shared design files. Commands that read git take a
worktree DIR and find the project from its repo (or --project); commits may be
rebased, since places are compared by path.

  builds design places DIR SHA...
      Prints every design path the commits change, one per line: `place PATH`
      (a component folder once, with a trailing /), `source PATH`,
      `spec PATH#HEADING` or `shared PATH`; nothing when none. land.sh
      requires --design N whenever this prints anything.

  builds design only DIR SHA...
      Prints nothing and succeeds when the commits are a design change and
      every path they change is a design file (boards, the design system,
      spec lines); otherwise names the paths that are not. land.sh takes
      --design N alone, with no --done or --part, only then: the design
      change holds the app work.

  builds design record --request FILE       (`-` for standard input)
      FILE: {"title", "details", "worktree", "range": "origin/main..HEAD",
      "places": {PLACE: {"item": N} | {"new": ITEM_DRAFT} | {"matches": HOW}},
      "boards": {BOARD: {"link": CANVAS_URL}},
      "review": [{"heading": H, "words": WORDS,
                  "boards": [{"board": BOARD_PATH, "caption": C,
                              "theme": "light" | "dark"}]}],
      "no_app_place": WHY}. `places` answers every design place the range
      changes (a board, a component folder, a spec section): an open item
      that does the app work, a new item (which waits on this design change,
      so it can't be taken before the board lands), or how it was checked
      that the app already matches. When the range changes shared design-system
      sources, `places` also lists each component folder whose drawing
      changes, changed by the range or not (it must exist), answered the same
      way; `no_app_place` says instead that no drawing changes (a comment in
      the source), and is refused beside a listed component or a changed board
      or component. Shared files that are no source (a README, a build
      script) change no drawing: only `no_app_place`, unless a place is
      resolved. `boards` gives every board place its canvas link. `review` is
      how the review page reads, in order: each section is a heading, the
      words under it (optional; `code`, **bold**, paragraphs and `-` lists)
      and its boards (optional), each a board file of the repo's design places
      that exists in `worktree`, with its caption and the theme it is drawn in
      (a board may be on the page twice, once per theme, and a board the
      change did not touch may be there to compare). Every board place of the
      change must be on the page. `worktree` is stored with the change: the
      dashboard draws every board of the page from it, each request, so it
      must hold the boards while the change is open. Boards need the design
      system's generated files (design/system/tokens.css and
      design/system/components/bundle.css and bundle.js) in that worktree, and
      each board's size in design/mocks/canvas.json. Refused, naming each,
      when a changed place is left unresolved, an answer names a place the
      range does not change, `matches` has no how, an item is closed or
      missing, a board has no link, `review` is missing, empty or has a
      heading with no text, a board of it is no file or no board place or
      has no caption, a board of the change is not on it, or the range
      changes no design files.

  builds design amend N --request FILE
      The same over a new range; the answers merge into N's places and
      boards, and `title` and `details` are optional; `worktree` replaces the
      one stored, and `review`, when given, replaces the whole page (left out,
      the page stays, and must still hold every board of the change). The
      person's approval is cleared: they approved what was drawn before.

  builds design approve N --by-person
      Records the person's approval, which only they give (say "--by-person"
      once they have said to land it, never on your own judgment). The same
      approval again writes nothing.

  builds design check N DIR SHA...
      Every place the commits change is resolved in open change N, shared
      files and sources are answered for, and the person has approved it;
      names what is not.

  builds design landed N DIR SHA...
      As land.sh calls it after the push, with SHAs on origin/main: records
      them and closes N, which frees the items waiting on it. The same
      commits again record once; other commits for a landed change are
      refused.

  builds design show N | builds design list
      One design change, open or landed; the open ones, one line each.

  builds design render DIR BOARD [--theme light|dark]
      Prints board BOARD of worktree DIR as one page of HTML (dark unless
      asked), the way the design canvas draws it: BOARD is the name
      (`mac.welcome.open-failed`) or the path
      (`design/mocks/mac.welcome.open-failed.dc.html`). It follows the boards
      the board mounts (`dc-import`), applies each board's own values
      (`renderVals`), `sc-if` and `sc-for`, and uses DIR's design system
      (design/system/components/bundle.js and bundle.css,
      design/system/tokens.css), which must be built there. Redirect it to a
      file and open that; it loads React and Roboto from the net. This is
      the page the review page's frames load. Reads no store.

What is derived, never stored: a wait is met when its question was answered,
settled or done, or its item or design change landed (a condition only when
removed); an item is running, the design session's (shown apart, never
dispatchable), waiting (a wait not met, or priority last while any other
open coordinator item that is not itself last exists) or ready; the stack
asks `placed first` questions (newest first), then those that unblock the most
open items directly or through chains of open items (ties oldest first), then
`placed last`.

Decisions (the log, never closed):

  builds decision add --request FILE [--by WHO]
      Records a decision. The request is JSON: title, by (who decided:
      person, coordinator, design-session, ...), body, and either `work` (item
      drafts the decision makes, each waiting as its draft says) or `no_work`
      with the reason there is none; optionally `replaces` (the id of an
      earlier decision it revises) and `plan` ({path, number}). Its date is
      today. Refused: both or neither of work and no_work; an empty body; a
      replaces that is not a decision; a draft the item rules refuse; a brief
      that is no file under the repo's main checkout. A question's answer is
      recorded by `question answer`, not here.

  builds decision edit N [--title T] [--body-file FILE|-] [--by WHO]
      Changes a decision's title or body. Refused when it changes nothing.

  builds decision find WORD...
      The decisions whose title or body holds every word, ignoring case,
      newest first, one line each.

  builds decision show N
      One decision in full: who decided and recorded it, the question it
      answered, the items it made and where they are, what it replaces and
      what replaces it (derived from the decisions that name it), its body.

  builds decision list [--plan PATH] [--since YYYY-MM-DD]
      The log newest first, one line each; --plan keeps the decisions
      recorded against that plan, with their plan numbers.
The decision stack: builds question ...

Long text comes from a file (--details-file F; `-` is standard input). Compound
writes take one JSON request (--request F), refused with the field that is
wrong when it does not parse or holds a field the command does not take. A
write lands whole or not at all; each prints what it did and what follows (the
stack's new top and what it blocks, the items an answer made ready).

  builds question ask --title T --kind question|your-step|held
                      --details-file F (--blocks N[,N] | --blocks-nothing WHY)
                      [--from-item N] [--first WHY] [--plan PATH --plan-number Qn]
      Puts an entry on the stack: a question, work only the person can do
      (your-step), or work held until they start it (held). Requires what it
      blocks: open items, which gain a wait on it (a running item may be
      blocked: its agent is held on the answer), or why it is asked though
      nothing waits. Refuses a --blocks item that is unknown or closed.
      --first puts it on top, with why. --from-item N closes item N as moved to
      the stack (it was the person's work); every item that waited on N waits
      on the new question instead, so the question blocks them. Refused for a
      running item. --plan and --plan-number tie it to a plan's open question;
      its answer carries the link.

  builds question answer N --request F
      The request: {"decision": {"title", "body", "by", "replaces"?},
      "blocked": {"ITEM": "proceeds" | {"edit": {fields}} | {"drop": WHY}},
      "work": [item drafts] | "no_work": WHY}. In one write: the decision (with
      the question and its work linked), every new item (made by the decision),
      each blocked item's edit or drop, and the question's close. `blocked` has
      every item waiting on N and no other; `work` or `no_work`, never both or
      neither; the decision's body is not empty. Only for a question-kind
      entry. Prints the items now ready and the stack's new top.

  builds question settle N --request F
      The request: {"by_rule": the rule or code that settles it, "blocked",
      "work" | "no_work"}. Records no decision: a question settled from rules is
      not the person's.

  builds question done N --request F
      For your-step and held entries: {"blocked", "work" | "no_work"}. A
      question-kind entry is closed with `answer`.

  builds question drop N --why WHY
  builds question defer N --issue URL
      Takes the entry off with no item waiting on it (the message names each
      and the `item wait ITEM --off question:N` that frees it). defer needs an
      open GitHub issue (`gh issue view URL --json state`, asked before the
      lock).

  builds question place N first|last|auto --why WHY [--by-person]
      Where it sits: first, last, or auto (the order of what it unblocks).

  builds question edit N [--title T] [--details-file F]
                         [--blocks-nothing WHY | --blocks-something]
      --blocks-something is refused when no open item waits on it: a question
      blocking nothing needs a why.

  builds question show N | builds question list
      One entry with its details, or the stack in the order it is asked (a
      closed question shows how it left).
The work queue (builds item ..., builds next, builds area ...). REF is item:N,
question:N, design:N or condition:TEXT. A relative brief path is looked for in
the main checkout of the repo the command runs in (plans are not in any
commit); an absolute path is itself.

  builds item add --title T --area A --details-file F [--for design-session]
                  [--wait REF]... [--brief P] [--priority first|last --why WHY]
      Needs a title of five to seven words, a known area (refused otherwise,
      naming the areas and `area add`), details, waits on open records, and a
      brief that exists.
  builds item edit N [--title T] [--area A] [--details-file F] [--brief P]
                     [--for F]
  builds item note N TEXT
      A lasting progress line on the item (`builds note` is the claim's).
  builds item wait N --on REF | --off REF
      Refused when it would make items wait on each other in a circle, or on a
      closed record. A condition is met only by --off.
  builds item take N [M...] --worktree W --branch B --brief P [--as design-session]
      W is a claimed side worktree of a project repo (the claim names the
      agent; the item stores none) and B a branch of it. Refused for an item
      that waits, one already running (stop it first), a design-session item
      without --as design-session, and a worktree already running another
      branch.
  builds item handoff N --brief P      A running item's next agent's brief.
  builds item stop N --why WHY         Back to the queue; the why is a note.
  builds item drop N --why WHY | defer N --issue URL
      Refused while the item runs, an open item waits on it (the message names
      them and the `item wait --off` that frees each), or it is the last item
      an open question blocks. defer needs an open GitHub issue.
  builds item place N first|last|none --why WHY
      Sets an open item's priority as `item add --priority` does: first goes
      ahead of the queue, last waits until nothing else is open, none gives it
      back to the order of area and age. The why is kept; refused for a closed
      item.
  builds item check-landing DIR [--done N]... [--part N]... SHA...
  builds item landed DIR [--done N]... [--part N]... SHA...
      What land.sh calls. check-landing (before anything is fetched): each N
      is open and running in a worktree of DIR's repo, and each SHA is on the
      branch of one of them. landed (after the push): each SHA is on
      origin/main; --part records a landed part, --done closes the item as
      landed. The same call twice records once; a different set of commits
      for an item already closed as landed is refused.
  builds item show N | list [--running] [--ready] [--area A] [--for F]
      list --running prints each item's marker line: Running: agent, repo
      worktree branch, brief.
  builds next
      The ready coordinator items in dispatch order: priority first (oldest
      first), then by area order and age, last items once nothing else is
      open. The design session's items never appear.
  builds area add NAME [--after AREA] | rename OLD NEW | move NAME --after AREA
              | remove NAME
      remove is refused while an item is in the area; rename follows the items.

builds release W is refused while an item runs in W, naming it.
