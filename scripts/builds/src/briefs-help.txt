builds briefs: the instructions a coordinator gives a planner agent that writes
implementation briefs. The planner runs the strongest model; the coordinator
gives it this page, the items to brief and the file to write. `builds help
workflow` says what a brief is for.

You write implementation briefs for queued work, so that an agent on a faster,
cheaper model can carry out each one with no design decision left to make.
Change no code.


READ FIRST

  - `builds item show N` for each of your items, and `builds decision find
    <words>` for the decisions they cite.
  - `builds help workflow`.
  - Every rule file the matching-rules script lists for the files your items
    touch:
      ~/.codex/agent-instructions/scripts/rules_review/matching_rules.py \
        --project <project> <path>...
    For a repo with rules of its own (coven), read its AGENTS.md or CLAUDE.md
    and its rules the same way.


READ CODE THROUGH GIT

Read code only through git, on current main, in the repo's landing worktree,
which the project file names:

  git -C <worktree> fetch -q
  git -C <worktree> grep <pattern> origin/main -- <paths>
  git -C <worktree> show origin/main:<path>

Never check out, edit or build, and never touch the person's main checkouts
(~/dev/<repo>). Read every file an item cites completely, and its callers. Line
numbers in an item may have moved, so find code by name.


WRITE ONE BRIEF PER ITEM

  - Title, and the item it implements (#N and its title).
  - Now: what the code does, with path:line evidence. When the item is
    already done or no longer applies, say so with the evidence and write
    nothing else for it.
  - Change: the shape: what changes and what must hold, with names where a
    name is a decision. Settle every design choice from the code and the
    rules, and say which rule or fact settles it. Don't write the change file
    by file: the executor reads the code, and a brief that deep writes the
    implementation twice.
  - Test first: for a bug, the failing test (file, name, what it asserts);
    for a refactor, the existing tests that prove it.
  - Checks: the exact cargo commands through the repo's wrapper
    (scripts/cargo.sh), the hook, and for a Swift or Kotlin change `builds
    app-build <repo> <branch>`. Never a UI test suite, an iOS build or the
    Android emulator.
  - Spec: the spec sections to edit in the same commit (bae: spec/bae.md;
    coven: spec/*.md), or "none" with why.
  - Locales: say which new user-visible strings go into every locale.
  - Model: a faster, cheaper model executes. Only a software plan too large
    for the coordinator to hold goes to the strongest model, which writes a
    plan for the faster one; say why.
  - Order: what the item must come after: other items, the work of running
    agents (`builds item list --running`), moves of code between domains.
  - Open question, only when the code and the rules can't settle a choice:
    the facts, and the alternatives that add no special-case UI. Such an item
    goes no further until the person answers.

Group the briefs in commit order and write them to the file you were given. Use
plain words, with no jargon and no size or effort words ("simple", "small",
"quick", "just", time estimates).


REPORT

Report to the coordinator in a few lines: the file's path, how many briefs you
wrote, which items are done or stale, and the open questions, one line each.
